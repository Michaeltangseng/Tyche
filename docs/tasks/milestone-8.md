# 任务单：里程碑 8 默认 playbook、清单与端到端试用

## 目标

补齐让项目室在真实项目上可用的内容：默认 playbook、角色侧写与平台立场提示词、检查点清单、就绪检查与最终评审、复盘与本地指标、模板、用量；然后用真实 Agent 在一个小型真实项目上完整试用一次。

- 里程碑 6、7 已验收。
- 已读 `docs/handoff-guide.md`。

## 任务

### 任务 8.1 默认 playbook 数据

在 `desktop/src/project-room/default-playbook.cjs` 中，以数据形式定义需求文档「默认 playbook」表的九个检查点：顺序、产物、默认软硬关卡（需求、功能架构、实施计划、每个开发里程碑、最终评审为硬关卡）、评审轮数上限 3、续跑上限、依赖关系、哪些检查点产出清单（功能架构产出模块清单，实施计划产出里程碑清单）。替换里程碑 4 中的最小占位。

### 任务 8.2 角色侧写与平台立场提示词

1. 每个默认角色一份侧写（需求文档「席位」：在意什么、拒绝什么、怎样算过得去、什么情况必须停下来问人），中英两套。
2. 平台立场提示词（M3 4.1 第 1 层），只管流程：结尾标记约定、评审的立场（「通过」是正当结论、意见要引用原文或证据、开头写几行摘要、驳回轮的说明）、修订以替换和删除为主。
3. 参考 BMAD-METHOD 与 GitHub Spec Kit 的角色与模板写法（架构 M1 的 Playbook 一行）：**引入前核对两者的 LICENSE**，在汇报中附上许可证名称与链接；只改写，不复制大段原文；不使用 BMAD 的商标。许可证不允许时停下来问。
4. 测试：每个角色都有非空的中英侧写；提示词中包含两种结尾标记的说明；不包含「默认要求修改」之类的指示（需求文档明确禁止）。

### 任务 8.3 检查点清单（R4）

清单文件 `meldwork/checklists/<检查点>.json` 的 zod 模式（模块清单：每项一个文件路径与主笔席位；里程碑清单：每项名称、是否硬关卡、实现的需求条目）。`evaluate-submission` 中的清单校验（M4/M6 B3.3）接上这个模式；人在硬关卡接受后，项目级进度（里程碑 5 的 `project-progress.cjs`）据此新增实例。测试：合法清单展开；非法清单进入「清单无效」关卡。

### 任务 8.4 就绪检查、最终评审、复盘

就绪检查与最终评审作为默认 playbook 中的检查点类型，提示词要求评审者对照需求条目编号检查追踪链（R13）。复盘检查点（R29）：最终评审接受后可选开启，首屏显示本地指标（M13 第 9 节）与复盘评审者的建议；每条建议可单独采纳，采纳生成 playbook 或侧写的新版本（里程碑 4 的版本机制），可选「同时更新模板」。

### 任务 8.5 用量（M10）

依据 M3 第 9 节：ACP 的 `usage_update`；Claude 与 Codex 的本地日志按会话号读取，只提取用量字段，读取范围限定在约定目录。日志的文件名与字段以里程碑 0 采集的样例为准，样例放进 `desktop/test/fixtures/usage/`。费用按价格表估算并标明「估算」。经现有的 `recordReplyUsage` 记录。测试：样例解析；读取范围不越出目录；拿不到时为「不可用」。

### 任务 8.6 组队占位（R18）

只保留接口：一个函数签名与说明「输入需求文本，输出结构化团队草案，经校验后交人确认」，返回 `PROJECT_AUTO_TEAMING_UNAVAILABLE`。界面上不显示任何入口。

### 任务 8.7 端到端试用

用两种不同的真实 Agent（一种主笔、一种评审），以默认 playbook 完整推进一个小型真实项目（例如一个命令行小工具），从访谈到最终评审与复盘。过程中至少包含：一次打回；一次在开发里程碑中修改已接受的需求文档（触发「文档新版本」关卡）；一个开发里程碑。

记录（写进 `docs/spikes/milestone-8-trial.md`）：每个关卡的原因、决定、决定用时；评审通过后人工要求修改的次数；遇到的所有问题，按严重程度分类。严重问题修复后重跑相关的检查点；其余问题列入后续计划。
