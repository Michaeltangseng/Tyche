# 需求：项目室

定稿。2026-11-12 起草，2026-11-13 第五版（吸收两轮独立对抗评审、源码核实和用户裁决）。还没开发。本文按完整产品定义需求；分几期交付，写在之后的实施计划里，不在需求阶段裁剪。

## 真实需求

现在用户自己就是调度器：把文档拷给 Agent B 请它评审，把意见拷回 Agent A 请它修改，判断够不够，再开下一阶段。真正需要人动脑的只有两件事：插入自己的判断，以及拍板通过。其余是搬运。

项目室把这套工程方法变成能执行的流程，让人从搬运工变成决策者：只在关卡上出现，其余时间流程自己推进。

稀缺的是人的注意力。项目室要优化的是：每一份被接受的产物，消耗了人多少注意力，以及人有多放心。由此有两条要求：关卡首屏要在大约 30 秒内让人判断「直接通过，还是需要细看」；人要能看到评审抓住了什么、漏了什么，否则一旦漏过一次重要问题，人就会回去盯每一轮。

现有群聊是按轮次说话，角色不会从任务里长出来，也没有一份会留下来的项目文件。项目室的中心是被接受的产物版本，聊天是侧边通道。

## 设计原则

1. Agent for agent。单个 Agent（例如 Claude Code、Codex）自带完整的体系和生态，已经能独立完成一个大任务。项目室不往下钻：不把大任务拆成小任务分派，不跟踪 Agent 内部的步骤，不自研调度去合并零碎结果。项目室工作在更上层：派大任务、在检查点让其他 Agent 介入评审校验、把结论交回主笔继续、在关卡上让人拍板。
2. 平台只看检查点，不看过程。平台能判断的只有：谁在做、是否到了检查点、评审结论是什么、人选了什么。其余交给 Agent。
3. 复用优先，但不是不能改。优先使用 Meldwork 已有能力和成熟开源项目；需要改时，以系统稳定为前提，做最小的、有测试的改动。
4. 按完整产品定义。需求和架构阶段不以「先做一个小版本」为由忽略问题；交付顺序在实施计划里安排。

## 用户的方法

1. 主笔先向人提问，弄清楚没说出来的偏好、底线和「不要什么」；已有代码的项目先摸清现状。
2. 调研：现有产品、同类开源项目、各自优缺点、哪些可以直接复用。可以由几位 Agent 各自独立调研，主笔汇总。
3. 主笔写需求文档。
4. 另一位、使用不同模型的评审者做对抗性评审，挑缺漏和矛盾。
5. 主笔修改。人可以在修改期间插话，把自己的判断加进去。
6. 往复，直到这份文档大家基本满意。
7. 用同样方式写功能架构文档、模块文档 1..N、实施计划。
8. 开发：主笔做完一个大任务（里程碑），再请人评审，满意后再做下一个。
9. 全部做完之后做一次最终评审：看结果、分析问题、打回修改。

用户的经验：至少要有 需求文档 + 功能架构 + 模块 1..N + 实施计划，项目质量才有保证。

## 核心模型

### 检查点循环（唯一的执行原语）

```
主笔用自己的体系完成一个大任务，结尾标记 ready
  → 评审者介入评审校验（可以是一位，也可以是几位各自独立）
  → 评审结尾标记：pass / revise / needs-human
      revise      → 主笔读评审，自行决定改什么、驳回什么，继续做 → 再次 ready
      pass        → 硬关卡：等人；软关卡：自动继续，事后进摘要
      needs-human → 关卡（等人）
  → 达到轮数上限，或产物内容没有变化 → 关卡（等人）
```

阶段只是 playbook 里一串检查点的定义：每个检查点写清楚产物是什么、谁主笔、谁评审、是硬关卡还是软关卡、轮数上限。平台不理解阶段内部。

### 平台能读的信号

平台不解析自由文本。状态机只读下面这些和语言无关的信号；其余内容都是给人和 Agent 看的。

| 信号 | 谁给 | 取值 | 平台怎么用 |
| --- | --- | --- | --- |
| 主笔结尾标记 | 主笔 | `ready`（到达检查点）/ `question`（需要人回答）/ `continue`（这一轮没做完，需要接着做） | `ready` 进入评审；`question` 进入关卡；`continue` 在同一原生会话里续跑，续跑次数有上限，到上限进入关卡 |
| 评审结尾标记 | 评审者 | `pass` / `revise` / `needs-human` | 见检查点循环 |
| 检查点清单 | 主笔写成结构化文件，人在硬关卡上确认 | 下一段要产出的文件列表，例如模块文档 1..N、里程碑 1..M，以及各自的主笔席位 | 确认后落盘，状态机按清单生成后续检查点 |
| 产物内容哈希 | 平台计算 | — | 判断产物是否变化、文档是否有新版本 |
| 人的选择 | 人 | 关卡选项 | 推进、打回、续轮 |

任何标记缺失或无法解析，一律按需要人处理，不重试猜测。

### 什么时候需要人

原则：只有这一轮存在必须由人做的裁决时，才停下来等人。具体是：

- 硬关卡上的评审 `pass`。
- 评审 `needs-human`、主笔 `question`。
- 达到轮数上限，或者评审要求修改而产物内容没有变化。这种情况一律等人，不自动继续，避免未修改的稿子流进下一阶段。
- 已接受的需求文档或功能架构文档出现新版本（见「实施中调整文档」）。

主笔驳回评审意见本身不叫人。驳回写在回应文件里，下一轮评审者读到后决定：接受驳回就给 `pass`；仍然坚持就给 `needs-human`，交人裁决，而不是再给一次 `revise` 来回争。

检查点只能由评审的 `pass` 或人的接受通过。人可以在没有 `pass` 的情况下选择「接受现状」，这一选择记入决策记录。

### 默认 playbook

| 顺序 | 检查点 | 产物 | 默认关卡 |
| --- | --- | --- | --- |
| 1 | 访谈与现状 | 主笔的问题与人的回答；已有代码时附现状说明 | 主笔提问即进入关卡，人答完继续 |
| 2 | 调研 | 各调研者的独立笔记，主笔汇总成一份调研文档：现有产品、开源项目、优缺点、可复用的部分 | 软 |
| 3 | 需求文档 | 引用已接受的调研文档，写明复用取舍；需求条目编号 | 硬 |
| 4 | 功能架构 | 列出模块，标明覆盖的需求条目 | 硬 |
| 5 | 模块文档 1..N | 每个模块一份 | 软 |
| 6 | 实施计划 | 分期、里程碑、每个里程碑的验收方式、追踪到需求条目 | 硬 |
| 7 | 就绪检查 | 评审者检查需求、架构、模块、计划彼此一致 | 软；不一致时转硬 |
| 8 | 开发里程碑 1..M | 代码与验收结果 | 软；计划里可以把某个里程碑标为硬 |
| 9 | 最终评审 | 评审结论、问题清单、打回目标 | 硬 |

默认的硬关卡：需求、功能架构、实施计划、每个开发里程碑、最终评审。软关卡在评审 `pass` 时自动继续，结果在下一个硬关卡上以批量摘要的方式呈现。软硬可以在 playbook 里逐个修改；例如用户嫌里程碑关卡太多，可以把里程碑改成软关卡，只保留计划里点名的。

开发里程碑默认是硬关卡，对应用户方法第 8 步「做完一个大任务再请人评审」。这是用户的方法，不为节省注意力而默认改写。

第 5 步有几份模块文档、第 8 步有几个里程碑，来自检查点清单：主笔在功能架构和实施计划里写出清单文件，人在这两个硬关卡上确认。

### 并行：各自的工作区，主笔汇总

并行有两种，规则相同：每份文件在任何时刻只有一位写入者。写入者按文件算，不按「整个项目室一位主笔」算。

- 多份草稿、收成一份：调研笔记、备选方案。几位席位各写自己草稿区里的一份，主笔读完汇总成一份正式文档。
- 多份正式产物：模块文档 1..N。检查点清单里每份文档有自己的主笔席位，可以同时写，各自走评审循环。

现有代码里有可借鉴的机制，但不能直接用：V4 独立提案阶段给每位 Agent 单独的写入作用域（`desktop/src/workspace/local-workspace-agent-invocation.cjs:278`），键是「会话 id + Agent 种类」。同一种 Agent 的两个席位会落进同一个作用域。项目室要的是按文件划分的新租约（见「项目室与群聊」）。草稿放在工作目录下各席位自己的子目录里。

### 评审：自由思考，收口最小化

评审者的提示词只给立场，不给模板：找出缺漏、矛盾、不现实的地方；认为方向错了，可以直接提出替代方案。正文按评审者自己的习惯写。

结尾只需要一个和语言无关的机器标记，表示结论：`pass` / `revise` / `needs-human`。缺少标记或无法解析时，按 `needs-human` 处理，不重试猜测。界面上显示本地化的文字（中英双语）。参考现有的控制回执解析器（`desktop/src/collaboration/collaboration-receipt.cjs`）。

主笔读完评审后，在回应中写明改了什么、驳回了什么以及理由。允许驳回，避免主笔一味讨好评审。

防止不收敛和谄媚（来自同类工具的失败报告，见「参考产品」）：

- 「通过」是正当结论。不指示评审者「默认要求修改」，否则它会编造问题交差。
- 评审意见要引用原文或证据。
- 主笔的驳回不在主笔和评审者之间来回争：有驳回时，检查点转为硬关卡，由人裁决。
- 第二轮起，评审者优先看相对上一版的变化和上一轮的意见；进入硬关卡之前做一次全文评审，避免只看 diff 漏掉改动与未改动部分之间的矛盾。
- 修订以替换和删除为主，不一轮轮追加。这是提示词约定，平台不检查。
- 产物内容哈希没有变化时，不再发起新一轮评审，直接进入关卡。

### 评审意见写成文档，文档是唯一真源

每一轮评审的原文、主笔的回应，都落成项目室里的文件，例如：

```
reviews/<检查点>/r<轮次>-<评审者席位>.md
reviews/<检查点>/r<轮次>-response.md
```

- 平台不解析单条意见，只保存文件、读取结论标记。意见的跟踪就是这些文件本身：后面的评审者、主笔、人都引用同一份文件，而不是各自记忆里的聊天。
- 评审文件由平台在评审者这一轮结束时写入，评审者保持只读，不需要写权限。
- 评审文件与产物一起快照。人在关卡上裁决驳回时，裁决写进 `decisions.md` 并引用对应的评审文件。
- 下一轮评审者读取：当前草稿、相对上一次接受快照的 diff、上一轮的评审文件和主笔回应文件。

## 两种信息：过程给人看，文档给 Agent 看

| | 执行过程（轨迹） | 文档（产物、评审、回应、决策） |
| --- | --- | --- |
| 内容 | Agent 每一步做了什么：思考摘要、计划、工具调用、命令、读写的文件、输出 | 结论 |
| 给谁 | 人：判断能不能信任这次评审、主笔是怎么做的 | Agent 和人：交接与引用的唯一真源 |
| 是否进入其他 Agent 的上下文 | 否，避免噪音 | 是 |

### 执行过程完整可见

用户在本地终端里能看到 Agent 的每一步。项目室（以及现有群聊的「运行详情」）要把这些原样搬进来：点击某位 Agent，在侧边详情里看到它这一轮完整的执行过程，接近在终端里看它工作。

现状：主进程只把过滤后的事件交给界面（`desktop/src/agents/cli/cli-runtime-event-sanitizer.cjs`）。事件类型限于状态、回答、思考摘要、计划、工具开始/更新/结果摘要、警告；摘要截到 2000 字符、详情截到 4000 字符；命令原文、原始输出不进入界面（`architecture.md` Trust Boundaries 第 6 条）。

这条边界要调整。依据：这是用户自己机器上、用户自己启动的 Agent，隐藏执行过程不是为了对用户保密。用户裁决：先完整显示，不再隐藏，后期按使用体验再收。

- 命令原文、工具参数、工具输出、读写的文件路径、思考内容、原始逐字输出，全部显示。CLI 提供什么就显示什么；有的 CLI 只给思考摘要、不给完整思维链，界面如实显示。
- 唯一保留的处理是密钥脱敏（API key、token 等，复用现有逻辑）。它不隐藏任何步骤，只把密钥值替换掉；这也是 `AGENTS.md`「不向 renderer 暴露凭据」的硬性规则。可执行文件路径原样显示，`AGENTS.md` 相应条款需要修改。
- 显示方式：侧边详情里按步骤展示，接近终端；长内容按需从主进程分页拉取。
- 范围：现有群聊的「运行详情」和项目室一起改，是同一套组件。
- 保留期限和磁盘上限：暂不设置，后期根据体验调整。这是用户接受的代价。
- 密钥脱敏只能替换已知的密钥值（来自 CLI 的环境与配置）。Agent 读出来的文件内容里如果含有其他密钥（例如读了某个 `.env`），会原样显示。这也是用户接受的代价。
- 这一改动要同步修改 `architecture.md` 的 Trust Boundaries 第 6 条。

## 已接受版本与上下文交接

- 主笔在草稿上工作。人或软关卡接受时，平台把产物存进应用私有区的影子 git 仓库（参考 Cline 的 checkpoints），记下提交号。
- 下一个检查点用新的原生会话启动，读取已接受的版本（以及实施期间产生的新版本和变更记录），不继承上一阶段的讨论噪音。
- 「只读已接受版本」靠提示词无法强制：席位能读工作目录，就能读到未接受的草稿。平台做的是确定性检查：每个检查点开始前，比较工作目录里上游文档的内容哈希和已接受版本；不一致时提示人（可能有人在应用外改了文件），由人决定以哪一版为准。草稿区里别人的草稿能被看到，这一点不强制隔离，标为提示词约定。
- diff 显示的是当前草稿相对上一次接受快照的变化，由影子仓库计算。平台不改动用户自己的仓库、分支和暂存区；用户可以在关卡上手动选择「同时提交到 git」。

### 追踪链与决策记录

- 需求条目编号。架构和模块文档标明覆盖哪些条目；实施计划的每个里程碑标明实现哪些条目、怎么验收。就绪检查和最终评审按这条链检查。开发阶段的评审也对照已接受文档检查实现是否偏离。
- 人的插话、关卡上的裁决、被接受的驳回，都记成决策：决定了什么、为什么、谁定的。决策写进 `decisions.md`（项目室产物的一部分），重新打开上游文档时先读决策记录。

## 团队与配置

### 席位

一个席位是一个角色，至少包含：

| 字段 | 说明 |
| --- | --- |
| 角色名与职责 | 例如「架构主笔」「对抗评审」「调研员」 |
| 背后的 Agent | 本机某个已安装的 Agent 种类 |
| 角色提示词 | 用户可编辑，叠加在平台的立场提示词之上 |
| 权限 | 可组合的能力：读工作目录、写自己的草稿区、写工作目录、运行命令（例如测试）。文件写入另受写入者租约约束 |
| 参与的检查点 | 在哪些检查点做主笔、评审或调研 |

权限由用户配置，例如实施阶段的评审者可以运行测试但不改文件。权限映射到各 CLI 已有的权限模式；某个 CLI 表达不了某种组合时（例如 Claude 的只读模式目前是 `--permission-mode plan`，跑不了测试，见 `desktop/src/agents/cli/cli-invocations.cjs:251`），配置界面要提示，不能静默降级或放宽。

同一种 Agent 可以占多个席位，各有独立的原生会话。

席位可以随时调整（包括访谈之后发现需要换人）。调整席位不会让已接受的产物失效；新席位用新的原生会话，读取已接受的文档接手。

默认评审者与主笔使用不同种类的 Agent；用户只装了一种时允许同种评审，界面提示。

### 用户介入的两个时机

1. 开始之前：配置团队和 playbook，包括席位、角色提示词、权限、关卡软硬、轮数上限。可以保存成模板复用。
2. 执行过程中：以正常成员的身份对当前检查点发表意见。插话是当前产物的新要求，本轮已经得到的「通过」作废，评审者要重看。主笔正在一轮里工作时，插话排队，在这一轮结束后交给主笔（print/exec 模式无法在一轮中途注入内容）；人也可以选择停止当前一轮，立即交给主笔。

### 组队

当前版本由人工组队：用户从默认 playbook 或模板出发，手动指定席位。自动组队（用户输入需求后，由组队步骤给出团队草案和裁剪过的 playbook，人确认后开始）先占位，不实现。

组队可以使用快速决策模型（例如 jev）。按产品边界，它要通过本机 CLI 或等价的本地方式调用，不直接接入某一家的 API；起一次本机进程是秒级，不是毫秒级。这个模型目前没有接入 Meldwork，接入方式要在架构阶段确定。没有可用的组队模型时，回退到默认 playbook 加现有的确定性路由（`desktop/src/agents/agent-routing.cjs`）。

### 推进

由应用里的确定性状态机负责：当前检查点、谁在做、结论、关卡、人选了什么。它不占席位，不调用模型。项目室的状态（检查点进度、已接受快照的哈希、轮次、决策）需要自己的持久存储，不能放在 Run Ledger 里（Run Ledger 只保留最近 64 次运行，是单次运行的检查点）。

## 长时间执行

主笔可能连续工作几个小时。原则是信任主笔自己的体系，平台只做最少的事：

- 不因为时间长而杀掉主笔。现状：默认无活动窗口 10 分钟、工具窗口 20 分钟（`desktop/src/workspace/local-workspace-runtime-contracts.cjs:18-19`），整个工作区一套（`desktop/src/workspace/local-workspace.cjs:143` 装配）。工具执行期间，原始输出不刷新计时（`desktop/src/runs/invocation-watchdog.cjs:106`）：一次工具调用如果只有原始输出、没有工具更新事件，约 20 分钟后被中止，strict 与否一样；CLI 持续发出工具更新事件时计时会刷新。项目室需要按调用设置看门狗策略：长时间无活动时提醒人，由人决定停止或继续，而不是直接中止。这是对现有代码的必要修改。
- 主笔一轮结束时按结尾标记处理：`question` 变成关卡，人回答后在同一原生会话里继续；`continue` 自动续跑。
- 应用重启或电脑休眠恢复后，从项目室的持久状态和已接受快照恢复。可写入的一轮不自动续跑，需要人确认（与现有 Run Ledger 规则一致）。

## 界面

- 侧边栏以项目室为一级，项目室下列出它的群聊。
- 群聊主区域右上角显示全体成员头像。点击头像弹出席位配置：角色、背后的 Agent、角色提示词、权限、增删席位。
- 右侧是工作目录的目录树，接近 Codex 的侧栏：可以折叠，可以预览文件，可以看当前草稿相对上一次接受快照的 diff。这是项目室的主视图之一。renderer 不能任意读文件，需要新的窄 IPC：限定在工作目录内、处理符号链接、限制大小（见 `architecture.md` Trust Boundaries）。
- 顶部或侧边显示检查点进度：当前检查点、主笔、评审轮次、在等谁。
- 关卡首屏：评审结论、评审者写的摘要、是否有驳回、改动的文件和 diff 入口、软关卡的批量摘要；选项至少有接受、再给几轮、打回并附意见、裁决驳回。
- 首屏摘要由最后一轮的评审者写，不由主笔写，避免人看到的是主笔的自我陈述。评审者在评审文件的开头写几行摘要：看了什么、结论、还有什么没解决、主笔驳回了什么。这是唯一要求评审者遵守的格式，正文仍然自由。写不进首屏的内容在评审文件和回应文件里，首屏给出入口。平台自己确定性地补充：改动的文件列表、diff 统计、轮次、用时。
- 所有界面文字中英双语。新的弹层支持 Escape 关闭，并阻止背景滚动。

## 与 Meldwork 现有能力的关系

项目室是群聊之上的一层，结构见「默认规则」中的「项目室与群聊」。项目室不使用 V4 的责任图协商、work package 和多人合成。

现有群聊的几种模式（单次回答、并发回复、顺序讨论、自动讨论）要不要保留、改造，还是基于项目室的原语重建，单独作为一个模块讨论，在模块文档阶段定。需求层面的约束：

- 留下来的模式与项目室共用同一套席位配置（角色、Agent、提示词、权限）和同一套完整轨迹显示。
- 观察：项目室的原语已经覆盖了这几种模式的核心用法。并发回复 ≈ 几个席位各自写草稿；顺序讨论 ≈ 写作者与评审者往复；自动讨论（V4）是本文明确不要的细粒度协商。重建可以显著减少代码量，但要处理已有会话记录的兼容。

源码核实结果（2026-11-13）：

| 能力 | 能否复用 | 说明 |
| --- | --- | --- |
| Human Gate | 可以，要改造 | 已有 decision / input 类型，持久化，选项不超过 16 个；但它绑定单次运行，等待者在内存里。阶段关卡要跨运行、跨重启 |
| Context Pack 的 blob 存储 | 可以 | 它的哈希针对任务输入和提示词，不针对工作区文件；内容寻址存储可以拿来存已接受快照 |
| Outcome Store 的 Findings | 不适合 | 只有 support / contradict，记录不可变。项目室不做条目级跟踪，所以不需要它 |
| Run Ledger | 只用于单次运行 | 最多 64 个运行；项目室状态需要自己的存储 |
| 写入者租约 | 可以，要扩展 | 作用域是会话，需要提升到项目室层的文档级协调；V4 独立提案已有按 Agent 分开的作用域，可以复用来做并行草稿 |
| 看门狗 | 要修改 | 见「长时间执行」 |
| 智能组队路由 | 可以作为回退 | 确定性路由，不调用模型 |

## 产品边界

- 平台不执行 Agent 写出来的命令。验收命令（测试、构建）由具有「可以运行命令」权限的席位在它自己的 CLI 沙箱里执行，结果写进它的评审。
- 写入工作目录需要用户在席位权限中显式开启。写入 `.git` 只在用户于关卡上选择时发生。
- 组队模型、ACP 适配器等新依赖，都通过本机 CLI 接入，保持 provider-agnostic，不加网关专用适配。

| 失败模式 | 对应规则 |
| --- | --- |

| 文档多到人审不完 | 精简要求、软关卡批量摘要、评审者写的首屏摘要 |
| 实现偏离 spec | 追踪链、就绪检查、开发评审对照已接受文档 |
| 长任务上下文丢失 | 按检查点换新会话，读取已接受快照和变更记录 |

## 默认规则（原缺口，已给出默认值）

以下规则为默认值，可在功能架构阶段调整，也可由用户在 playbook 中修改。

### 打回与级联

- 任何关卡都可以打回到某个上游检查点。打回前，关卡展示影响预览：哪些已接受的下游产物会被标为过期。
- 被打回的检查点重新进入循环。完成后，过期的下游依次重新进入循环：由各自的主笔读取上游的变化和决策记录，判断哪些需要改，不默认整份重写；改完照常评审。
- 已经写好的代码属于开发里程碑的产物，同样标为过期，由实施主笔对照新的文档判断修改范围。

### 轮数上限与关卡选项

- 默认每个检查点最多 3 轮评审。
- 到达上限时的选项：接受现状、再给 N 轮、换评审者、打回并附意见、人自己改后再评审。

### 实施中调整文档：不锁定，但可追踪

日常开发中，实施到一半发现部分目标需要调整是正常的。已接受的文档在实施阶段不锁定，要求是改动可追踪、其他 Agent 能正常拿到最新信息：

- 主笔可以直接修改已接受的文档。每次修改形成新的版本快照，并在 `changes.md`（或文档末尾的变更记录）里写明：改了什么、为什么、在哪个里程碑、谁改的。
- 其他席位下一次被调用时，平台把「自你上次读取以来，哪些文档有了新版本」以及对应的变更记录交给它，它读取最新版本，而不是旧快照。
- 已接受的需求文档或功能架构文档出现新版本时，平台立即开一个关卡（按文件判断，不靠理解内容），人接受这次调整，或打回到对应的上游检查点。其他文档（模块文档、实施计划）的改动在下一个关卡的摘要里单独列出。
- 小改动不需要回到上游检查点重走一遍循环，避免因为一处措辞调整把整条链标为过期。

### 最终评审的可运行预览

默认指打开文件、看 diff、评审者指出问题。需要运行产品时，由具有运行命令权限的席位在自己的沙箱里启动和检查，平台只展示结果和轨迹。

### 主笔失败与接替

主笔的 CLI 登录失效、额度用尽或连续失败时，进入关卡。人可以重试、换一位 Agent 接替。接替者用新的原生会话，读取已接受快照、当前草稿、评审和回应文件继续。

### 成本与通知

- 暂不设预算上限。每个检查点显示用量（CLI 提供时）。
- 到达关卡时用系统通知提醒，不引入远程通知渠道。

### 项目室与群聊

项目室和群聊是两个层级：

- 项目室是项目本身：一个工作目录，一套已接受的文档、评审和决策记录，一份 playbook 和团队配置，一条检查点进度。一个项目只有一个项目室。
- 群聊是项目室里的工作会话，可以有多个。例如一个群聊推进主流程，另一个群聊临时讨论某个技术问题，或者处理某个里程碑。
- 项目室里的所有群聊共享同一个真源：它们读取的都是项目室里的文档（产物、评审、回应、决策、变更记录），而不是彼此的聊天内容。一个群聊里形成的结论，要写进文档，才能被其他群聊看到。
- 任何群聊都可以修改项目室的文档，修改遵守「实施中调整文档」的变更记录规则。同一份文档在任何时刻只有一位写入者，即使写入请求来自不同的群聊。现有的写入者租约按会话划分（见「与 Meldwork 现有能力的关系」），项目室需要把文档级的写入协调提升到项目室这一层。
- 群聊之外，单聊和不属于任何项目室的普通群聊保持现有行为。

### 方法论的反馈回路

最终评审结束后，平台提供一个可选的复盘检查点：评审者列出最终评审发现、但前面检查点没有抓到的问题，以及对应的 playbook 或提示词调整建议。是否采纳由人决定。playbook 和角色提示词带版本，可以回退。
