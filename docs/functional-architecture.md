## 1. 总体结构

```
┌────────────────────────── Renderer（Vue） ──────────────────────────┐
│ 侧边栏：项目室 ▸ 群聊      群聊头部：成员头像 / 席位配置            │
│ 检查点进度   关卡面板      目录树 / 预览 / diff     完整轨迹面板    │
│ M12 组件，按 M13 交互规格实现：待我决定 / 右侧抽屉（文件·轨迹）    │
└───────────────┬───────────── preload：窄 IPC ──────────────────────┘
                │ project:* / workdir:* / trace:* / 现有 local-workspace:*
┌───────────────┴──────────────── Main ───────────────────────────────┐
│ M2 检查点引擎（纯转移函数 + 发件箱） ── M1 项目室存储               │
│   │        │            │                                           │
│   │        │            └─ M5 关卡（检查点实例的一部分）            │
│   │        └─ M4 产物与版本（影子 git 仓库、diff、过期传播、记录文件）│
│   └─ M3 席位调用适配 ── 现有 invokeAgent ── ACP（优先）/ print 回退  │
│                  └─ M6 写入协调（复用调度器租约）                    │
│ M7 完整轨迹（轨迹存储 + 分页）   M8 工作目录浏览   M9 组队   M10 用量 │
└──────────────────────────────────────────────────────────────────────┘
```

核心思路：

- 项目室是 main 进程里的一层新协调器，目录 `desktop/src/project-room/`。它不扩展 `LocalWorkspaceAutoRunner`（V2/V3/V4 的执行器），只通过现有的单 Agent 调用入口 `LocalWorkspace.invokeAgent`（`desktop/src/workspace/local-workspace.cjs:2895`）驱动 Agent。Agent 的进程、会话恢复、事件、Run Ledger、失败分类全部沿用现有链路。`invokeAgent` 的第一个参数是群聊，所以检查点调用一律以项目室的「主流程」群聊为宿主（决定 A13）。
- 状态机只读四类输入：主笔与评审的结尾标记、人的关卡走向（继续改 / 接受 / 打回）及其自由文本、相对影子仓库某次提交的 `git diff`、已确认的检查点清单（R2）。它不调用模型，不解析自由文本，也不另算一份内容哈希。
- 文件是 Agent 之间唯一的共享真源（R9）；完整轨迹只给人看（R21）。

## 2. 关键架构决定

| # | 决定 | 理由 | 替代方案及放弃原因 |
| --- | --- | --- | --- |
| A1 | 项目室作为独立协调器，经 `invokeAgent` 调用 Agent | 复用调用链约 1,400 行的成熟逻辑；不碰 V4 执行器（约 8,000 行） | 扩展自动讨论执行器：耦合 V4 回执与阶段，违背 agent for agent |
| A2 | 轻量项目元数据放 `meldwork-workspace.json`，引擎状态放独立私有存储 | 工作区文件每次保存整体重写；引擎状态和版本记录会持续增长 | 全放工作区文件：写放大；全放私有存储：侧边栏快照要跨两个来源拼装 |
| A3 | 原生会话键加入「项目、检查点、席位」 | 同种 Agent 多席位需要独立会话（R16）；新检查点要新会话（R10） | 每个席位一个合成群聊：污染侧边栏与消息存储 |
| A4 | 已接受版本 = 影子 git 仓库中的提交（参考 Cline checkpoints）：仓库放在应用私有区，通过 `core.worktree` 指向项目工作目录。同一项目的全部 git 操作经一个先进先出的互斥队列串行执行，共用影子仓库自己的一份索引 | 快照、diff、删除识别、忽略规则、大文件全部由 git 提供；不碰用户的 `.git`（R25）；非 git 目录同样可用。串行化避免并发调用在 `index.lock` 上冲突；共用一份索引保留 git 的文件状态缓存，整个工作目录的快照因此足够便宜 | 自研哈希清单 + 内容寻址快照 + diff 库：重复造 git；写用户的 `.git` 或用户仓库里的 `refs/meldwork/*`：违背 R25；每次快照用临时索引：丢失状态缓存，大目录每次全量重算哈希 |
| A5 | 写入协调 = 按目标文件的建议性租约 + 轮后变更检测，检测覆盖整个工作目录 | CLI 沙箱以整个工作目录为单位，无法在进程层面限制到单个文件；能做到的诚实保证是「排队 + 事后发现越界并交人处理」。越界改动在并行写入时不一定能归属到某一位席位，界面如实说明（M6） | 为每个席位复制工作树：Agent 失去完整上下文，违背 agent for agent |
| A6 | 项目关卡是 `CheckpointInstance` 的一个字段，存在 M1 的项目状态文件里，不扩展 Human Gate | 引擎是项目关卡唯一的等待者，状态本来就随实例持久化，跨重启不需要孤儿决定路径。Human Gate 的记录模式是严格的（`human-gate-records.cjs`：`runId`、`agentRunId` 必填，`gateId` 由内容哈希得出，只有 `input` 类型可以带附言，选项最多 16 个），而「打回」要携带目标检查点，可选的上游数量随清单增长，会超过 16 个；它的恢复路径（`canResume`、`reconcileDecisions`、`reconcileOrphans`）全部围绕运行，并与 V4 共用 | 扩展 Human Gate：要改严格模式、两处附言校验、三条恢复路径，且碰到 V4 共用代码，改动面比新写一个字段大。调用中由 Agent 发起的权限类关卡仍然是 Human Gate，不受影响 |
| A7 | 完整轨迹走独立通道：main 写入经脱敏的追加日志，renderer 分页拉取 | 现有摘要通道带多层截断，且被 Run Ledger 与证据胶囊依赖；另开通道不破坏它们 | 直接放宽现有通道的上限：会撑大 Run Ledger 与消息存储 |
| A8 | 结尾标记沿用现有回执语法 `[[MELDWORK_…:{json}]]`，新建独立解析模块 | 流式隐藏（`answer-marker-filter.cjs`）可直接复用；不扩展 V4 白名单，避免与 V4 耦合 | 扩展 `collaboration-receipt.cjs` 的 V4 阶段：把项目室绑进 V4 记录 |
| A9 | Agent 接入以 ACP 为主通道，现有 print/exec 适配作为回退。Claude 与 Codex 在实测通过之前，主通道仍是现有的 print / exec | ACP 的工具调用事件自带结构化完整内容（M7）；每次工具调用都经客户端审批，权限可以在一处统一实现（M3）；进程常驻，可在一轮中取消，适合长时间运行（R20）；Meldwork 已有成熟的 ACP 运行器 | 为每个 CLI 分别补完整轨迹映射和权限参数：工作量随 Agent 数量增长 |
| A10 | 单个检查点的推进是一个纯函数 `transition(instance, event) → { instance, effects }`，配一张穷举的「状态 × 事件」转移表（`docs/modules/m2-checkpoint-engine.md`）；项目级进度是 M1 里的检查点实例加依赖 | `CheckpointInstance` 已经是唯一的权威记录，状态机库的快照只能当缓存，升级后还要重建，等于维护两种持久化格式。检查点内部只有十来个状态，纯函数加表格就能穷举测试；副作用以数据形式返回，正好接入发件箱（A11）。模块文档和里程碑的数量来自运行时确认的清单，项目级进度本来就不是一张静态图 | XState v5（上一版的选择）：快照与定义版本绑定、actor 生命周期要和实例同步，收益只剩可视化，不抵新增依赖；LangGraph.js：为 LLM 图设计，恢复时节点重跑；Temporal：需要服务进程，违背本地优先；Bernstein 等编排器：细粒度任务图，违背 agent for agent |
| A11 | 副作用走发件箱：转移结果连同待执行的副作用先原子写入项目状态文件，再逐个执行；每个副作用有确定性 ID，执行器按 ID 幂等。副作用的结果不单独标记完成，而是作为事件进入下一次转移，与「已消费」标记同一次原子写入；每个副作用记录产生它时实例的执行纪元，纪元过期（上游重开）的副作用不执行；重启时重放未消费、未过期的副作用 | 一次「接受」要写影子仓库、项目状态、`decisions.md`，可能还要提交到用户仓库，中途崩溃会让它们互相矛盾。先记意图再执行，恢复时只需要看项目状态文件这一处 | 「最后写实例」：崩溃后要反向推断哪些副作用做过，每类副作用各写一套对账；两阶段提交：本地单进程不需要 |
| A12 | 「正文未变」与「驳回轮」分开判断：回应文件不算目标文件；正文未变但有新的回应文件时，进行一次驳回轮评审，驳回轮里评审仍给 `revise` 按需要人处理 | 需求同时要求「产物未变就叫人」和「驳回交下一轮评审裁决」。把回应文件算进目标文件，前一条永远不触发；不算，全部驳回时会跳过评审直接叫人。分开判断能同时满足两条，而且仍然有界 | 只看目标文件：全部驳回时绕过评审；只要有回应就再评审：未修改的稿子可以反复送审，直到轮数上限 |
| A13 | 每个项目室有一个「主流程」群聊，随项目室创建，项目室存在期间不可删除。它是所有检查点调用的宿主群聊，成员是全体席位所用 Agent 种类的并集，席位变更时同步 | `invokeAgent`、会话状态、Run Ledger 都以群聊为单位。宿主群聊被删，检查点的会话和运行记录就失去归属 | 每个席位一个合成群聊：污染侧边栏与消息存储；允许删除主流程群聊、调用时临时建一个：会话与运行记录断链 |
| A14 | **受管理的可写进程**：Meldwork 启动的每一个可写调用（项目室的检查点调用、项目内群聊、普通群聊）都在一个受管理的进程容器里运行，并登记在应用级的进程登记表中。三层保护：①启动握手，身份落盘之前 Agent 不能开始工作；②监护，主进程死亡时整个容器随之结束；③恢复屏障复核，重启后确认容器已空，确认不了的作用域在调度器里保持占用。「结束」指整个容器已空，不是根进程退出 | 现有调用链以独立进程组启动 Agent（`cli-adapters.cjs:250`），主进程崩溃时 `before-quit` 不执行，Agent 及其启动的测试、构建进程会继续写工作目录；`recoverInterrupted`（`run-ledger.cjs:568`）只改运行状态，不处理操作系统进程；Windows 的 `terminateWindowsProcessTree` 在直接子进程退出后直接返回（`cli-process-support.cjs:47`），证明不了后代已退出。租约协议（M2 5.4）的正确性依赖「持有者结束」这一事实，必须有可靠的确认 | 只登记根进程 id：漏掉后代进程，且启动与登记之间有窗口；只在项目室调用上做：项目内群聊的残留进程同样写同一个工作目录；超时后视为结束：超时只说明不再等待 |

## 3. 模块

### M1 项目室存储

管什么：项目实体、席位、playbook 实例、检查点进度、产物版本索引、决策与插话队列。（R16、R19、R23）

- 工作区文件新增 `projects: [{ id, name, workdir, createdAt, updatedAt }]`；群聊新增可选的 `projectId`。需要修改的白名单：`local-workspace-state.cjs:224-244` 加载路径、`local-workspace-message-records.cjs` 的 `emptyState` 与 `normalizeLoadedGroup`、`createGroup`、`workspaceSnapshot`（`local-workspace-state.cjs:428-456`）、renderer 的 `desktop-snapshot.js:367-376`。版本号升到 4，加载时接受 1–4。
- 引擎状态存 `meldwork-private/projects/<projectId>.json`，按 `human-gate-store.cjs` 的模式实现：单文件、经 `atomicWritePrivateFile` 原子写入、`0600`、有大小上限。项目关卡（A6）和待执行的副作用（A11）都在这个文件里，它是项目室唯一的权威状态。
- 同一项目的所有状态写入经一个按项目的异步队列串行执行：并行运行的检查点各自产生转移，但转移与落盘一次一个，不会互相覆盖。
- 产物快照存进 M4 的影子 git 仓库，引擎状态只保存提交号。
- 一个工作目录只对应一个项目室：创建时按真实路径（realpath）判重（R23）。
- 创建项目室时同时创建主流程群聊（A13），在工作区文件里标记 `projectRole: 'main'`。删除群聊的入口对它不可用，只能随项目室一起删除。
- 删除项目室：删除引擎状态、影子 git 仓库、轨迹文件、主流程群聊，以及 `sessions` 中以 `project:<projectId>:` 开头的会话键（现有的 `clearSessionState` 只按群聊前缀清理，覆盖不到这些键）。其他项目内群聊变为普通群聊或一并删除（由用户选择）；不删除工作目录里的文件。
- 默认 playbook 以数据形式内置：需求文档里的九个检查点、默认软硬关卡（需求、架构、实施计划、每个里程碑、最终评审为硬关卡）、评审轮数上限 3、续跑上限。每个默认角色带一份侧写，不是空的。

主要记录（字段在模块文档里定）：

| 记录 | 要点 |
| --- | --- |
| Project | id、名称、工作目录、文档根目录（默认 `meldwork/`）、席位列表、playbook 实例、主流程群聊 id、状态文件模式版本 |
| Seat | id、角色名、职责、Agent 种类、侧写、能力集合（读 / 写草稿区 / 写工作目录 / 运行命令）、参与的检查点。侧写与席位一起保存，带版本，可回退（R16、R29）。更换 Agent 种类不改侧写。同一种 Agent 的两个席位各有一份侧写 |
| Playbook | id、版本、检查点定义列表；可保存为模板（R17、R29）。默认侧写改写自 BMAD-METHOD 的角色人设，平台立场提示词和文档模板改写自 BMAD-METHOD 与 Spec Kit（均为 MIT；不使用 BMAD 商标）。立场提示词只管流程，侧写原样叠加上去 |
| CheckpointDef | key、类型（访谈 / 调研 / 文档 / 就绪检查 / 里程碑 / 最终评审 / 复盘）、目标文件、主笔席位、评审席位、并行草稿席位、关卡软硬、评审轮数上限、续跑次数上限、是否产出清单、依赖的上游检查点 |
| CheckpointInstance | 状态、候选提交、轮次列表（每轮的候选提交、是否驳回轮、各评审结论与评审文件）、进行中的调用（副作用 id、角色、轮次、会话代数）、续跑次数、主笔会话键与代数、当前关卡、待执行副作用、已接受版本、读取过的上游版本、过期标记。这是唯一的权威记录，跨应用版本按模式版本迁移 |
| Gate | 关卡 id（由实例 id 与关卡序号确定性得出）、修订号（关卡内容刷新时加 1）、唯一的原因（硬关卡通过 / 需要人 / 问题 / 产物未变 / 轮数上限 / 续跑上限 / 失败 / 漂移 / 文档新版本 / 恢复 / 清单无效 等，完整列表见 M2 模块文档）、绑定的候选提交、首屏内容、人的走向与意见、打回目标。存在 `CheckpointInstance.gate` 里，决定后移入决策 |
| Effect | id（由实例 id、转移序号、序号确定性得出）、类型、参数、状态（待执行 / 已开始 / 完成 / 失败）、结果 |
| ArtifactVersion | 接受提交的提交号（`commit`，包含平台管理的记录文件）、对应的候选提交（`candidateCommit`，经实施中调整或漂移确认形成的版本没有）、涉及的文件、接受时间、来源（关卡 / 软关卡 / 实施中调整 / 漂移确认）、对应决策 |
| DriftItem | 项目级「未解决漂移」：修订号、文件、归属的已接受检查点与已接受内容、观察快照（发现差异时为工作目录做的影子仓库快照）、发现时间、来源（接受送审版本 / 漂移检查）、状态。它是状态而不是副作用，与产生它的转移同一次落盘；一落盘就进入「待我决定」，解决前阻止读取过归属检查点的下游被接受（M2 模块文档第 8 节） |
| Decision | 决定、理由、谁定的、引用的评审文件；同时追加到 `decisions.md` |
| Interjection | 内容、目标检查点、状态（排队 / 已交付） |

### M2 检查点引擎

管什么：按 playbook 推进检查点，决定下一步谁做什么、何时叫人。（R1–R5、R12、R15、R19、R20）

- 由四部分组成（决定 A10、A11）：
  - `checkpoint-transitions.cjs`：纯函数 `transition(instance, event, config) → { instance, effects }`。不做 I/O，不读时钟（时间由事件携带），不调用 Agent。完整的「状态 × 事件」表见 `docs/modules/m2-checkpoint-engine.md`，单元测试按表穷举，表外的组合一律返回「事件被忽略」并记录。
  - `project-progress.cjs`：项目级进度，同样是纯函数。根据实例与依赖决定哪些实例可以开始；清单确认后新增实例；打回时计算影响范围。
  - `effect-runner.cjs`：按类型执行副作用（调用 M3、做 M4 快照与提交、追加记录文件、提交用户仓库、发通知），每类都按副作用 ID 幂等（见下）。
  - `checkpoint-engine.cjs`：把事件送进转移函数，经 M1 的项目队列落盘，再交给副作用执行器，把执行结果作为新事件送回。
- 一次转移的顺序固定为：计算 → 把新实例连同待执行副作用原子写入项目状态文件 → 逐个执行副作用 → 副作用的结果作为事件进入下一次转移，这次转移把该副作用标记为已消费，并与新的副作用一起原子落盘。副作用执行器不单独写「完成」，所以不存在「已完成但结果没有生效」的窗口；崩溃后，未消费的副作用重放一遍，再消费同样的结果。唯一单独落盘的是调用和用户仓库提交的「已开始」标记（M2 模块文档 4.3、第 10 节）。
- 调用结果的隔离：每个调用结果都带副作用 id、轮次和会话代数，只有仍登记在实例「进行中调用」里的结果才会被处理；被取消的旧调用晚到的结果一律丢弃。写入按作用域划分（主笔作用域、每个草稿席位的作用域、里程碑的整个工作目录）：同一作用域同一时刻最多一个可写调用，并行草稿分属不同作用域；主笔开始前本实例的草稿调用必须全部结束；要在同一作用域发起新的可写调用时，先等已取消的旧调用结束（M2 模块文档 4.2、5.2）。
- 执行纪元：上游重开、打回或重新打开时，实例的纪元加 1；执行器启动每个副作用前比较纪元，过期的待执行副作用（例如已排入但尚未启动的主笔调用）不执行，重启重放时同样比较。已经开始的接受事务照常完成，再标为过期（M2 模块文档 5.3）。
- 副作用失败：必要副作用（快照、接受提交、写评审文件、追加决策等）自动重试 3 次，仍失败则暂停这个实例后续的必要、调用和外部副作用，在项目室顶部显示错误与「重试」；它不是关卡原因，不改变状态。只有持有者被放弃时产生的清理（取消调用、撤回租约、删除快照引用）越过暂停照常执行；正常流程中的租约释放是链上的普通一步，前面的步骤暂停时它也等待，租约继续持有，人重试时仍受保护。暂停的那个副作用因纪元过期而作废时，暂停一并解除。用户仓库提交失败不撤销项目内部的接受；通知等尽力而为的副作用失败只记日志（M2 模块文档 9.2）。
- 各类副作用的幂等方式：

| 副作用 | 幂等方式 | 重启时 |
| --- | --- | --- |
| 影子仓库快照与接受提交 | 结果写到影子仓库内的引用 `refs/meldwork/effects/<副作用 id>`，已存在就直接取它的提交号 | 重放 |
| 追加 `decisions.md`、补 `changes.md` 的 `to=` | 每条记录带隐藏标记 `<!-- meldwork:<副作用 id> -->`，已存在就跳过 | 重放 |
| Agent 调用 | 运行 id 由副作用 id 确定性得出；执行前标记「已开始」 | 只读调用重新发起；可写调用不重放，转为恢复关卡（R20） |
| 提交到用户仓库 | 至多一次：执行前标记「已开始」；提交说明带尾注 `Meldwork-Decision: <决策 id>` | 标记为已开始而未完成时不重试；检查用户仓库 `HEAD` 是否带这个尾注，有则补记完成，无则在界面上提示「提交状态未知」 |
| 系统通知 | 尽力而为 | 不重放 |

- 同一项目室同一时刻可以有多个检查点在运行（并行模块文档），但每个检查点内部严格串行。

检查点状态（概览，完整的表在 M2 模块文档）：

```
pending → checking（漂移检查）→ drafting（并行草稿，可选）→ leading
leading   ─ ready → submitted
          ─ question → gate（问题）─ 回答 → leading（同一会话）
          ─ continue → leading（同一会话，续跑次数 +1，到上限 → gate）
          ─ 失败 → gate（失败：重试 / 换人接替）
submitted ─ 首轮，或正文有变化 → reviewing
          ─ 正文未变 + 新回应 → reviewing（驳回轮）
          ─ 正文未变 + 无新回应 → gate（产物未变）
reviewing ─ 全部 pass + 软关卡 → accepting → accepted
          ─ 全部 pass + 硬关卡 → gate
          ─ revise（普通轮，未到上限）→ leading
          ─ needs-human / 驳回轮里的 revise / 到达上限 → gate
gate      ─ 接受 → accepting → accepted
          ─ 继续改 → leading
          ─ 打回（指定上游）→ 该上游重新开始，依赖它的检查点标为 stale
stale     ─ 上游重新接受 → checking（主笔用新会话）
```

事件来源：主笔结尾标记、评审结尾标记、Agent 调用失败、人的关卡选择、人的插话、已接受的需求或架构文档出现新版本、工作目录与已接受版本不一致（R11）。

其他规则：

- 评审轮次：每个评审席位一次独立调用。多位评审时，任一 `needs-human` 即进入关卡，同一轮里还在运行的评审调用被停止，晚到的结论丢弃；全部 `pass` 才算通过；其余情况按 `revise`。
- 送审快照：主笔每次交回 `ready`，引擎都在影子仓库做一次快照，提交号记进这一轮。`accepting` 是接受的副作用正在执行的中间状态，副作用全部完成后才进入 `accepted`。
- 正文未变与驳回轮（决定 A12）：
  - 正文指检查点的目标文件，不含 `meldwork/reviews/` 下的评审和回应文件。主笔交回 `ready` 后，对上一轮的送审快照做 `git diff --quiet -- <目标文件>`。
  - 正文有变化 → 普通评审轮。
  - 正文未变，且主笔写了这一轮的回应文件 `r<n>-response.md` → 驳回轮：评审者被告知正文未改、主笔驳回了意见，只能接受驳回给 `pass`，或坚持并给 `needs-human`。驳回轮里给出 `revise` 时，平台按 `needs-human` 处理（需求「坚持就交人裁决，不再来回争」）。
  - 正文未变，也没有新的回应文件 → 关卡（产物未变，R5）。
  - 驳回轮计入评审轮数上限。部分采纳、部分驳回时正文有变化，按普通轮处理，评审者照常读回应文件。
- 检查点清单（R4）：主笔把清单写成 `meldwork/checklists/<检查点>.json`；引擎按模式校验，校验失败按需要人处理；人在硬关卡上接受后生成后续检查点实例。
- 打回与重新打开（R15）：从关卡上选择一个上游检查点，或者在已接受的检查点上直接选择「重新打开」；引擎计算依赖于它的检查点（已接受的和进行中的都算），先在关卡上展示影响预览，确认后标为过期，进行中的调用被取消。过期检查点在上游重新接受后依次重新开始（先做漂移检查，主笔用新会话），主笔的输入包括上游的变化和决策记录。
- 实施中调整文档（R12）：每次主笔或其他群聊的调用结束后，M4 检测已接受文档是否变化。变化即形成新版本。
  - `changes.md` 的每条记录有一行机器可读的头部。主笔写文件时只写路径和上一份已接受提交，例如 `- [path=docs/requirements.md from=<上一份已接受提交>]`，说明文字写在下面。上一份提交号由平台放进提示词。M4 形成新版本时把 `to=<新提交>` 补进这一行。平台只核对这个路径有一条新的头部。
  - 需求文档或功能架构发生变化：无论记录是否齐全，立即开关卡；记录缺失时在关卡上标出。这个关卡挂在文档所属的已接受检查点上（例如需求检查点），不打断造成改动的那个检查点；但后者在关卡决定之前不能被接受，自动和人工都不行（M2 模块文档 6.1、第 8 节）。
  - 其他文档发生变化：列入下一个关卡的摘要；记录缺失时一并标出，不单独开关卡。
- 插话（R17）：主笔一轮进行中时排队，下次调用主笔时放进提示词；人选择「停止并交付」时，用现有的停止机制结束当前一轮后立即调用。接受检查点之前（包括软关卡的自动接受），引擎先检查插话队列：有未交付的插话，则作废这一轮的 `pass`，把插话交给主笔，回到 `leading`。
- 重启（R20）：引擎状态持久化。每个项目先过恢复屏障：迁移状态文件、处理中断的调用、作废过期副作用、按状态重建全部写入租约并落盘；屏障通过前不执行任何副作用，调度器不把这个项目的租约键批给其他请求。之后未结束的只读调用重新发起；可写入的调用一律转为关卡，由人决定是否续跑，与现有 Run Ledger 规则一致（M2 模块文档第 10 节）。

### M3 席位调用适配

管什么：把「席位 + 检查点 + 输入」变成一次 `invokeAgent` 调用，并把结果变成引擎事件。（R2、R8、R10、R16、R20）

- 提示词由四层拼成：平台立场（评审立场、结尾标记约定）+ 席位侧写 + 检查点输入（目标文件、已接受上游版本、上一轮评审与回应文件、排队的插话、变更通知）+ 语言约定。侧写原样放入，平台不解析。
- 新增调用策略 `sessionPolicy: 'project-room'`。现有路径都不满足项目室：`isolated` / `frozen` 收下固定提示词，但强制只读（`local-workspace-agent-invocation.cjs:287`）；`v4: true` 可写，但会在提示词后附加 `RESPONSE_SCOPE_INSTRUCTION` 与工作偏好（`invocation-prompt.cjs`）。新策略的规则：
  - 宿主群聊是主流程群聊（A13）。
  - 提示词原样发送，不附加任何后缀。
  - 权限按席位能力决定，可以写入。现有路径从群聊的 `allowWrite` 取权限（`local-workspace-agent-invocation.cjs:284`、`:392`、`:398`）；`project-room` 策略改用调用上下文给出的模式，不读主流程群聊的 `allowWrite`。
  - 使用调用者给出的会话键（见下）。
  - 与现有路径一样必须带合法的 `contextPackId`（`:98-115`，缺失抛 `LOCAL_RUN_ISOLATED_CONTEXT_INVALID`）。每次调用前，M3 用现有的 Context Pack 存储捕获这一次的输入（提示词、上游版本的提交号），这也是每次调用的可追溯记录。
- 结尾标记：新模块 `signal-markers.cjs`，语法与现有回执一致，例如 `[[MELDWORK_CHECKPOINT:{"signal":"ready"}]]`、`[[MELDWORK_REVIEW:{"verdict":"pass"}]]`。复用 `answer-marker-filter.cjs` 在流式输出时隐藏。缺失或无法解析 → 需要人。
- 会话（决定 A3）：
  - 主笔：键为 `project:<projectId>:cp:<checkpointId>:seat:<seatId>:<kind>:g<代数>`，与现有键一样存在工作区的 `sessions` 里。同一检查点内的 `revise`、`continue` 和驳回轮恢复这个会话；新检查点用新键，也就是新会话；同一检查点过期后重开、或换人接替时代数加 1，同样是新会话。这些键不以群聊 id 开头，删除项目室时按 `project:<projectId>:` 前缀清理（M1）。
  - 评审者：每轮一个新会话，避免被上一轮的立场锚定。`project-room` 策略下，评审调用不把会话号写入 `sessions`，要在 `onSessionRef` 和结束时的 `session.complete` 两处都跳过。现有的跳过条件只覆盖代码审查类 Agent 和 `isolated`（`local-workspace-agent-invocation.cjs:385`、`:964`、`:1371`）。Claude、Codex 做评审者不会走到那里。
  - 需要修改的位置：`resolveSessionState`（`local-workspace-context.cjs:437`）目前总是用群聊级的键，要让项目室调用使用传入的键；`sessionKey()` 的超长哈希回退（`local-workspace-context.cjs:357-371`）只包含群聊、任务和 Agent 种类，要把项目、检查点和席位也纳入哈希，否则两个席位会撞到同一个键。`canonicalConversationSessionKey`（`local-workspace.cjs:2701`）只归并 `group:task:<id>:kind` 形式的键，不影响项目室的键。
- 接入通道（决定 A9）：

| Agent | 主通道 | 来源 | 现状 |
| --- | --- | --- | --- |
| Claude | print / exec | 现有 `claude` CLI | ACP 适配器 `@agentclientprotocol/claude-agent-acp`（Apache-2.0）待实测是否沿用本机登录；通过前不切换 |
| Codex | print / exec | 现有 `codex` CLI | ACP 适配器 `@agentclientprotocol/codex-acp`（Apache-2.0）待实测；通过前不切换 |
| Gemini | ACP | 原生 `gemini --acp` | 现为 print；改为原生 ACP |
| Qwen | ACP | 原生 `qwen --acp` | 现为 print；改为原生 ACP |
| Pi | ACP | 社区适配器 `pi-acp`（版本 0.0.x，较早期） | 现为 print；实测后再切换，不稳定则保留 print |
| DeepSeek、Hermes、Kimi、MiMo、OpenCode | ACP | 已在用 | 不变 |
| OpenClaw | ACP（每轮起停） | 已在用 | 不变 |
| WorkBuddy、ZCode 等 | print / exec | 无 ACP | 保留现有适配作为回退 |

  - 适配器是外部 npm 包，由安装器按固定包名安装，与现有的安装器策略一致；版本固定，升级经过测试。
  - 每种 Agent 记录能力：完整轨迹、`read-exec`、一轮中取消、用量。席位配置界面按能力提示，例如某个回退通道的 Agent 无法提供完整工具输出。
- 能力到权限的映射：现在只有 `read-only` 与 `workspace-write` 两种模式（`agent-runtime-contract.cjs:31`）。新增第三种模式 `read-exec`（能运行命令、不改文件），需要修改运行时约定和调度器的模式校验（`run-scheduler.cjs:143`）。
  - ACP 通道：在自动审批策略（`agent-permission-policy.cjs`）中实现：批准读取与执行类工具，拒绝编辑与写入类工具。一处实现，所有 ACP Agent 生效。
  - 回退通道：逐个 CLI 设置参数。例如 Claude 的 print 模式可以用 `--disallowedTools Edit Write` 加 `--allowedTools` 放行读取与命令（注意不能在禁止列表里写任何 Bash 规则，否则整个 Bash 被移除）。
  - 不能表达的组合，在席位配置界面提示，不静默降级或放宽（R16）。
- 「写草稿区」能力在 CLI 层就是 `workspace-write`，限制由 M6 的轮后检测保证。
- 受管理的可写进程（决定 A14）。这是跨模块契约，平台实现在 M3 模块文档中分别给出 POSIX 与 Windows 的方案，并逐项实测：
  - **登记表**：应用私有区的 `meldwork-private/process-registry.json`（原子写入、`0600`），每条记录包括调用 id、所属群聊与项目、工作目录、租约作用域、容器标识（POSIX 为进程组 id 与组长启动时间；Windows 为作业对象的标识）、状态（启动中 / 运行中 / 结束中 / 已结束）。覆盖 Meldwork 启动的所有可写调用，不只是项目室。
  - **启动握手**：先写「启动中」记录，再启动容器；容器里最先运行的是一道门，它在收到主进程的「放行」信号之前不启动 Agent。主进程拿到容器标识并落盘为「运行中」之后才放行。主进程在放行之前死亡，门的信号通道随之关闭，门直接退出，Agent 从未开始。所以任何能写文件的 Agent 进程，它的容器标识必定已经落盘。只有「启动中」而没有容器标识的记录，表示 Agent 从未开始，可以直接结束。
  - **容器与结束的确认**：Agent 及其启动的所有子进程（测试、构建、脚本）都在同一个容器里。「结束」以容器已空为准，而不是根进程退出：POSIX 上为进程组中已没有任何进程；Windows 上为作业对象中已没有任何进程。正常结束时，根进程退出后仍留在容器里的进程由平台结束，确认容器已空后才释放租约。
  - **监护**：主进程死亡时，容器里的进程随之结束。POSIX 上由门之后留下的监护进程负责：它感知到与主进程的信号通道关闭，就结束整个进程组。Windows 上使用设置了「关闭即结束」的作业对象，由随应用分发的小型辅助程序持有，辅助程序在主进程死亡时退出。断电等情况下全部进程本来就不存在。
  - **恢复屏障复核**：应用启动时，先处理进程登记表，再允许任何可写调用。对每条未结束的记录确认容器已空，不空就结束容器并再次确认；确认不了的，在调度器里登记为「残留占用」，直到人在界面上确认已结束或重试成功。其他不冲突的调用照常恢复。
  - **残留占用按真实路径识别冲突**：残留进程写的是磁盘上的目录，而现有普通群聊的租约键按群聊 id 生成（`local-workspace-agent-invocation.cjs:280`），两个群聊即使用同一个目录，键也不同。所以残留占用不用原来的租约键表示，而是记录真实路径：项目室调用为它租约作用域对应的文件或目录，项目内群聊与普通群聊为它的工作目录。**所有**新的可写调用（包括平时互不协调的普通群聊）开始前，都检查自己的写入路径与每个残留占用是否相同或互相包含；冲突就等待。路径的规范化（真实路径、大小写、符号链接）、包含关系的判断，以及与 `project:<id>:…` 键的对应，在 M4/M6 模块文档中定义。
  - **同一持有者只恢复一次**：项目室调用确认不了已结束时，它在项目状态文件里的「已获批」租约改为「待释放」并与残留占用关联，由残留占用代表它继续阻挡；重建租约时跳过它，不会与自己冲突（M2 模块文档第 10 节）。
  - **已知限制**：POSIX 上，主动脱离进程组的进程（例如以 `setsid` 启动的守护进程）不在容器内，平台无法跟踪。写入 Known Risks。Windows 的作业对象方案在 M3 实测通过之前，Windows 上的这一保证标为未实现，并在界面上说明，不静默降级。
- 看门狗：调用上下文新增 `watchdog` 选项（读取位置 `local-workspace-agent-invocation.cjs:636`）。项目室的主笔调用使用「提醒不中止」策略：无活动超时只发提醒事件和系统通知，由人停止或继续；`cli-adapters.cjs:396-399` 的 2 小时硬上限也改为可按调用覆盖（R20）。
- 评审文件：评审者保持只读；它这一轮的最终回答由平台写入 `meldwork/reviews/<检查点>/r<轮次>-<席位>.md`（R9）。主笔的回应由主笔自己写入 `r<轮次>-response.md`。回应文件在主笔的写入租约内，但不算目标文件，不参与「正文未变」的判断（A12）。主笔的提示词写明：全部驳回时也要写回应文件，否则这一轮按产物未变进入关卡。

### M4 产物与版本

管什么：快照、哈希、diff、漂移检查、过期传播所需的依赖、`decisions.md` 与 `changes.md`。（R10–R15、R25）

- 影子 git 仓库（决定 A4，参考 Cline 的 checkpoints 实现）：
  - 每个项目室一个仓库，放在 `meldwork-private/projects/<projectId>/shadow.git`，设置 `core.worktree` 为项目工作目录。用户自己的 `.git` 不受影响。
  - 候选提交：主笔每次交回 `ready` 时的送审快照就是这一轮的候选提交。评审的提示词写明它的提交号，关卡和接受都绑定它。
  - 评审读到的就是候选内容：检查点从进入 `leading` 起持有写入租约，经过送审和评审一直不释放，直到进入关卡、接受或过期（M6）。所以从送审快照到评审结束，项目室里没有其他写入者能改动目标文件，评审者在工作目录里读到的就是候选提交的内容。评审者仍在真实的工作目录里工作，需要运行测试的评审可以使用已安装的依赖和构建产物；这是不把候选版本导出成只读副本的原因，因为导出的快照不含被忽略的文件（例如 `node_modules`）。评审提示词里的 diff 由影子仓库的两个固定提交计算。评审结束时再核对一次工作目录，用来发现应用外的改动。
  - 已接受版本：接受时在影子仓库提交，提交说明记录检查点与决策。提交树以候选提交为基础，再叠加平台管理的记录文件（这个检查点的评审文件、回应文件、`decisions.md`、`changes.md`），不读工作目录里的目标文件。文档类检查点的候选提交覆盖目标文件；里程碑的候选提交覆盖整个工作目录。因此送审之后工作目录又被改动（例如项目内另一个群聊改了文件），改动也不会以这一轮的评审结论进入已接受版本；评审结束时和人接受前都会核对工作目录是否仍等于候选提交，不一致时在关卡上说明，人可以「接受送审版本」或「以当前文件重新送审」。选前者时，工作目录里与候选不同的文件立即记为未解决漂移，不等下游开始时才发现（M2 模块文档 6.1、第 8 节）。
  - 串行化（决定 A4）：`shadow-git.cjs` 为每个项目维护一个先进先出的互斥队列，这个项目的所有 git 调用（快照、提交、diff、漂移检查）都排进去。影子仓库只有一份索引，放在影子仓库内，保留 git 的文件状态缓存。
  - 快照的做法：`add -A`（遵守排除规则）→ `write-tree` → `commit-tree`，结果写到影子仓库内的引用 `refs/meldwork/snap/<id>`，不移动任何分支。快照是某一时刻整个工作目录的状态；别的席位正在写入时拍下的是中间状态，这一点由 M6 的归属规则处理。
  - 轮后检测（M6 使用）：所有可写调用（文档检查点、草稿、里程碑、项目内群聊）都对整个工作目录做前后快照。只看 `meldwork/` 的话，文档主笔改了源码也发现不了，「写草稿区」能力就没有兑现。单次快照超过时长或体积上限时，跳过检测并在关卡上说明，不阻塞流程。上限在模块文档中定。
  - 引用的清理：送审快照和已接受提交一直保留；一次调用的前后快照在对应关卡决定后删除引用，由 git 的垃圾回收清理对象。前后快照的提交不写入 `ArtifactVersion`，已接受版本只认接受时记下的提交号。
  - 必须写死的不变量（保护用户的仓库，R25）：
    - 影子仓库的每一次 git 调用都显式带上 `--git-dir=<影子仓库>` 与 `--work-tree=<项目工作目录>`，由封装函数生成参数。写入用户自己的仓库走另一个入口，见下。其他代码不得直接调用 git。
    - 不执行任何钩子（`-c core.hooksPath=/dev/null`）；提交身份用 `-c user.name=… -c user.email=…` 传入，不读也不改用户的全局 git 配置。
    - 排除规则写在影子仓库的 `info/exclude`（默认 `.git`、`node_modules` 以及用户仓库中的 Git LFS 模式），同时读取工作目录的 `.gitignore`，但不修改它。
    - 以固定参数调用 `git` 可执行文件，不经过 shell。
    - 本机没有 `git` 时，创建项目室失败并说明原因。
- diff：影子仓库的 `git diff` 生成统一 diff，main 解析后交给 renderer；renderer 用 `@git-diff-view/vue`（MIT）展示。
- 用户自己仓库的提交（R25）使用用户自己的 `.git`，不带影子仓库的 `--git-dir`。只在人接受时勾选「同时提交到 git」，且工作目录本身是 git 仓库时出现。目标是只提交本次接受的内容，并保留用户原有的暂存状态：
  - 前置条件，在关卡上勾选前检查，执行时再检查一次：本次接受的每个路径在工作目录中的内容等于已接受版本；这些路径在用户索引中的条目等于 `HEAD`，也就是用户没有暂存过它们。任一条件不满足，勾选框不可用并说明原因（例如「`src/a.ts` 有你暂存的改动，请先处理」）。执行时才发现不满足（用户在勾选之后自己暂存了这些路径）时，直接跳过，不碰用户的索引。这两种情况下接受照常完成，只是不提交到用户仓库。
  - 执行：`git add -A -- <本次路径>`，然后 `git commit --only -m <说明> -- <本次路径>`。`--only` 只提交列出的路径，用户索引中其他已暂存的内容保持暂存、不被提交；由于前置条件保证这些路径原本没有暂存内容，也不会覆盖用户的部分暂存。不执行 `git add .`。
  - 这是用户自己的仓库，钩子和签名配置照常生效，与影子仓库「不执行钩子」的规则不同。提交失败（例如钩子拒绝）时，只恢复这个副作用自己暂存过、而且索引条目仍等于本次暂存内容的路径（恢复为 `HEAD`）；索引条目已经不同的路径说明用户在此期间动过，保持原样并在通知里列出。界面报告失败原因，不重试。执行 `git add` 前先落盘「已暂存」标记；重启后发现标记存在而提交没有完成时，不自动恢复索引，只通知人「提交状态未知」并列出这些路径的索引状态。
  - 提交说明带尾注 `Meldwork-Decision: <决策 id>`，至多执行一次（M2 副作用表）。
- 漂移检查（R11）：检查点开始前，对上游已接受提交做 `git diff --quiet -- <文件>`。工作目录里的文件有差异 → 关卡，人决定以哪一版为准。
- 记录文件：`decisions.md` 由平台追加（来源是关卡上的走向和自由文本）；`changes.md` 由修改文档的 Agent 写头部和说明，平台补上新提交号，并只核对头部。
- 依赖：每个检查点实例记录它读取过的上游版本，打回时据此计算影响范围。

### M5 关卡

管什么：项目室的所有等人时刻：硬关卡、问题、失败、漂移、需求或架构新版本、打回确认。（R5、R6、R15、R27、R28）

- 存储（决定 A6）：关卡是 `CheckpointInstance.gate`，随项目状态文件持久化。一个检查点同一时刻最多一个待决关卡，一个关卡只有一个原因，不合并。M2 模块文档第 6 节说明了为什么按转移表不会同时出现两个原因；实现中如果出现，引擎拒绝这次转移并保留原关卡。越界条目、上游待确认、候选被改动是关卡上的信号或接受的前置条件，不是关卡原因。关卡 id 由实例 id 与关卡序号确定性得出，重复提交同一个决定不会重复生效。Human Gate 代码不做修改；调用进行中由 Agent 发起的权限类关卡照旧走 Human Gate。
- 决定的提交：renderer 调用 `project:decideGate(projectId, gateId, { gateRevision, candidateCommit?, outcome, comment, upstreamCheckpointId?, impactHash?, commitToGit? })`。main 校验关卡仍处于待决、关卡修订号与候选提交都与当前一致（关卡在用户查看期间被刷新时拒绝，界面重新载入首屏并保留意见）、走向合法、打回目标确实是这个检查点的上游、影响范围哈希与重新计算的一致（不一致要求重新预览）；接受时还校验 M2 模块文档 6.1 的前置条件：读取过的上游没有待决的「文档新版本」关卡和未解决漂移（不提供强制接受），工作目录是否仍等于候选提交（不等时先返回差异让人确认）。重启后待决关卡原样保留，不存在被系统拒绝的情况。校验通过后作为事件送进 M2，转移函数再校验一次。
- 重新打开：已接受的检查点（包括最终评审）可以直接重新打开。renderer 先调用 `project:previewReopen` 看影响预览，再提交 `project:reopen(projectId, checkpointId, reason, impactHash)`，理由必填；之后与打回的级联相同。
- 未解决漂移：`project:resolveDrift(projectId, [{ itemId, revision }], choice)`，`choice` 为「以工作目录为准」或「恢复为已接受版本」。修订号不符即拒绝，要求重新查看。「以工作目录为准」接受的是条目的观察快照，不是工作目录此刻的内容；两种处理执行前都再核对一次工作目录是否仍等于观察快照，不等则刷新条目、要求重新查看。「恢复为已接受版本」要先经 M6 拿到这些文件的写入租约才写文件。归属检查点的原接受事务完成之前，条目照常显示并阻止下游接受，但不能处理；每个条目绑定它所偏离的已接受版本，归属检查点之后又形成新版本时，旧条目的处理被拒绝并重新比较。条目与待决关卡一起出现在「待我决定」里，项目全部完成后仍然保留。
- 人的意见是自由文本，不是一排固定按钮。走向只有三个：`continue`（继续改）、`accept`（接受）、`reject-upstream`（打回，并指定上游检查点；上游数量不受限）。写了意见又没有点接受时，走向是继续改。没有 `pass` 时点接受，就是接受现状，记入 `decisions.md`。「再给几轮」「换评审者」「裁决驳回」都落在这三种走向里，不另设按钮。接受时可以勾选「同时提交到 git」。意见长度上限沿用 Human Gate 附言的 32 KiB，并做同样的密钥脱敏。
- 首屏内容存在关卡字段里，由 main 组装；renderer 经 `project:*` 快照取得，不经过 `local-workspace-state.cjs` 的运行类关卡过滤。
- 首屏内容（R6）：评审者摘要（评审文件开头的几行）、是否有驳回、是否经过驳回轮、改动的文件和 diff 统计、轮次、用时、软关卡批量摘要，加上意见输入框和三种走向。漂移关卡额外让人选定以哪一版为准。有未处理的越界条目时，首屏列出越界文件，并注明是否能归属到这一位席位（M6）。
- 通知（R28）：扩展 `shell/main-run-notifications.cjs`，新增项目关卡通知，点击后打开对应项目室。

### M6 写入协调

管什么：同一文件同一时刻只有一位写入者，跨群聊生效。（R7、R23）

- 租约的持有者：检查点的写入租约由检查点实例持有，而不是由单次调用持有。主笔作用域从进入 `leading` 起持有，经过送审和评审，到进入关卡、接受或过期时释放；草稿作用域在草稿期间持有。项目内群聊的可写调用仍按调用持有。这保证评审期间没有项目室内的写入者改动目标文件（M4「评审读到的就是候选内容」），代价要如实说明：项目内群聊的可写调用申请的是整个工作目录键，而工作目录键与所有文件键互斥。所以主流程只要有一个检查点处在主笔与评审的循环中，项目内群聊的**所有**写入都要等待，不只是写同一批文件的那些；只读调用不受影响。等待在这个检查点的循环到达关卡时结束，关卡期间租约已释放，所以写入者不会等上几天。界面显示「等待写入权」以及是谁持有（M13）。这是用正确性换并发：评审读到的就是送审内容，这一保证比项目内群聊的写入并发更重要。
- 「项目维护」持有者：恢复漂移文件（M2 模块文档 8.2）由平台以「项目维护」的身份申请对应文件的写入作用域，与检查点和项目内群聊的作用域互斥，拿到后才写文件，写完立即释放。
- 租约的生命周期（M2 模块文档 5.4）：每次申请在项目状态文件里有记录，状态为等待中、已获批、待释放、已撤回或已释放；调度器只持有内存中的队列，项目状态文件是权威。唯一的顺序原则是**状态先落盘，再通知调度器**：撤回与释放都由转移函数改记录并落盘，副作用只负责通知。调度器契约：收到当前持有者的释放通知之前，不把冲突的作用域授予下一位；授予要经转移函数消费并落盘后才生效。由此，项目状态文件里的「已获批」与「待释放」记录互不重叠，重启重建不会冲突。等待中的申请被放弃时立即撤回，不等任何东西；迟到的获批立即释放。只有实际写入（可写调用、恢复文件）在进行时才进入「待释放」，要确认进程已退出或写入不会再发生才释放，超时不算结束，无法确认时继续持有并给出诊断。可写调用和恢复文件启动前确认租约仍是已获批，否则从申请重新开始。重启时只重建已获批的申请，等待中的申请在恢复屏障之后重新排队。崩溃时 `before-quit` 不会执行，以独立进程组启动的 Agent 可能存活并继续写入，所以屏障先按落盘的进程标识（进程组 id、进程 id、启动时间）确认残留进程已结束，再把待释放的记录改为已释放；无法确认的实例保持阻塞并给出诊断。「残留占用」（A14）是调度器里的第三种占用：由恢复屏障登记，按真实路径与所有可写申请比较冲突（不只是项目室的键），只有人在界面上确认或重试结束成功后才解除。调度器侧的实现在 M4/M6 模块文档。
- 租约键（决定 A5）：项目室内的可写调用不再使用按会话的键（`local-workspace-agent-invocation.cjs:278-282`），而是按目标：
  - 文档检查点：每个目标文件一个键，例如 `project:<id>:file:<相对路径>`；主笔这一轮的回应文件也申请一个文件键。
  - 草稿：每个席位自己的草稿目录一个键。
  - 里程碑和项目内群聊的可写调用：整个工作目录一个键 `project:<id>:workdir`，与所有文件键互斥。
- 需要给调度器（`run-scheduler.cjs`）增加原子地同时获取多个键的能力，以及「工作目录键与文件键互斥」的层级关系。现在的键只是不透明字符串（`:22-26`），单键可以直接使用。
- 防止死锁：一次调用（或一个检查点作用域）在开始前一次性申请它需要的全部键，持有期间不追加。持有文件键的调用不能再去申请工作目录键；工作目录键要等所有文件键释放后才能获得，持有工作目录键时，文件键等待。
- 轮后检测：可写调用开始前和结束后，M4 各对整个工作目录做一次快照（M4「快照的做法」）。两次快照之间改动了的文件，减去这次调用持有租约的文件，就是候选的越界文件。这是建议性租约的兜底，也是对「写草稿区」能力的实际保证。
- 归属规则：快照只能说明「这段时间里哪些文件变了」，说明不了「是谁改的」。并行写入时引擎按下面的规则判断，界面如实标注：
  - 候选文件如果在时间上重叠的另一次可写调用的租约里，归那次调用，不算这次越界。
  - 剩下的文件，如果这次调用的时间窗里没有别的可写调用，标为「这一轮期间出现的越界改动」；人也可能在应用外改了文件，所以措辞不写成「某席位写的」。
  - 如果时间窗里还有别的可写调用，标为「来源不确定」，并列出重叠的调用。同一份清单出现在所有重叠调用的关卡上，人处理一次即可。
  - 越界条目不打断流程，只阻止自动接受：有未处理的越界条目时，软关卡的通过转为硬关卡，条目列在首屏。人在任何一个关卡上处理一次，所有引用它的实例都视为已处理。
  - 已知限制：一次调用写进了另一次并行调用租约内的文件，无法被检测到。那份文件的评审者会读到它，主笔的提示词也写明不得越界。这条写入 `architecture.md` 的 Known Risks。
- 并行写入的范围：只有文档检查点（各自的目标文件）和草稿（各自的草稿目录）可以并行写入；里程碑和项目内群聊持有工作目录键，天然与其他写入互斥，因此这两类调用的越界改动不会和其他席位的写入混在一起（人在应用外的改动仍然可能混入）。

### M13 产品交互体验

管什么：产品层面的交互规格，即用户在每种处境下看到什么、先看到什么、用什么动作推进，以及怎样把注意力花在关卡上。M12 按它实现组件。（「真实需求」一节，R5、R6、R15、R17、R20、R22、R27、R28、R29）详细规格见 `docs/modules/m13-interaction-experience.md`。

- 体验规则：不在关卡上就不打扰；关卡的信号条和决定区始终可见，其余区域有条数预算，30 秒内能判断「直接通过还是细看」；首屏的风险信号由平台确定性给出，摘要由评审者写，不放主笔的自我陈述；每个结论都能一键追到评审文件、diff 或轨迹；「评审通过后人工要求修改」会被自动记下，供复盘使用，但不推断为评审漏检。
- 布局：右侧只有一个抽屉，分「文件」「轨迹」两个标签，不并排放两块面板（现有右侧已经是 `RunTracePanel`）；「文件」标签最上方是已接受文档及其版本状态。侧边栏顶部有跨项目室的「待我决定」，包括待决关卡和未解决漂移。
- 关卡首屏的顺序：标题行 → 结论与风险信号 → 评审者摘要 → 改动文件 → 软关卡批量摘要 → 决定区。决定区的主按钮是「接受」（没有全体通过时变为「接受现状」并要求确认，不绑定快捷键）；输入框非空时可以「发送意见，继续改」；「打回…」打开两步弹层：先选上游，再看影响预览并填写理由。
- 主流程群聊只有一个输入框，它总是绑定一个明确的操作目标：输入框上方显示「正在操作：检查点 X · 插话 / 关卡意见」。目标由用户点击进度项或待决关卡切换，草稿按目标保存，发送时带目标 id；后台状态变化不会把已写的文字改投其他目标。输入框旁有「去项目群聊讨论」的入口。全部完成后，进度条上的每个已接受检查点都有「重新打开」。
- 通知只在进入关卡、长时间无活动和重启恢复时发出；30 秒内的多个关卡合并成一条；通知文字不含产物内容。
- 状态和关卡原因有统一的中英用语表，图标不只靠颜色区分。
- 本地指标（决定用时、评审通过后人工要求修改、接受现状次数、打回与重新打开次数、最终评审才发现的问题）只在本机保存，不上报，用于复盘。

## 4. 主要流程

### 一个文档检查点

1. M2 检查前置条件：上游已接受、漂移检查通过（M4）。
2. 如果定义了并行草稿：M3 并行调用各草稿席位（每人一个草稿目录键），全部 `ready` 后进入主笔。
3. 检查点获取目标文件和回应文件的租约（已持有时跳过；由检查点持有，直到进入关卡、接受或过期才释放）；M4 做调用前快照；M3 调用主笔（检查点会话，宿主为主流程群聊）。
4. 主笔结束：M4 做调用后快照，M6 做越界判断（租约继续持有；越界条目记入项目级列表，阻止自动接受）。`ready` → M4 做送审快照，与上一轮送审快照比较目标文件：有变化或首轮 → 5；未变且有新回应文件 → 5（驳回轮）；未变且无新回应 → M5（产物未变）。`question` → M5，人的回答作为继续改的意见，回到 3；`continue` → 续跑次数加 1，未到上限回到 3，到上限进入 M5。
5. M3 调用各评审者（只读、新会话，不保存会话号）；平台写入评审文件。
6. M2 汇总结论。兑现任何 `pass` 之前先看插话队列：有未交付的插话，作废 `pass`，把插话交给主笔，回到 3。队列为空时：普通轮的 `revise`（未到上限）→ 回到 3（输入加上评审文件）；全体 `pass` 时先核对工作目录是否仍等于候选提交：软关卡且没有阻止自动接受的条件（越界条目、上游待确认、候选被改动等）→ 7；否则，或者是硬关卡 → M5；`needs-human`、驳回轮里的 `revise`、到达上限 → M5。
7. 接受（`accepting`）：人工接受先通过前置条件校验（上游没有待决的新版本关卡；工作目录不等于候选提交时由人确认）。M2 一次性把接受的副作用写进发件箱：以候选提交为基础的影子仓库提交、`ArtifactVersion`、追加 `decisions.md`，人若勾选，再提交到用户自己的仓库。全部完成后进入 `accepted`，M2 推进到下一个检查点，或者在清单确认后生成后续检查点。

### 实施中的文档调整

主笔在里程碑中修改了已接受的 `requirements.md` → 这一轮结束后，M4 对已接受提交做 `git diff` 发现该文件有变化 → 形成新版本并核对 `changes.md` 头部 → 因为是需求文档，M2 在需求检查点上立即开关卡，里程碑照常继续但不能自动接受 → 人接受（版本生效，其他席位下次调用时收到变更通知），或者打回到需求检查点。

### 项目内的群聊

用户在第二个群聊里讨论某个技术问题 → 调用沿用现有的群聊路径，额外注入「项目室已接受文档清单 + 自上次以来的变化」→ 该 Agent 若改了文档，按「实施中的文档调整」处理；可写调用使用 `project:<id>:workdir` 键，与主流程的写入互斥。

## 6. 信任边界与产品边界的变更

| 现有规则 | 变更 | 依据 |
| --- | --- | --- |
| `architecture.md` Trust Boundaries 1：renderer 不得任意读取文件 | renderer 可以读取项目工作目录内的文件，由 main 校验路径并限制大小 | R22；工作目录本来就是用户选定的、界面可见的路径 |
| Trust Boundaries 6：命令、原始输出、工具负载不进入 renderer | 进入 renderer，只做密钥脱敏 | R21，用户裁决 |
| `AGENTS.md`：不得向 renderer 暴露可执行文件路径 | 完整轨迹中的可执行文件路径原样显示；修改 `AGENTS.md` 的这一条，限定为「轨迹显示以外，renderer 不接收可执行文件路径，也不能据此启动进程」 | R21；用户裁决 2026-11-13 |
| `architecture.md` Reliability：写入租约按会话划分，会话之间互不等待 | 项目室内改为按文件和工作目录划分；项目外的会话保持原样 | R7、R23 |
| `architecture.md` Known Risks：共用文件夹的写入不协调 | 项目室内已协调；项目外仍不协调。新增一条：项目室内的租约是建议性的，并行写入时，一次调用写进另一次调用租约内的文件无法被检测到；其余越界改动能被发现，但并行时不一定能归属到某一位席位。应用外的程序在评审期间改动文件、又在评审结束前改回，评审结束时的核对发现不了 | R23、A5 |
| Local Data 表格 | 新增项目室状态文件、影子 git 仓库、轨迹文件 | M1、M4、M7 |
| `AGENTS.md`、`architecture.md`：现有群聊的可写调用 | 所有可写调用（包括项目外的普通群聊）改为在受管理的进程容器中运行：一轮结束后，Agent 留下的进程（例如它启动的开发服务器）由平台结束；残留占用按真实路径阻挡同目录的其他写入。这是对普通群聊现有行为的改变，在打开写入权限的地方提前说明（M13） | A14 |
| `architecture.md` Known Risks：新增 | 可写调用在受管理的进程容器中运行（A14）；POSIX 上主动脱离进程组的进程（例如 `setsid` 启动的守护进程）不在容器内，无法跟踪；Windows 的作业对象方案实测通过前，崩溃后的残留进程保证在 Windows 上未实现 | A14 |
| `architecture.md` Known Risks：新增 | 密钥脱敏只能替换已知的密钥值；Agent 读出的文件内容中的其他密钥（例如 `.env`）会原样显示在轨迹中。用户已接受 | R21 |
| `architecture.md` Known Risks：安装器使用可变的上游包 | 新增的 ACP 适配器包同样适用；固定版本 | A9 |

不变的边界：Agent 执行仍在 main；不引入服务器；不执行 Agent 写出的命令（验收命令由具备 `read-exec` 或写入能力的席位在自己的 CLI 沙箱中执行）；密钥只经系统安全存储；写入仍需显式开启（R26）。
