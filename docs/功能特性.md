# Meldwork 功能特性问答

供二次开发跟进。结论以当前源码为准，日期 2026-11-12。

Meldwork 不自己调用模型。它拉起本机已经登录的 Agent CLI，由那个 CLI 去调用自己的模型。界面负责发任务，并只展示过滤后的结果。

## 单聊

### 单聊的原理是什么？和本地终端比，限制在哪里？

一条单聊在数据里是 `conversationType: 'direct'` 的会话，里面只有一个 Agent。发出去的文字先写入本地会话，主进程再包成提示词交给 CLI。

已经有原生会话时，提示词主要是这一轮请求，外加权限和语言提醒。原生会话自己记着上文。会话是新建的，或上次的会话号失效被丢掉之后，才会把更早的记录打包进去，并标明这些内容只供参考、需要自行核对。见 `desktop/src/workspace/local-workspace-context.cjs` 的 `directPromptFor`。

CLI 的接法分两类：

- Codex、Claude、Qwen、Gemini、Pi、WorkBuddy、Zcode：每一轮新起进程，带上 `--resume` 或 `--session`，这一轮结束进程退出。
- Hermes、Kimi、MiMo、DeepSeek、OpenCode：走 ACP，主进程尽量留着同一个子进程。同时活着的这类进程最多 16 个。OpenClaw 不留进程，每轮拉起再拆掉，会话号另外保存。

它用的是各 CLI 的 `print` / `exec` / `acp` 模式，不是终端里的交互界面。因此这些终端能力不在应用里：

- 斜杠命令、TUI 菜单、CLI 自己的会话列表、中途改模型。
- 终端里逐条确认工具权限。这里默认在当前沙箱内自动放行。沙箱是只读，或只允许改工作目录，由会话的写入开关决定。新开的单聊默认允许写入。
- 原始标准输出、完整思维链、命令原文、可执行文件路径、原生会话号。界面只能看到过滤后的结论和有限的工具摘要。
- 图片不是每个 Agent 都能收。Codex、OpenCode 最多 4 张，Hermes 最多 1 张，其他 Agent 带图会直接失败。
- 只读时工具被收窄。例如 Pi 只留 `read`、`grep`、`find`、`ls`。WorkBuddy 的独立回复还有内部轮数上限，默认 8 轮。
- 一轮卡住会被看门狗停掉：无进展大约 10 分钟，工具执行大约 20 分钟。
- 同一个会话里，能写文件的 Agent 必须轮流来。

模型本身没有被换成另一个模型。被收掉的是 CLI 的交互壳，以及 Meldwork 在提示词、权限和输出上加的边界。

### 能否新开多个单聊？上下文隔离吗？session 是谁的？

可以。应用是一个 Electron 窗口，侧边栏里每一条单聊是一个独立会话。每条有自己的消息、工作目录、写入开关，以及自己的原生会话号。键是 `会话 id:Agent 种类`。两条单聊不共用模型上下文，也不会因为对方还在跑就互相等待。它们如果指向同一个文件夹，可以同时改文件。换工作目录会清掉这条会话的原生会话号。

会话有三层：

| 层 | 是什么 | 谁持有 |
| --- | --- | --- |
| 应用会话 | 侧边栏里的那条聊天，消息在 `meldwork-workspace.json` | Meldwork |
| 原生会话号 | CLI 返回的 session id，存在 `sessions["会话id:Agent"]` | 号在 Meldwork；对话记忆在该 CLI 自己的数据目录 |
| 进程 | 只对 ACP 那一类尽量留着子进程，上限 16 | 主进程内存里的一张表，退出应用就没了 |

这个会话号不是 PID。PID 只在 ACP 进程还活着时存在。进程被关掉之后，下一轮靠会话号再恢复。会话号无效时，主进程丢掉它，下一轮把历史重新塞进提示词。

群聊没有一个共享的模型会话。群由 Meldwork 维护：成员、发言顺序、打包后的共享上下文、谁这轮可以写文件。每个成员仍有自己的原生会话，键是 `群id:这个Agent`。一个 Agent 看不见另一个 Agent 进程里的私有状态，只能看到 Meldwork 写进提示词的共享记录。

## 群聊

### 群聊能选 Agent，但没有「Gemini 是 UX、Claude 是架构师」这种角色吗？

没有这种由用户保存的岗位。建群时选定的是 Agent 种类，外加一个群名称和一条群主题。主题是整群共享的一句话，不是每个人的职责说明。

运行中会出现另外几种「角色」，它们都是调度身份，不是专业人设：

- 交付负责人。顺序讨论里，默认是本轮选中名单的第一位。这位负责判断任务是否完成，也可以把负责人身份交给另一位仍在名单里的 Agent。见 `v4NaturalOwner`。
- 写入者。开了工作区写入时，同一时刻只有一位 Agent 可以改文件，其他人只读。
- 自动讨论里临时协商出来的执行者、整合者、复核者。这是某一轮协作图上的分工，存在这次运行的记录里，不会变成该 Agent 的固定人设。
- 界面上的主提案者、审查者、仲裁者等标签，来自这一轮的阶段，不是用户事先填的职称。

智能组队按能力、成本、延迟、工具类型选「最小可用团队」，也不读取「UX 专家 / 高级架构师」这种描述。

所以各司其职目前只能写进当次消息或群主题，靠模型自己理解。应用不会记住「Gemini 永远做 UX」，也不会在提示词里强制这位 Agent 只回答 UX 问题。

### 群聊目前有哪几种形式？为什么这样设计？缺点是什么？

侧边栏的「群聊」是一个会话容器。输入框上的回复模式决定这一轮怎么调度。成员在建群时选定，顺序讨论和自动讨论会用上全部已选成员；单次回答和并发回复可以再勾选其中几位。

| 界面 | 发给后端 | 这一轮怎么进行 |
| --- | --- | --- |
| 单次回答 | `manual`，只点了一位 | 只叫这一位，用它自己的原生会话接着说 |
| 并发回复 | `manual`，点了多位 | 每个人收到同一份冻结任务，按名单顺序各自回复，互不看到对方这一轮的答案 |
| 顺序讨论 | `auto`，风格默认 `sequential` | 按名单轮流发言。后一位能看到前一位已经写完的内容。默认最多约 6 轮，也可以改成不限轮数 |
| 自动讨论（Beta） | `auto` 且 `discussionStyle: agent-led` | 首轮各自独立交一版。之后由 Agent 在回复末尾用控制回执邀请下一位，或提出一个候选版本。全员明确认可同一版才结束 |

这样拆，是因为三种需求不一样：只要某一个 Agent 的答案、要同时比较几种看法、要让它们接话并交出同一份结果。调度放在 Meldwork，而不是放进某一个 CLI 的会话里，是因为每个 Agent 的进程和会话号都是自己的，谁也叫不动谁。应用负责排队、把别人的发言写进下一位的提示词，并在展示前拿掉控制回执。

缺点：

- 没有固定专业角色。分工要么靠这一轮的提示词，要么靠运行时临时选出来的负责人，第一位被选中的 Agent 并不一定是最合适的负责人。
- 并发回复不会互相修正，综合要用户自己做。
- 顺序讨论按名单顺序说话，慢，而且排在前面的人要等下一轮才能看到后面的意见。轮数用尽会停，不保证事情做完。
- 自动讨论依赖模型老实写出控制回执。回执错了会被丢掉或再问一次，讨论可能空转、重复转交，或在没有新内容时被停掉。Beta 也表示这条协议还在收。
- 同一群里能写文件的人必须轮流来。两个群如果指向同一个文件夹，仍然可能同时改同一批文件。
- 智能组队打开后，这次消息会忽略手动点选的 Agent。
