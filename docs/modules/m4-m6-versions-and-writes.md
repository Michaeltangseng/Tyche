## A. 写入协调（M6）

### A1. 现状

`desktop/src/runs/run-scheduler.cjs`：

| 事实 | 位置 | 对本文的影响 |
| --- | --- | --- |
| 每个请求只有一个不透明的 `workspaceKey`，每个键同一时刻最多一个 `workspace-write` 持有者 | `canGrant`、`activeWorkspaceWriters` | 要扩展为一次申请多个作用域、并有目录与文件的包含关系 |
| `drain()` 跳过暂时不能授予的请求，让后面的请求先行 | `drain` | 多作用域申请会被源源不断的小申请饿死，要加公平规则 |
| 租约只存在于一次 `withLease(operation)` 期间，`operation` 结束即释放；`suspend` 在等人时先释放、再重新排队 | `withLease` | 检查点要跨越多次调用持有租约（M2 5.2），需要不绑定单次操作的申请接口 |
| 进程结束失败时，等进程真正退出后再释放 | `withLease` 中 `LOCAL_AGENT_TERMINATION_FAILED` 分支 | 与 M2 5.4 的「待释放」一致，沿用这个思路 |
| 全局、任务、工作区三级并发上限 | `limits` | 保留，只作用于调用，不作用于检查点持有的作用域（A3.4） |

现有写入键由群聊 id 生成（`desktop/src/workspace/local-workspace-agent-invocation.cjs:280`），注释写明同一文件夹下的不同群聊有意互不协调。

### A2. 作用域的统一表示：路径声明

M2 和架构里出现过四种写入范围：检查点的文件键、工作目录键 `project:<id>:workdir`、草稿目录、残留占用的真实路径。本文把它们统一成**路径声明**（claim）：

```
claim = { root, path, mode }
  root：工作目录的真实路径（realpath），由声明的创建者在申请时解析
  path：相对 root 的规范化路径；空字符串表示整个 root
  mode：exclusive（独占）| shared-legacy（项目外普通群聊的兼容模式，见 A2.3）
```

| M2 / 架构中的说法 | 对应的声明 |
| --- | --- |
| 主笔作用域（目标文件 + 回应文件） | 每个文件一条 `exclusive` 声明 |
| 草稿作用域 | 草稿目录一条 `exclusive` 声明 |
| 里程碑作用域、`project:<id>:workdir` | `path = ''` 的 `exclusive` 声明 |
| 「项目维护」恢复漂移文件 | 每个文件一条 `exclusive` 声明 |
| 残留占用（A14） | 原调用的声明；原调用没有声明的（项目外普通群聊），用它工作目录的 `path = ''` |

#### A2.1 冲突规则

两条声明冲突，当且仅当：

1. 它们在同一个文件系统卷上，并且
2. 一条的路径（`root` + `path`，按段比较）是另一条的前缀或与之相同，并且
3. 至少一条是 `exclusive`。

`shared-legacy` 与 `shared-legacy` 之间不冲突（保留现有行为，见 A2.3）。残留占用视为 `exclusive`，与一切重叠的声明冲突。

#### A2.2 路径规范化

- `root` 取 `fs.realpathSync.native`。所有比较都在解析后的绝对路径上做。
- `path` 统一为 `/` 分隔，去掉 `.` 段；含 `..` 段、绝对路径、空字节的拒绝。
- Unicode 统一为 NFC，避免 macOS 文件名的组合字符造成同名不同串。
- **大小写**：按卷探测一次并缓存。在 `root` 下创建一个临时文件，用改变大小写后的名字 `stat`，能找到就是大小写不敏感的卷（macOS 默认的 APFS 即如此）；在不敏感的卷上，比较前先做大小写折叠。项目室创建时探测并记入项目记录；项目外的 `root` 在第一次申请时探测并缓存到进程结束。
- **符号链接**：`root` 和声明路径都按磁盘上的实际位置比较，而不是按字面。
  - 声明路径中已存在的部分用 `realpath` 解析，不存在的尾部（例如还没创建的目标文件）接在最近的已存在祖先解析结果之后。这样 `root/alias → root/docs` 时，`alias/spec.md` 与 `docs/spec.md` 解析为同一路径，判为冲突。
  - 解析结果必须仍在 `root` 的真实路径之内，否则拒绝这条声明：检查点的目标文件不能经符号链接指向工作目录之外。
  - 解析在申请时进行。获批之后才出现的符号链接（例如 Agent 在工作中新建了一个别名），调度器无法提前识别；由越界检测兜底：影子仓库把符号链接存为链接本身，经别名写入的改动显示为真实文件的改动，不在声明范围内就会被列为越界（A6）。
  - 硬链接（同一文件的两个名字）不在识别范围内，写入架构的 Known Risks。
  - Agent 经符号链接写到工作目录之外，不在本文保证之内（M8 的读取通道另有限制）。

#### A2.3 项目外普通群聊

- 工作目录与任何项目室的 `root` 不重叠的普通群聊：保持现有行为，以 `shared-legacy` 声明自己的工作目录，并继续用按群聊 id 生成的键保证同一群聊内的写入轮流进行。这样它们彼此不等待，但会被残留占用挡住（A14）。
- 工作目录与某个项目室的 `root` 重叠（相同、父目录或子目录）的普通群聊：以 `exclusive` 声明自己的工作目录，与项目室的写入互斥。否则评审期间它能改动送审文件，破坏 M2 5.2 的保证。这是对现有行为的改变，写入架构第 6 节（本文第 E 节）。

### A3. 调度器的新接口

保留 `acquire` / `withLease`（现有调用方继续可用），新增一组不绑定单次操作的接口。所有新接口按申请 id 幂等。

| 接口 | 作用 | 对应 M2 |
| --- | --- | --- |
| `request({ requestId, holder, claims, onGranted })` | 排队申请一组声明，**全有或全无**地授予。`onGranted(requestId)` 在授予时调用，由引擎转为 `LEASE_GRANTED` 事件。`holder` 为 `{ kind, projectId?, ownerId }`，`kind` 是 `checkpoint-scope`、`project-maintenance` 或 `invocation`（现有的 `acquire` / `withLease` 一律记为 `invocation`）；`snapshot()` 中带出这个字段，M2 的对账据此只处理前两类 | 5.4「申请」 |
| `release(requestId)` | 释放已授予的申请；之后立即尝试授予等待者 | 5.4「正常释放」 |
| `withdraw(requestId)` | 等待中的移出队列；已授予的等同 `release`；不存在则无操作 | 5.4「放弃（撤回）」 |
| `restoreGranted(requests)` | 恢复屏障中使用：不经队列直接恢复一批已授予的申请；任一重叠即整体拒绝并返回冲突清单 | 第 10 节第 6 步 |
| `registerResidual({ residualId, claims })`、`clearResidual(residualId)` | 登记与解除残留占用 | A14、第 10 节第 2 步 |
| `holdRoot(root)`、`openRoot(root)` | 某个 `root` 恢复期间暂停对它重叠声明的授予 | 第 10 节屏障 |
| `snapshot()` | 现有快照之外，加上声明、持有者、残留占用、被暂停的 `root`；用于界面显示「是谁在占用」 | M13「等待写入权」 |

#### A3.1 全有或全无

一个申请的所有声明在同一时刻都可授予时才授予，否则一个也不授予。持有部分作用域再等待其余作用域的情况不会出现，所以不会形成「各持一部分、互相等待」的死锁。这取代架构 M6 原来「工作目录键要等所有文件键释放」的分层描述：分层关系已经由 A2.1 的前缀规则表达。

#### A3.2 公平：冲突的申请按到达顺序

现有 `drain()` 允许后到的请求越过不能授予的请求。对多声明申请，这会让「整个工作目录」的申请被源源不断的单文件申请饿死。新规则：

- 一个等待中的申请，对与它冲突的**后到**申请构成阻挡：后到者即使此刻可授予，也要排在它之后。
- 与所有更早的等待者都不冲突的申请，可以越过它们（保留现有的并行度）。

例：项目内群聊申请整个工作目录，正在等主流程检查点释放主笔作用域；这期间另一个检查点申请某个文件，它与等待中的工作目录申请冲突，只能排在后面。主流程的主笔作用域在评审结束、进入关卡时释放（M2 5.2），项目内群聊随即拿到工作目录。

#### A3.3 授予与落盘

调度器在内存里授予后调用 `onGranted`。M2 5.4 契约第 3 条要求：引擎消费这个事件并把记录落盘为「已获批」之前，持有者不执行任何需要租约的步骤。所以调度器侧的「已授予」可能先于文件里的「已获批」。这不破坏不重叠性质：在落盘之前崩溃，调度器的内存状态随之消失，记录仍是「等待中」，重启后重新排队。

契约第 1 条（收到释放通知之前不授予冲突的下一位）由调度器的实现直接保证：作用域只在 `release` / `withdraw` 被调用时空出，而引擎只在记录落盘为「已释放」「已撤回」之后才调用它们（契约第 2 条，M2 的顺序原则）。

#### A3.4 并发上限

检查点实例持有的作用域可能跨越几个小时，其中大部分时间没有调用在运行（例如主笔与评审之间的快照）。所以作用域申请不计入全局、任务、工作区三级并发上限。每一次实际调用仍然经过现有的 `acquire`，以只读模式计数（作用域已由外层持有，调用本身不再声明路径），并发上限照常生效。

#### A3.5 等待的可见性

`snapshot()` 给出每个等待中申请的阻挡者：当前持有者、残留占用，或排在前面的冲突申请。M13 的「等待写入权」据此显示「是谁在占用」。调度器不设等待超时；等待是否过长由人判断，界面提供「取消」。

### A4. 租约生命周期：调度器侧

M2 5.4 的五个状态与调度器的对应：

| M2 记录状态（项目状态文件） | 调度器内存状态 | 进入方式 |
| --- | --- | --- |
| 等待中 | 在队列中，或尚未提交（崩溃后、屏障之前） | `request` |
| 已获批 | 已授予 | `onGranted` 被消费并落盘 |
| 待释放 | 已授予（继续阻挡） | 引擎决定释放，但实际写入还在进行 |
| 已撤回 | 不存在 | 落盘后调用 `withdraw` |
| 已释放 | 不存在 | 落盘后调用 `release` |

调度器自己不保存任何持久状态；重启时一切从项目状态文件和进程登记表重建（第 C 节）。

### A5. 残留占用

- 由进程登记表的恢复（A14，M3 实现）调用 `registerResidual` 登记，声明取自原调用（A2 表格最后一行）。
- 与一切重叠的声明冲突，包括 `shared-legacy`。
- 只能由人在界面上解除：「重试结束」成功后由 M3 调用 `clearResidual`；「我已手动结束」时，M3 再确认一次进程组已空，确认后才调用。
- 与它关联的 M2 记录（「待释放」）在解除时一并改为「已释放」并落盘，然后才调用 `clearResidual`，同样遵守「先落盘、再通知」。

### A6. 越界检测与归属

越界检测依赖影子仓库的快照（B3），规则见架构 M6；这里补充实现细节。

- 每个可能写入的调用（`workspace-write`，以及运行的命令可能写文件的 `read-exec`，M3 3.1）在开始前、结束后各做一次整个工作目录的快照（`snapshot` 副作用，B3）。开始前的快照在作用域获批之后、调用启动之前做；结束后的快照在容器已空（A14）之后做。所以两次快照之间，这次调用的所有写入都已发生。
- 候选越界文件 = `git diff --name-only -z <前> <后>` 中，不在这次调用声明范围内的文件。
- 归属用调度器的授予记录：引擎为项目内每次可写调用记下「作用域获批 → 容器已空」的时间窗与声明，存在项目状态文件里。候选文件落在另一个时间重叠的调用的声明里，就归那次调用；其余文件按架构 M6 的规则标为「这一轮期间出现的越界改动」或「来源不确定」。
- 任一次快照被跳过（B3.4 的上限），越界检测随之跳过，结果标为「已跳过」，按 M2 8.3 作为关卡上的信号。

## B. 影子仓库与版本（M4）

### B1. 仓库与 git 调用

**位置**：`meldwork-private/projects/<projectId>/shadow.git`，以 `git --git-dir=<shadow.git> --work-tree=<root> init` 创建，`core.bare=false`。

**名字的编码**：M2 的副作用 id 形如 `<实例 id>:<seq>:<序号>`，含有冒号，不是合法的 git 引用名（实测 `git update-ref` 返回 128）。所以引用名、临时文件名里出现的一切 id，都用 `h(id)` 表示：id 的 UTF-8 字节的 SHA-256，取小写十六进制全长 64 位。它只含 `[0-9a-f]`，在 git 引用、macOS、Linux、Windows 的文件名中都合法，且长度固定。原始 id 写在提交说明里，便于诊断。下文的 `<…>` 凡是出现在引用名或文件名中的，都指编码后的值。

**唯一入口**：`desktop/src/project-room/shadow-git.cjs`。其他代码不直接调用 git。每次调用由它生成参数，以 `execFile` 调用 git 可执行文件，不经过 shell：

```
git --git-dir=<shadow.git> --work-tree=<root>
    -c core.hooksPath=/dev/null      不执行钩子
    -c core.autocrlf=false           不改换行
    -c core.fileMode=true            记录可执行位
    -c core.symlinks=true            符号链接存为链接本身
    -c core.quotepath=false          路径原样输出
    -c core.fsmonitor=false          不调用外部监视程序
    -c gc.auto=0                     不自动回收，由 B5 控制
    -c user.name=Meldwork -c user.email=meldwork@localhost
    <子命令> ...
```

环境变量：清除 `GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE`、`GIT_OBJECT_DIRECTORY` 等一切 `GIT_*`，再设 `GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM=1`、`GIT_TERMINAL_PROMPT=0`，不读用户的全局与系统 git 配置。Windows 上 `/dev/null` 换成 `NUL`。

**原始字节**：影子仓库保存工作目录文件的原始字节，不做任何内容转换。`core.autocrlf=false` 不足以做到这一点：工作目录里的 `.gitattributes` 规则（例如 `*.txt text eol=lf`）仍会让 `git add` 把 CRLF 存成 LF，而之后的 `git diff` 用同样的规则比较，会报告「无差异」。实测确认了这个问题：工作目录是 CRLF、快照里是 LF，候选核对却通过。所以创建影子仓库时写入 `shadow.git/info/attributes`：

```
* -text -eol -filter -ident -working-tree-encoding
```

`info/attributes` 的优先级高于工作目录中的任何 `.gitattributes`，这一行对所有路径关闭换行转换、清理与还原过滤（包括 Git LFS）、`$Id$` 展开和编码转换。不关闭 `diff` 属性，文本文件仍按文本显示 diff。实测：加上这一行后，快照保存 CRLF 原样；工作目录由 CRLF 改为 LF、或者可执行位变化时，`git diff --quiet` 都报告有差异；文本 diff 照常输出。由此，候选核对、漂移检查、恢复文件、用户仓库提交的前置条件（B7）比较的都是同一份原始字节与文件模式。

**版本要求**：git ≥ 2.32（`GIT_CONFIG_GLOBAL` 从这个版本起可用）。创建项目室时检查，不满足则创建失败并说明原因。macOS 自带的 git（例如 2.39）满足。

**串行化**：每个项目一个先进先出的互斥队列，这个项目的所有影子仓库操作排进去，同一时刻只有一个 git 进程在操作这个仓库。

**索引**：影子仓库自己的一份 `shadow.git/index`，长期保留，让 git 的文件状态缓存生效。只有 B2 的接受提交使用临时索引，原因写在那里。

### B2. 排除规则

写在 `shadow.git/info/exclude`，分两段：

- 固定段：`.git`、`node_modules/`、`.DS_Store`。
- 自动段（以注释行标出，由平台维护）：不存内容的路径（B3.5）。注意：排除规则只对**未跟踪**的文件生效，已经在影子索引里的路径不受它约束（实测：已跟踪文件写入 exclude 后变大到 2 MB，`git add -A` 仍存入完整内容）。所以自动段只是辅助，真正保证不存内容的是 B3.5 的占位条目。

工作目录里的 `.gitignore` 由 git 照常读取，平台不修改它。

例外：**检查点的目标文件和回应文件只要存在，就要进入快照**，即使用户的 `.gitignore` 忽略了它们，否则送审快照会漏掉正在评审的文档。做法见 B3.1 第 2 步。

**嵌套仓库**：工作目录里含有其他 git 仓库（子模块或嵌入的仓库）时，git 只会记下一个指针，不跟踪其中的文件内容。创建项目室时扫描并列出这些目录，把它们写进排除规则的自动段；界面说明「这些目录的改动不会被快照、越界检测和漂移检查覆盖」。这条写入架构的 Known Risks（第 E 节）。

### B3. 快照

#### B3.1 做法

在项目互斥队列中：

1. 如果 `refs/meldwork/effects/<h(副作用 id)>` 已存在，直接返回它指向的提交（M2 9.1 的幂等方式）。
2. **确定本次的占位集合并改写排除规则**（B3.5「每次快照对占位路径的处理」）：需要占位的路径移出影子索引并写进排除规则；已删除、缩小或换了类型的旧占位路径从排除规则中删除。这样下一步的 `git add -A` 既不会存入超限内容，也不会把不再需要占位的路径误当作不存在。
3. `git add -A`。它记录工作目录中所有未被忽略的新增、修改与删除，包括此前被强制加入、现在已被删除的文件（它们已在影子仓库的索引里）。
   然后对本检查点的目标文件与回应文件中**当前存在**的那些（以 `lstat` 判断）执行 `git add -f -- <文件…>`，让被 `.gitignore` 忽略的目标文件也进入快照。对不存在的路径执行 `git add -f` 会失败（实测返回 128），所以不存在的文件不传给它：从未存在的文件在快照中就是「不存在」，主笔首次开工前目标文件还没创建、回应文件还没写，都属于这种正常情况。
4. 为第 2 步中归为「占位」的路径写入占位条目：`git hash-object -w --stdin` 写入占位内容，再 `git update-index --add --cacheinfo 100644,<对象>,<路径>`。已删除的路径不写，快照中即为不存在。
5. `git write-tree` → 树。
6. `git commit-tree <树> -m <原始副作用 id>` → 提交。快照之间不设父子关系，相同内容的对象由 git 自动复用。
7. `git update-ref refs/meldwork/effects/<h(副作用 id)> <提交>`。

快照总是覆盖整个工作目录（架构 A4、A5）。

#### B3.2 引用的命名

| 引用 | 用途 | 保留到 |
| --- | --- | --- |
| `refs/meldwork/effects/<h(副作用 id)>` | 所有快照与接受提交的幂等记录 | 见 B5 |
| `refs/meldwork/accepted/<h(checkpointId)>/<版本序号>` | 已接受版本（`ArtifactVersion.commit`） | 项目室删除时 |
| `refs/meldwork/candidate/<h(checkpointId)>/<轮次>` | 每轮的候选提交 | 所属检查点被接受或重开之后，只保留最后一轮 |
| `refs/meldwork/drift/<h(itemId)>/<修订号>` | 漂移条目的观察快照 | 条目解决或作废时 |

#### B3.3 对应的 M2 副作用

| M2 副作用 | git 做法 |
| --- | --- |
| `snapshot` | B3.1 |
| `evaluate-submission` | 目标文件或回应文件在快照中不存在是正常值，不是错误；`git diff` 对不存在的路径照常比较。`bodyChanged`：`git diff --quiet <上一轮候选> <本次快照> -- <目标文件>`。`newResponse`：回应文件在本次快照中存在，且与上一轮候选中的不同（`git diff --quiet <上一轮候选> <本次快照> -- <回应文件>`）。清单校验读取本次快照中的清单文件（`git show <提交>:<路径>`），不读工作目录 |
| `verify-candidate`、`verify-observed` | 先为工作目录做一次快照（B3.1），再 `git diff --quiet <候选或观察快照> <新快照> -- <文件>`。所有「工作目录是否仍等于某个提交」的比较都这样做，而不是直接拿工作目录与提交比较，这样占位路径（B3.5）与普通路径用同一种方式比较 |
| `drift-check` | 为工作目录做一次快照，对每个上游的已接受提交：`git diff --name-only -z <已接受提交> <快照> -- <上游的文件>`。有输出即为漂移，这次快照同时作为漂移条目的观察快照 |
| `detect-accepted-changes` | 为工作目录做一次快照，对每份已接受文档：`git diff --quiet <它的最新已接受提交> <快照> -- <文件>`；有差异时，这次快照作为新版本的候选 |

#### B3.4 上限

| 上限 | 默认值 | 超出时 |
| --- | --- | --- |
| 单个文件 | 50 MB | 以占位条目代替内容（B3.5）；目标文件与回应文件超出时快照失败 |
| 单次快照的用时 | 60 秒 | 见下 |
| 单次快照新增的文件数 | 20 万 | 见下 |

快照超出用时或文件数上限时，处理取决于它的用途：

- **调用前后的快照**（只用于越界检测）：放弃这次快照，结果为「已跳过」，越界检测随之跳过（A6）。这是唯一可以跳过的快照，跳过的结果在关卡上作为信号显示（M2 8.3），不会被当作「没有越界」。
- **其余所有快照都失败闭合**：送审快照、漂移的观察快照、接受提交，以及 B3.3 中为核对而做的快照（`verify-candidate`、`verify-observed`、`drift-check`、`detect-accepted-changes`）。它们是评审、版本和核对的依据，「无法核对」绝不当作「无差异」。超出上限时按 M2 9.2 作为必要副作用失败：实例暂停，错误条写明是哪一步（例如「工作目录太大，无法核对送审版本」），并建议在项目设置里增加排除规则或调高上限；人调整后重试。

上限可以在项目设置中修改。

#### B3.5 不存内容的路径：占位条目

有两类路径不把内容存进影子仓库：

- 超过单文件上限（默认 50 MB）的普通文件；
- 用户仓库里按 Git LFS 管理的文件。判定用**用户仓库**的属性：`git -C <root> check-attr -z --stdin filter`，值为 `lfs` 即是。工作目录不在 git 仓库里时，没有这一类。不能在影子仓库里判定，因为 B1 的 `info/attributes` 已经关闭了 `filter`。

**例外**：检查点的目标文件与回应文件总是保存完整内容，因为它们是评审与接受的对象。目标文件或回应文件超过上限时，快照作为必要副作用失败（M2 9.2），错误条写明是哪个文件。

**占位内容**：一个小的文本对象，记录这个路径的事实，而不是内容。占位只用于普通文件；符号链接本身很小，总是按链接保存。

```
meldwork-placeholder 1
reason oversize | lfs
mode 100644 | 100755
size <字节数>
sha256 <原始内容的 SHA-256>
```

**为什么这样做**：排除规则只对未跟踪的文件生效，已经在影子索引里的路径（曾被强制加入，或此前低于上限、后来变大）仍会被 `git add -A` 存入完整内容。B3.1 第 2 步先把这些路径移出索引，`git add -A` 之后再写入占位条目，所以无论路径此前是否被跟踪，都不会存入超限内容。

**每次快照对占位路径的处理**（B3.1 第 2、4 步的展开）。先确定本次的占位集合，再改排除规则，最后才 `git add -A`：

1. 候选路径 = 上一次快照的占位清单 ∪ `git status --porcelain=v2 -z --untracked-files=all`（影子仓库）列出的新增、改动与删除路径。**这一步必须在对影子索引做任何改写之前完成**，也就是在下面移出旧占位路径之前：`git status` 依据的是当前索引，索引一旦被改写，旧占位路径就不再「被跟踪」，它们的删除与变更信息会丢失。候选路径确定之后，本次快照只改写索引、不再调用 `git status`。
2. 对每个候选路径 `lstat`，按结果归类：

| 本次状态 | 处理 | 快照中的结果 |
| --- | --- | --- |
| 不存在 | 移出索引，从排除规则和占位清单中删除，**不写占位** | 该路径不存在，与上一次快照之间是一次删除 |
| 普通文件，超过上限或属于 LFS，且不是目标/回应文件 | 移出索引，写入排除规则；`git add -A` 之后写入占位条目 | 占位 |
| 普通文件，未超过上限且不属于 LFS（例如缩小了） | 从排除规则和占位清单中删除，交给 `git add -A` 正常加入 | 完整内容 |
| 符号链接或其他类型（例如普通文件被换成了链接） | 从排除规则和占位清单中删除，交给 `git add -A` | 按链接或其类型保存 |
| 目标/回应文件，超过上限 | 快照失败（必要副作用，M2 9.2） | — |

   排除规则的自动段每次都按本次的占位集合整体重写。否则一个已不再需要占位的路径会继续被排除，在快照里表现为「不存在」，被误报为删除。
3. `git add -A`，然后为第 2 步中「占位」一行的路径写入占位条目。

**占位哈希何时重算**：每个占位路径在占位清单里记录上次计算哈希时的文件状态：设备号、inode、大小、修改时间、状态变更时间（ctime），以及记录的时刻。本次 `lstat` 得到的这些值中任意一项变化，就重新计算 SHA-256。另外，如果上次记录时，文件的修改时间或 ctime 与记录时刻相差不到 2 秒（文件可能在同一时间粒度内又被写过），本次一律重算。

这与 git 判断普通文件是否变化的依据相同（git 的文件状态缓存，以及它的「racy git」处理）。保证程度也与 git 相同：

- 写入后用 `utimes` 把修改时间改回原值，仍会被发现，因为任何写入和 `utimes` 都会更新 ctime，用户态程序无法把 ctime 改回去。
- 不能发现的情况，与 git 对普通文件不能发现的情况相同：修改了系统时钟，或者绕过文件系统直接改写磁盘。这条写入架构 Known Risks，不宣称占位条目能发现一切内容变化。

如果改为每次快照都对所有占位文件重算哈希，素材很多的仓库（例如几十 GB 的二进制资源）每做一次快照就要多读一遍这些文件，而每轮检查点会做好几次快照。所以不采用。

**统一的路径状态**。为了让同一个变化在关卡、漂移条目、「文件」标签里看起来一样，每个路径在某个提交（或新快照）中的状态只取下面四种之一。所有显示变化、判断可选操作的地方，都调用 main 中同一个函数 `describePathChange(旧状态, 新状态)`：

| 状态 | 含义 |
| --- | --- |
| 不存在 | 提交中没有这个路径 |
| 文件（完整内容） | 普通文件，模式 `100644` 或 `100755`，内容保存在影子仓库 |
| 文件（占位） | 普通文件，只有模式、大小与 SHA-256 |
| 链接 | 符号链接，保存链接目标 |

`describePathChange` 的输出：

| 旧 → 新 | 显示 | diff 内容 |
| --- | --- | --- |
| 不存在 → 任一 | 新增（类型） | 完整内容可显示时显示 |
| 任一 → 不存在 | 删除（类型） | 完整内容可显示时显示 |
| 文件 → 文件，模式不同 | 可执行位变化；若内容也变，同时显示「内容变化」 | 完整内容可显示时显示 |
| 完整内容 → 完整内容，内容不同 | 内容变化 | 统一 diff（B6） |
| 涉及占位的文件 → 文件 | 大文件变化：大小 a → b（或 LFS 文件变化） | 不显示内容 |
| 文件 ↔ 链接 | 类型变化：文件 → 链接（目标 x），或链接 → 文件 | 链接显示目标；文件按以上规则 |
| 链接 → 链接，目标不同 | 链接目标变化：x → y | 无 |

**漂移的可选操作**由已接受一侧的状态决定，与入口无关：

| 已接受版本中的状态 | 「以工作目录为准」 | 「恢复为已接受版本」 |
| --- | --- | --- |
| 不存在 | 可用（接受新增） | 可用（删除工作目录中的这个路径） |
| 文件（完整内容） | 可用 | 可用（恢复内容与模式） |
| 链接 | 可用 | 可用（重建链接） |
| 文件（占位） | 可用 | **不可用**：影子仓库里没有内容；说明原因 |

「以工作目录为准」接受的是观察快照中的状态，可以是不存在、文件、占位或链接（M2 8.2）。

**各操作对占位路径的处理**：

| 操作 | 处理 |
| --- | --- |
| 快照之间的比较（越界、漂移、送审比较） | 照常 `git diff`；占位内容不同即文件不同；删除表现为路径不存在 |
| 工作目录与提交的比较 | B3.3：先做新快照，再比较两个提交 |
| 接受提交（B4） | 候选提交中的占位条目原样进入接受提交 |
| 恢复为已接受版本（B5） | 见上表 |
| 给 renderer 的 diff（B6） | 按 `describePathChange` |
| 提交到用户仓库（B7） | 前置条件比较工作目录文件与占位记录中的存在性、类型、模式、大小和 SHA-256；通过后照常由用户仓库提交 |

占位清单在项目设置中列出（M13）。

### B4. 接受提交

对应 M2 的 `accept-commit`。目标：提交树里的目标文件**严格等于候选提交**，再叠加平台管理的记录文件的当前内容（M2 9.1）。

这一步使用一份**临时索引**（`GIT_INDEX_FILE=shadow.git/accept-<h(副作用 id)>.index`）。它不扫描工作目录，只从候选提交构造树，所以不影响长期索引的文件状态缓存，也不受 B3.4 的上限影响：

1. `git read-tree <candidate>`。
2. 对每个记录文件（本检查点的评审文件与回应文件、`decisions.md`、`changes.md`）：`git hash-object -w -- <文件>` 得到对象，再 `git update-index --add --cacheinfo <模式>,<对象>,<路径>`。工作目录中不存在的记录文件跳过。
3. `git write-tree` → 树；`git commit-tree <树> -p <这个检查点上一个已接受提交（如有）> -m <检查点、决策 id>` → 提交。
4. 更新 `refs/meldwork/effects/<h(副作用 id)>` 与 `refs/meldwork/accepted/<h(checkpointId)>/<序号>`，删除临时索引。

里程碑检查点的候选提交覆盖整个工作目录，接受提交同样以它为基础。

### B5. 漂移确认与恢复

**以工作目录为准**（M2 8.2）：新版本以条目的观察快照为基础，用 B4 的方法构造。区别只在第 1 步读入的是观察快照，并且只取漂移条目涉及的文件，其余文件取自基准版本：先 `read-tree <基准版本>`，再用观察快照中这些文件的条目覆盖。

**恢复为已接受版本**（`restore-files`）。在 M2 5.4 的租约保护下，对每个文件：

1. 检查取消标记，已取消就停止，并上报「不会再执行任何改名」。
2. 取已接受版本中的内容：`git cat-file blob <提交>:<路径>`；同时取文件模式（`100755` 恢复可执行位）。
3. 在同一目录下写临时文件 `.<文件名>.meldwork-restore-<随机>`，`fsync`。
4. 检查取消标记；然后 `rename` 覆盖目标文件。
5. 已接受版本中不存在、工作目录中存在的文件（新增的文件），恢复即删除：先改名为同目录下的临时名，再删除。
6. 已接受版本中是链接的：在同一目录下以临时名创建符号链接，再改名覆盖。已接受版本中是占位的不在恢复范围内（B3.5）。

整个操作在 main 进程里执行，不启动子进程，所以「写入已结束」的确认就是这次操作的 Promise 已经落定（M2 5.4）。

### B6. 给 renderer 的 diff

- `git diff --no-color --no-ext-diff -M --numstat` 先得到每个文件的增删行数；二进制文件显示为 `-`，界面只显示「二进制文件已变化」。
- 再按需取单个文件的统一 diff：`git diff --no-color --no-ext-diff -M <a> <b> -- <文件>`；`b` 可以是工作目录。单个 diff 的输出上限 2 MB，超出时截断并标出，界面提供「在外部编辑器中打开」。
- 所有 diff 经 M8 的 `workdir:diff` 通道交给 renderer，路径校验在那里完成。

### B7. 提交到用户仓库

对应 M2 的 `user-git-commit`，规则在架构 M4，这里给出具体命令。这一步使用**用户自己的** git 环境：不带影子仓库的参数，不清除用户的 git 配置，钩子与签名照常生效；仍然以 `execFile` 调用、不经过 shell，并设 `GIT_TERMINAL_PROMPT=0`。

1. **定位**：`git -C <root> rev-parse --show-toplevel`。工作目录可能是用户仓库的子目录，下面的路径都换算成相对仓库顶层的路径。
2. **前置条件**（勾选时和执行时各检查一次）。对每个本次路径：
   - 索引等于 `HEAD`：`git diff --cached --quiet -- <路径>`。
   - 工作目录等于已接受版本，逐项比较：**存在性**（已接受版本中不存在的路径，工作目录里也不应存在）、**文件类型**（普通文件或符号链接）、**git 模式**（`100644`、`100755`、`120000`）、**内容**（普通文件比较原始字节的 SHA-256，符号链接比较链接目标字符串）。只比较内容不够：只改可执行位时内容哈希相同，但 `git add` 会把模式变化提交出去（实测 `mode change 100644 => 100755`）。已接受版本一侧的模式与内容取自影子仓库（B1 保证是原始字节），占位路径取自占位记录（B3.5）。不直接比较对象 id，因为用户仓库可能使用 SHA-256 对象格式。
   - 任一不满足：跳过，不碰索引（架构 M4）。
   - **两个仓库比较的对象不同**：影子仓库比较的是工作目录的原始字节（B1）；提交到用户仓库时，由用户仓库自己的属性决定存入什么，例如换行规范化、LFS 文件转成指针。前置条件保证的是「工作目录里这些文件此刻与接受版本逐字节、逐模式相同」，提交内容是用户仓库对这些文件按它自己的规则处理的结果。这与用户自己执行 `git add` 的行为一致。
3. **执行**：
   - 先把「已暂存」标记落盘（M2 第 10 节），再 `git add -f -A -- <路径…>`。`-f` 是必要的：目标文件可能被用户的 `.gitignore` 忽略（影子仓库里它们是强制加入的，B3.1），不加 `-f` 时 `git add` 以 1 退出、文件不进入索引（实测）。勾选「同时提交到 git」时，界面列出其中被 `.gitignore` 忽略的文件，提示「这些文件会被强制提交」。
   - 用 `git ls-files -s -z -- <路径…>` 记下本次暂存的条目，并落盘。
   - `git commit --only -m <说明> -m "Meldwork-Decision: <决策 id>" -- <路径…>`。
4. **失败时的恢复**：对每个路径，当前索引条目（`git ls-files -s`）仍等于第 3 步记下的条目时，`git reset -q -- <路径>` 把它恢复为 `HEAD`；不等的路径保持原样，并在通知里列出。
5. **重启后的核对**：`git log -1 --format=%(trailers:key=Meldwork-Decision,valueonly) HEAD`，值等于本次决策 id 即记为完成；否则按 M2 第 10 节，不重试、不恢复索引，只通知人。

### B8. 回收

- 不使用 git 的自动回收（`gc.auto=0`）。
- 引用按 B3.2 的保留规则删除；调用前后的快照引用在对应关卡决定后由 `drop-snapshot-refs` 删除。
- 应用空闲时（项目没有进行中的调用），如果松散对象超过 5,000 个，在项目互斥队列里执行一次 `git gc --prune=now`。所有需要的对象都有引用指向，所以立即修剪是安全的。
- 影子仓库的磁盘占用显示在项目设置中，暂不设上限，与轨迹的保留策略一致（R21）。

### B9. 失败与修复

| 情况 | 处理 |
| --- | --- |
| git 命令非零退出 | 作为副作用失败上报，按 M2 9.2 自动重试 3 次，之后暂停 |
| 长期索引损坏（`index file corrupt`） | 删除 `shadow.git/index`，下一次快照重新建立。只损失文件状态缓存，不损失数据。自动执行一次，再失败则按上一行处理 |
| 影子仓库目录缺失或对象缺失 | 项目室进入只读，界面说明；不自动重建，因为已接受版本已经无法核对 |
| 本机找不到 git | 创建项目室时失败并说明；已有项目室在启动时发现时进入只读 |

## C. 启动恢复中的顺序

应用启动时，M3、M6、M2 按以下顺序协作，前一步完成之前不进入下一步：

1. **调度器以恢复模式启动**：不授予任何可写申请，只接受 `holdRoot`、`registerResidual`、`restoreGranted`。
2. **为所有项目目录建立保护**：从工作区文件的项目列表（M1，`meldwork-workspace.json` 的 `projects`）读出每个项目室的工作目录，对每一个 `holdRoot(root)`。这一步只依赖工作区文件，不依赖各项目的状态文件，所以即使某个项目的状态文件读不出来，它的目录也已受保护。
3. **进程登记表恢复**（A14，M3 实现）：确认每个未结束容器已空；确认不了的调用 `registerResidual`。
4. **退出恢复模式**：调度器开始授予可写申请。与仍处于保护中的项目目录重叠的申请（例如使用项目目录的普通群聊）继续等待；其他申请照常授予。
5. **各项目的恢复屏障**（M2 第 10 节），各项目之间互不等待：在屏障内执行 `restoreGranted`（只含「已获批」且未被残留占用代表的申请），落盘后 `openRoot(root)`，再按原申请时间重新提交「等待中」的申请。
6. **读不出状态的项目**（状态文件损坏、迁移失败）：目录保持保护，项目室只读打开，界面说明原因。用户可以修复后重试；确实需要在这个目录里写入时，可以「解除这个目录的写入保护」。这一操作绕过了恢复的安全边界：此时残留进程、旧租约和已接受版本都是未知的，所以要求：
   - **先重新扫描**：解除之前必须先执行一次「重新检查残留进程」，对登记表中工作目录与这个目录重叠的记录再确认一次容器已空。扫描发现仍有确认不了的残留进程时，不允许解除，只能先处理残留占用（A5）。
   - **明确的确认**：确认弹层写明原因（「这个项目的状态读不出来；平台无法确认是否仍有 Agent 在写入、哪些写入权仍被占用、已接受版本是否完整」），并要求输入这个目录的文件夹名才能确认。
   - **记录**：在应用级的审计记录 `meldwork-private/audit.jsonl`（追加写、`0600`）中记下时间、目录、项目室 id、当时读不出状态的原因、扫描结果。项目状态文件读不出来，所以不能记在那里。
   - **解除之后的限制**：项目室保持只读，不执行自动恢复，不能接受任何检查点、不能处理漂移、不能提交到用户仓库；进度条与「待我决定」显示「写入保护已解除，项目状态未恢复」。状态文件修复并成功通过恢复屏障之后，这些限制才解除；屏障会把解除期间工作目录的变化当作漂移交给人确认（M2 第 8 节）。
   - 解除保护不解除残留占用。残留占用只能按 A5 处理。

这个顺序保证：在任何项目恢复旧租约之前，没有项目外的调用能先拿到它目录内的写入，项目恢复时也就不会把合法状态判为冲突。

`restoreGranted` 整体拒绝时（记录损坏），按 M2 第 10 节第 6 步：冲突的持有者记为 `blockedOn`，其余申请单独重试恢复。

## D. 测试

调度器（`desktop/test/run-scheduler.test.cjs` 扩展，`desktop/test/project-room-claims.test.cjs` 新增）：

- 冲突规则：相同路径、前缀路径、按段比较（`a/b` 与 `a/bc` 不冲突）、大小写不敏感卷、NFC 与 NFD 同名、`shared-legacy` 之间不冲突、残留占用与一切重叠声明冲突。
- 符号链接：`root/alias → root/docs` 时 `alias/spec.md` 与 `docs/spec.md` 冲突；尚不存在的文件按最近的已存在祖先解析；解析到 `root` 之外的声明被拒绝。
- 启动顺序：在进程登记表恢复期间提交一个使用项目目录的普通群聊申请，断言它在该项目 `openRoot` 之前不被授予，项目恢复旧租约时不报冲突；项目状态文件损坏时，断言目录保持保护；重新扫描仍发现残留进程时，断言不允许解除保护；解除后断言接受、漂移处理、用户仓库提交都被拒绝，审计记录已写入。
- 全有或全无：申请两个文件，其中一个被占用，断言两个都没有授予。
- 公平：工作目录申请在等待时，后到的单文件申请不能越过它；与它无关的申请可以越过。
- 生命周期：`withdraw` 对等待中、已授予、不存在三种情况都幂等；`release` 后立即授予下一位；`restoreGranted` 遇到重叠整体拒绝。
- 与 M2 的契约：在「调度器已授予、引擎未落盘」时模拟崩溃，断言重启后记录仍是「等待中」。

影子仓库（`desktop/test/shadow-git.test.cjs` 新增，使用临时目录与真实 git）：

- 参数与环境：断言每次调用都带 `--git-dir`、`--work-tree` 和 B1 的配置，清除了 `GIT_*`，不经过 shell；在用户全局配置里放入钩子和 `core.autocrlf=true`，断言不生效。
- 不碰用户仓库：在一个真实的用户仓库上运行全部操作，断言它的 `.git` 目录（索引、引用、配置、钩子）前后逐字节相同。
- 快照：被 `.gitignore` 忽略的目标文件仍进入快照；目标文件与回应文件都不存在时快照成功；被强制加入过的目标文件删除后，快照记录删除；超过单文件上限的被排除并列出；同一副作用 id 重复执行返回同一提交；含冒号等字符的副作用 id 生成合法的引用名与临时文件名。
- 原始字节：工作目录有 `*.txt text eol=lf` 规则、文件为 CRLF 时，断言快照保存 CRLF、文件改为 LF 后候选核对报告差异、恢复文件后字节与原来相同；可执行位变化被检测到；LFS 过滤不被调用。
- 接受提交：目标文件严格等于候选提交，即使工作目录已被改动；记录文件取当前内容。
- 恢复文件：在改名前后注入取消，断言不会出现写了一半的文件；新增文件被删除；可执行位被恢复。
- 候选路径的顺序：在实现里把「移出旧占位路径」放到 `git status` 之前（故意写错），断言测试失败：被删除的占位文件没有在新快照中表现为删除。正确顺序下断言通过。
- 占位条目的时序：删除一个占位文件，断言新快照中该路径不存在、与上一次快照之间是删除；占位文件缩小到上限以下，断言新快照保存完整内容、排除规则中已没有它；占位文件被换成符号链接，断言新快照保存链接。
- 占位哈希：大小与修改时间不变、但内容改写后用 `utimes` 恢复修改时间，断言 ctime 变化触发重算并报告变化；记录时刻与文件时间相差不到 2 秒时断言下一次强制重算。
- 核对快照失败闭合：让 `verify-candidate` 的快照超过用时上限，断言实例暂停、不进入接受；`drift-check` 同样。
- 路径状态：对第 B3.5 的每一种「旧 → 新」组合，断言关卡、漂移条目、「文件」标签得到相同的 `describePathChange` 输出与相同的可选操作。
- 占位条目：已跟踪的文件变大超过上限后，断言快照中是占位而不是完整内容，影子仓库对象库没有增加该大小的对象；占位文件内容或模式变化时，两次快照的 diff 报告变化；LFS 文件按用户仓库属性判定并占位；目标文件超过上限时快照失败并写明文件；占位路径的漂移只提供「以工作目录为准」。
- 用户仓库提交：被用户 `.gitignore` 忽略的目标文件提交成功；只改变可执行位时前置条件不满足；普通文件被替换为同内容的符号链接时前置条件不满足；用户已暂存其他文件时，断言它们仍然暂存且不在提交里；本次路径有用户暂存时跳过且索引不变；钩子拒绝时只恢复本次暂存的路径；子目录作为工作目录时路径换算正确；SHA-256 对象格式的仓库前置条件比较正确。
- 失败：删除长期索引后快照仍成功；git 不存在时创建项目室失败。
