本文定义项目室在产品层面的交互：用户在每个时刻看到什么、先看到什么、用什么动作推进，以及怎样把人的注意力花在该花的地方。组件拆分、数据接入和 IPC 属于 M12，M12 按本文实现。

## 1. 体验目标

需求原文：稀缺的是人的注意力。项目室要优化的是每一份被接受的产物消耗了人多少注意力，以及人有多放心。落到交互上是五条规则，后面每一节都从这里推出：

| # | 规则 | 怎么检验 |
| --- | --- | --- |
| X1 | 不在关卡上就不打扰：除关卡、未解决漂移、长时间无活动提醒、恢复提示和系统错误外，不弹通知，不抢焦点 | 一次完整的文档检查点里，用户收到的系统通知数等于关卡数 |
| X2 | 30 秒判断：不滚动就能看到结论、风险信号和决定区，据此决定「直接通过，还是需要细看」 | 关卡面板的标题与信号条固定在顶部，决定区固定在底部，中间区域按第 4 节的预算显示；在最小窗口尺寸和 200% 字号下验收 |
| X3 | 信号由平台给，摘要由评审者写：首屏上的风险信号来自状态和 git，不来自主笔的自我陈述 | 风险信号的每一项都能追溯到 M2 或 M4 的一个字段 |
| X4 | 任何结论都能一键追到来源：摘要 → 评审文件，改动 → diff，评审 → 完整轨迹 | 首屏每个元素都可以点开 |
| X5 | 看得见评审之后发生了什么：评审通过后人仍要求修改、最终评审才发现的问题，会作为事实记下来并在复盘里呈现，不由平台推断成「评审漏检」 | 第 9 节的本地指标 |

## 2. 用户在项目室里的四种处境

交互按用户此刻的处境组织，而不是按功能组织：

| 处境 | 用户想知道什么 | 主要界面 |
| --- | --- | --- |
| 离开时 | 有没有需要我做的事 | 系统通知、侧边栏「待我决定」 |
| 旁观时 | 现在在做什么、谁在做、做了多久、卡没卡住 | 进度条、时间线、右侧轨迹 |
| 决定时 | 能不能直接通过；不能的话看哪里 | 关卡首屏 |
| 回看时 | 这份产物是怎么来的，评审抓住了什么、漏了什么 | 检查点历史、文件 diff、复盘 |

## 3. 信息架构与布局

```
┌ 侧边栏 ───────┬ 主区 ─────────────────────────────────┬ 右侧抽屉 ───────────┐
│ 待我决定 (2)  │ 头部：项目室名 · 成员头像 · 抽屉开关   │ [文件] [轨迹]        │
│ ─────────────│ 进度条：访谈✓ 调研✓ 需求● 架构○ …      │                      │
│ ▾ 项目室 A ●  │ ──────────────────────────────────── │ 文件：               │
│    主流程     │ 时间线：主笔与评审的消息、关卡卡片     │  已接受文档（版本）  │
│    技术讨论   │                                        │  目录树              │
│ ▸ 项目室 B    │ ──────────────────────────────────── │  预览 / diff         │
│ 单聊、群聊…   │ 待决关卡固定在输入框上方               │ 轨迹：               │
│               │ 输入框（按处境切换用途，见第 6 节）    │  现有 RunTracePanel  │
└──────────────┴────────────────────────────────────────┴──────────────────────┘
```

决定：

- 右侧只有一个抽屉，分「文件」「轨迹」两个标签，不并排放两块面板。现有布局（`App.vue`）右侧已经是 `RunTracePanel`，再并排一个目录树会挤压主区。点击时间线里的某位 Agent 打开「轨迹」标签；点击关卡上的改动文件打开「文件」标签并定位到 diff。抽屉的宽度和上次的标签按项目室记住。
- 「文件」标签最上方是「已接受文档」列表：每份文档的当前版本、是否有待确认的新版本、是否过期。下面才是完整目录树。用户最常看的是已接受文档，不是整棵树。
- 侧边栏顶部的「待我决定」汇总所有项目室的待决关卡和未解决漂移（M2 第 8 节），按等待时间从长到短排列，数字是两者之和。项目室条目上的圆点表示它有其中任一项。项目全部完成后，未解决漂移仍留在这里，直到被处理。
- 窄窗口下，抽屉覆盖在主区上面，不再挤压主区，断点沿用现有样式。覆盖时按弹层规范处理：Escape 关闭，阻止背景滚动。
- 普通单聊和群聊的布局不变；它们的右侧抽屉只有「轨迹」标签。

## 4. 关卡首屏

关卡首屏是项目室最重要的一个界面。它同时出现在两处：时间线里的关卡卡片，以及固定在输入框上方的待决关卡（两者是同一个组件，后者是折叠态）。

展开后的面板分三段：顶部固定、中间可滚动、底部固定。不管内容多长，结论、风险信号和决定区都不会被挤出视野。

**顶部（固定）**

1. **标题行**：检查点名称 · 关卡原因（本地化，见第 8 节）· 第几轮 · 本检查点用时。
2. **信号条**：每位评审一个结论标签（通过 / 要求修改 / 需要人 / 未返回）。旁边是平台给出的风险信号，按严重程度排序，最多显示 4 个，其余收成「+N」；没有任何信号时显示「无风险信号」。风险信号全部是确定性的：

| 信号 | 来源 | 对决定区的影响 |
| --- | --- | --- |
| 上游有待确认的新版本，或上游有未解决漂移 | M2 第 8 节 | 「接受」不可用，附「去处理」链接 |
| 送审后文件有变化 | M2 候选核对 | 点「接受」时先让人二选一（见决定区） |
| 未全体通过（此时接受即「接受现状」） | M2 本轮结论 | 「接受」变为「接受现状」 |
| 越界改动 N 个文件（可归属 / 来源不确定） | M6 越界条目 | 无；接受即保留这些改动 |
| 主笔驳回了意见 / 经过驳回轮 | 回应文件存在 / 轮次标记 | 无 |
| 到达轮数上限 / 产物未变 | 关卡原因 | 无 |
| `changes.md` 头部缺失 | M4 核对 | 无 |
| 轮后检测被跳过（超过快照上限） | M4 | 无 |
| 评审与主笔是同一种 Agent | 席位配置 | 无 |

**中间（可滚动，有预算）**

| 区域 | 预算 | 超出时 |
| --- | --- | --- |
| 评审者摘要：每位评审文件开头的几行，原样显示 | 每位最多 4 行；最多显示 2 位，给出「需要人」「要求修改」的排在前面 | 「展开」看完整摘要；「另外 N 位评审」展开其余；每段附「打开评审全文」「查看这次评审的轨迹」 |
| 改动：文件列表，每行有增删行数，点击在右侧打开 diff。文档检查点对比上一次接受，里程碑对比上一个里程碑 | 最多 6 个文件，按改动量排序 | 「共 N 个文件」展开全部 |
| 软关卡批量摘要（硬关卡才有）：自上一个硬关卡以来自动接受的检查点，每个一行：名称、轮数、有没有风险信号 | 只列有风险信号的，最多 5 个 | 「另有 N 个检查点无风险信号」展开全部 |

**底部（固定）**：决定区，见下。

首屏不放主笔的总结。主笔的最后一条消息仍在时间线里，需要时可以看，但它不进入判断区（X3）。

### 决定区

需求规定只有三种走向：写了意见又没有点接受，就是继续改。按钮按这条规则设计：

| 控件 | 行为 |
| --- | --- |
| 意见输入框 | 自由文本 |
| 主按钮「接受」 | 有意见时，意见作为接受备注记入决策。没有全体通过时，按钮文字变为「接受现状」，点击后要再确认一次。上游有待确认的新版本时不可用（M2 6.1，不提供强制接受）。送审后文件有变化时，点击后先二选一：「接受送审版本」（工作目录里的后续改动不进入这次接受，留给下游开始前的漂移检查）或「以当前文件重新送审」 |
| 次按钮「发送意见，继续改」 | 只在输入框非空时可用；快捷键 `⌘/Ctrl + Enter` |
| 文字按钮「打回…」 | 打开打回弹层（第 5.5 节） |
| 勾选框「同时提交到 git」 | 只在工作目录是 git 仓库、且走向是接受时出现；默认不勾，按项目室记住上次的选择。前置条件不满足时（本次路径有用户暂存的改动，或工作目录与接受版本不一致，见架构 M4）不可用，并说明是哪个文件、怎么处理 |

- 「接受」不绑定快捷键，避免误触。接受之后没有撤销按钮；需要撤销时，在这个检查点上「重新打开」（5.10）。接受后的提示文字写明这一点。
- 某个走向在当前关卡原因下不可用时（见 M2 第 6 节），按钮置灰并说明原因，例如问题关卡上「接受」置灰，提示「请先回答主笔的问题」。
- 关卡在用户查看期间被刷新（例如「文档新版本」出现了更新的快照）时，提交会被 main 拒绝。面板顶部出现「关卡内容已更新，请重新查看」，首屏换成新内容，用户写的意见保留在输入框里。打回和重新打开的影响范围在预览后发生变化时同样处理：弹层回到影响预览这一步。
- 漂移关卡把「接受」换成二选一：「以工作目录为准」「恢复为已接受版本」，两项都附 diff 入口。
- 问题关卡把输入框标题改为「回答主笔」，主按钮是「发送回答」。

## 5. 关键流程

### 5.1 新建项目室

1. 选择工作目录。如果这个目录已经有项目室，直接打开它，不报错。
2. 选择 playbook：默认 playbook 或已保存的模板，并展示检查点链和硬关卡位置。可以当场改关卡的软硬和轮数上限。
3. 确认席位：每个默认角色已经填好角色名、侧写和建议的 Agent（来自确定性路由）。界面当场提示以下问题：
   - 评审者与主笔是同一种 Agent
   - 某个 Agent 未安装或未登录
   - 某种权限组合在这个 CLI 上表达不了（R16，不静默降级）
   - 某个 Agent 只能走回退通道、看不到完整轨迹
   - 某个 Agent 不支持「只运行命令」（`read-exec`），或在可写调用中不能保持会话（每轮都是新会话），或当前平台上受管理进程尚未实现（M3 第 10 节）
   - 任何席位有写入能力时，提示：「每一轮结束后，Agent 留下的进程（例如它启动的开发服务器）会被结束。需要常驻的服务请在 Meldwork 之外启动。」
4. 点「创建」后进入主流程群聊。不会自动开始；用户点进度条上的「开始」或在输入框里写下需求，第一个检查点（访谈）才启动。启动 Agent 就会消耗用量，所以由用户来触发。

### 5.2 访谈

主笔的问题以关卡的形式出现，标题是「主笔有 N 个问题」。主笔的问题原文在摘要位置，输入框标题为「回答主笔」。回答后主笔在同一会话里继续，可能再问，直到交回 `ready`。

### 5.3 旁观

- 进度条：一行显示检查点链，每个检查点一个状态图标（第 8 节）。当前检查点展开成一句话：「评审中 · 第 2 轮 · Codex（对抗评审）· 已 12 分钟」。点击展开完整列表，模块文档和里程碑按清单嵌套。
- 时间线：主笔和评审的回答以消息出现。超过一屏时折叠，并给出「在文件中查看」，因为文档才是真源。每条消息的头像可以点开这次调用的轨迹。
- 旁观不需要任何操作。进度条和时间线在应用后台时也照常更新，但不弹通知（X1）。

### 5.4 插话

主笔或评审正在工作时，以这个检查点为操作目标（第 6 节），输入框的提示文字是「对检查点 X 提出意见（这一轮结束后交给主笔）」。发送后，插话以「排队中」的气泡显示在时间线底部。气泡上有「停止并立即交付」：点击后结束当前一轮，立即交给主笔。如果这一轮的评审已经给了 `pass`，气泡上提示「插话会让本轮的通过作废」。

### 5.5 打回

1. 在关卡上点「打回…」，打开弹层。
2. 第一步：选择上游检查点，以检查点链的形式列出，只有上游可选。
3. 第二步：影响预览。平台列出会被标为过期的检查点，以及会被取消的进行中调用，并标明其中的硬关卡和已经写好的代码。
4. 填写打回理由（必填），这段理由会交给被打回检查点的主笔。确认后关闭弹层，进度条上相关检查点显示过期图标。

弹层支持 Escape 返回上一步或关闭，打开时阻止背景滚动。

### 5.6 长时间运行

- 进度条一直显示「最近一次活动：N 分钟前」。
- 到达无活动阈值时，在进度条下方出现提醒条：「主笔已 25 分钟没有新输出」，提供「继续等待」「停止这一轮」两个按钮，并附「查看轨迹」。同时发一条系统通知。选择「继续等待」后，同一轮不再重复提醒，除非又过了一个阈值。
- 不自动停止（R20）。

### 5.7 失败、恢复与接替

- 失败关卡的标题写明失败分类（登录失效、额度用尽、连续失败），并给出对应的下一步：登录失效 → 「在终端登录后重试」，附命令说明；额度用尽 → 「稍后重试或换一位 Agent 接替」。「换人接替」打开席位配置并选中这个席位；保存后回到关卡，点「重试」即用新的 Agent、新的会话继续。
- 应用异常退出后重启时，如果上次有 Agent 进程（包括它启动的测试、构建）仍在运行，平台会先结束它们，再恢复项目。结束不了的，在「待我决定」里出现一条「上次的 Agent 进程仍在运行」：写明是哪个群聊或检查点、进程组 id、所在工作目录，并列出这些进程（进程 id、命令、启动时间、是否带有本容器的标记）。平台不会自动结束它们：原来的监护程序已经不在，对单个进程发信号无法排除进程 id 被复用、误伤无关进程的可能（M3 3.7）。按钮是「我已手动结束」和「这些进程与 Meldwork 无关」，平台在你选择后再复核一次，复核通过才放行。只有原来的监护程序仍在运行时，才显示「等待它完成清理」并自动继续。在处理之前，相关的写入权不会交给任何人，界面上相关的检查点和项目内群聊显示「等待写入权：上次的进程仍在运行」。残留占用按目录生效：使用同一目录、其父目录或子目录的任何群聊（包括项目外的普通群聊）在此期间都不能写入，它们的消息上同样显示「等待写入权：上次的进程仍在运行」。
- Windows 上，崩溃后残留进程的保证在实测通过之前没有实现（架构 A14）。项目室的设置页和新建流程第 3 步都写明这一点。
- 应用重启后，有恢复关卡的项目室在侧边栏显示圆点；打开时首屏说明「上次在 14:02 中断：主笔正在写入」，提供「在同一会话续跑」「把当前文件送审」两个选项。

### 5.8 文档新版本

主笔在里程碑里改了需求文档后，关卡出现在需求检查点上，并进入「待我决定」。首屏的改动区就是这份文档相对上一个接受版本的 diff，摘要位置显示 `changes.md` 里对应的那条记录。里程碑继续推进；它的进度项上显示「等待需求新版本确认后才能接受」，它的关卡上「接受」不可用，并附「去处理」链接直达需求检查点的关卡。

### 5.8.1 未解决漂移

在关卡上选了「接受送审版本」、而工作目录与送审版本不同，或者检查点开始前发现文件与已接受版本不一致时，这些文件会作为「未解决漂移」立即出现在「待我决定」里，不等下一个检查点开始。

- 每个条目显示：文件、它属于哪个已接受的检查点、发现时间、与已接受版本的 diff 入口。
- 显示的 diff 是发现差异时的固定快照，不随工作目录实时变化。处理方式二选一：「以工作目录为准」（接受的就是你看到的这份快照，形成新的已接受版本）或「恢复为已接受版本」。可以多选条目后一次处理。
- 超过大小上限的文件和 LFS 文件，平台只记录它们的大小与哈希、不保存内容，所以只能选「以工作目录为准」，「恢复为已接受版本」不可用并说明原因。
- 变化的说法（新增、删除、内容变化、可执行位变化、大文件变化、类型变化、链接目标变化）与可选操作，在关卡、漂移条目、「文件」标签中完全一致，由同一条规则生成（M4/M6 B3.5）。文案进入中英文 locale。
- 你查看之后文件又被改动时，处理会被拒绝，条目刷新为新内容并提示「内容已变化，请重新查看」。
- 刚在关卡上「接受送审版本」时，接受本身还在保存，条目已经显示，但处理按钮不可用，显示「等待接受完成」；接受因错误暂停时，提示先在项目室顶部的错误条上重试。
- 归属的文档在此期间又形成了新版本时，条目会按新版本重新比较：差异消失就自动标为已解决，仍有差异就刷新内容。
- 「恢复为已接受版本」要先拿到这些文件的写入权。主流程正在运行里程碑时，恢复会等到它的循环到达关卡；条目上显示「等待写入权」，等待期间可以「取消处理」，取消立即生效，条目回到未解决。恢复过程中出错时，条目显示「恢复已暂停」，重试会从出错的那一步继续。
- 条目未处理时，依赖它的检查点照常运行，进度项上显示「有未解决漂移，处理后才能接受」，关卡上的「接受」不可用并附「去处理」。

### 5.9 最终评审与复盘

最终评审是硬关卡。接受之后，进度条末尾出现可选的「复盘」。复盘的首屏是第 9 节的本地指标，加上复盘评审者列出的「前面没抓到的问题」和 playbook / 侧写的调整建议。每条建议可以单独采纳，采纳即生成 playbook 或侧写的新版本。

### 5.10 重新打开已接受的检查点

进度条展开后，每个已接受的检查点（包括最终评审）都有「重新打开…」；「文件」标签的已接受文档列表上也有同样的入口。流程与打回相同：影响预览 → 填写理由（必填）→ 确认。这是接受之后唯一的「撤销」方式，项目全部完成后同样可用。

### 5.11 主流程群聊的时间线

（定稿后的补充。）主流程群聊的时间线由两类内容组成：**存下来的消息**与**从投影生成的卡片**。Agent 与人提交过的有效内容存为消息；当前卡片来自实时状态，已结束关卡与检查点开始／重开记录来自 M1/M5 4.5 的私有历史存储，不依赖会被压缩淘汰的决策索引。卡片不存为聊天消息。

**存为消息的**（由 M2 的 `append-message` 在状态提交后写入，使用稳定来源 id、原始时间和私有正文暂存引用；不在调用回调中直接写消息。存为顶层字段 `projectRoom`，白名单与持久化去重见 M1/M5 4.5）：

| 来源 | 角色 | 内容 | 附加的元数据 |
| --- | --- | --- | --- |
| 主笔、草稿席位、评审的一次调用结束 | `agent` | 最终回答，**去掉结尾标记**（M3 4.4）；评审的回答就是评审文件的正文 | `projectRoom = { projectId, checkpointId, seatId, role: 'lead' \| 'draft' \| 'review', round, generation, verdict?, signal?, reviewFile? }`；现有的 `trace` 胶囊照常附上，供点击头像打开轨迹（M7/M8） |
| 人在关卡上提交的意见 | `user` | 意见原文 | `projectRoom = { projectId, checkpointId, generation, gateId, revision, outcome }` |
| 人的插话（交付给主笔时） | `user` | 插话原文 | `projectRoom = { projectId, checkpointId, generation, interjection: true, interjectionId }` |
| 项目开始时的需求（`start`） | `user` | 需求原文 | `projectRoom = { projectId, start: true }` |

- 调用失败、被取消、标记缺失时，仍存一条消息：有回答文本就存回答，没有则不存；失败本身由关卡卡片表达，不另存系统消息。
- 消息正文超过一屏时折叠，并给出「在文件中查看」（5.3）：主笔消息指向它的目标文件，评审消息指向评审文件。
- 只读的评审被取消（M2 第 7 节）、晚到被丢弃的结果（M2 4.2）**不存为消息**：它们不是有效的历史。

**从投影生成的卡片**（不存为消息，随项目快照变化）：

| 卡片 | 位置 | 内容 |
| --- | --- | --- |
| 检查点分隔条 | 一个检查点第一条消息之前 | 检查点名称、开始时间；之后每次重开（打回、重新打开）另起一条，写明「第 N 次开始：原因」 |
| 关卡卡片 | 产生关卡的那条消息之后 | 第 4 节的关卡面板（折叠态）；已决定的关卡显示为一行摘要：原因、走向、时间，可展开看意见 |
| 排队中的插话 | 时间线底部 | 5.4 的气泡 |
| 运行中的调用 | 时间线底部 | 「主笔工作中 · 已 N 分钟」等，与进度条一致 |
| 未解决漂移、越界、错误条 | 不在时间线中 | 在「待我决定」与项目室顶部（第 3 节、5.7） |

卡片插在时间线中的位置，由投影给出的时间戳与消息的时间戳排序决定。

历史卡片经 `timelineHistory` 分页加载，服务合并已归档记录与发件箱中已提交但尚未归档的历史，按稳定 id 去重；`project:changed` 后刷新最近页，不把完整历史塞进每次项目快照。重启、关卡决定后以及状态压缩后，旧卡片仍能展开。时间与代数取自原事件，不能取重放时的当前值。

**检测与失败的显示**：群聊写入尚待检测（包括排队、执行、重试）时，接受按钮禁用并显示「等待文档变更检测」，不是等失败后才禁用。检测失败显示项目级错误条与诊断；项目级「重试」调用不带 `checkpointId`，不要求人选择一个无关的检查点。关卡仍可查看，取消与租约释放不受影响。上述文案均提供中英翻译。

**重开之后的旧消息**：检查点被打回、重新打开或过期后重新开始时，之前各轮的消息保留在时间线中，标为「之前的第 N 次」，默认折叠在检查点分隔条下；新的一次从新的分隔条开始。已作废的关卡（M2 5.1：上游重开时作废并记入决策）显示为一行「已作废：上游被重开」。

**项目内的其他群聊**：时间线保持普通群聊的形式，不显示检查点卡片；其中 Agent 的回答若修改了已接受文档，修改的结果出现在主流程群聊的关卡或下一个关卡的摘要中（M3 4.6（四）），而不是在这个群聊中。

### 5.12 用量的显示

（定稿后的补充，对应 R28 与 M3 第 9 节。）

- **进度条**：展开后的完整列表中，每个检查点一行显示它的累计用量（token 数，可得时附估算费用）。
- **关卡首屏**：标题行（第 4 节第 1 项）在用时之后显示本检查点的累计用量。
- **消息**：每条 Agent 消息的元数据行显示这次调用的用量（沿用现有消息上的用量显示方式）。
- **项目室概览**（点击进度条标题）：全项目累计，按席位分列。
- 估算费用一律标明「估算」；拿不到 token 数的 Agent 显示「不可用」，不以字数估算冒充 token（M3 第 9 节）。
- 暂不设预算上限（需求「成本与通知」），不因用量产生关卡或通知。

## 6. 输入框与操作目标

主流程群聊只有一个输入框。项目室里可能同时有几个检查点在运行或等人（并行模块文档），所以输入框总是绑定一个**明确的操作目标**，而不是猜测「当前检查点」。

- 输入框上方显示目标条：「正在操作：检查点 X · 插话」或「正在操作：检查点 X · 关卡意见」。目标条旁边显示「另有 N 个待决关卡」，点击可以切换。
- 切换目标只有两种方式：点击进度条上的检查点，或点击某个关卡卡片。后台状态变化不会切换目标；别的检查点出现新关卡时，只更新「另有 N 个待决关卡」和侧边栏，不抢走输入框。
- 进入主流程群聊时的默认目标：等待最久的待决关卡所在的检查点；没有待决关卡时，最近活动的运行中检查点；都没有时没有目标。
- 草稿按目标分别保存。切换目标时，原来写的文字留在原目标上。
- 用途由目标检查点的状态决定（与 M2 第 7 节一致）：

| 目标检查点的状态 | 用途 | 提示文字（中文） |
| --- | --- | --- |
| 项目刚建好，还没有开始 | 写下需求并开始 | 描述你要做的事，发送后开始访谈 |
| `pending`、`checking` | 插话（排队） | 对检查点 X 提出意见，它开始时交给主笔 |
| `drafting`、`leading`、`submitted`、`reviewing` | 插话（排队，可停止并交付） | 对检查点 X 提出意见（这一轮结束后交给主笔） |
| 有待决关卡（包括 `accepted` 上的「文档新版本」关卡） | 关卡意见；问题关卡为「回答主笔」 | 写下意见（不点接受就是继续改） |
| `accepted`、`stale`，且没有待决关卡 | 不可用 | 这个检查点已接受，可以重新打开 |
| 没有目标（全部完成） | 不可用 | 项目已完成；可以在进度条上重新打开某个检查点 |

- 用途看的是「有没有待决关卡」，不只看 `state`。所以 `accepted` 实例上挂着「文档新版本」关卡时，输入框写的是关卡意见。
- 写到一半，目标检查点的用途变了（例如运行中的检查点进入了关卡）：文字保留，目标条上出现一行提示「检查点 X 已进入关卡，发送将作为关卡意见」，发送按钮的文字随之改变。发送永远由用户显式触发。
- 发送时带上目标实例 id、用途和关卡 id（如有）。main 发现与当前状态不符时拒绝，并返回原因；renderer 保留文字、显示原因，不自动改投到其他目标。
- 输入框旁边有「去项目群聊讨论」：打开这个项目室最近的项目内群聊，没有时新建一个。主流程输入框只用于推进流程；想自由讨论时从这里去。

项目内的其他群聊保持普通群聊的输入框行为，只有一处不同：主流程有检查点处在主笔与评审的循环中时，这些群聊的可写调用要等待（架构 M6）。等待时，消息上显示「等待写入权：主流程的检查点 X 正在工作，预计在它进入关卡时开始」，并提供「取消」和「改为只读回答」。只读调用不受影响。新建项目内群聊时，在输入框下方用一行说明提示这条规则。

### 普通群聊的写入开关

A14 同样作用于项目外的普通群聊，这是对它们现有行为的改变。普通群聊打开写入权限的开关旁，以及升级后第一次打开这个开关时，显示同一句说明：「每一轮结束后，Agent 留下的进程（例如它启动的开发服务器）会被结束。」这句说明进入中英文案。

## 7. 通知与打扰

| 时机 | 系统通知 | 侧边栏 | 其他 |
| --- | --- | --- | --- |
| 进入关卡（硬关卡、问题、失败、漂移、文档新版本等） | 是；点击打开对应关卡 | 「待我决定」+1 | — |
| 软关卡自动接受 | 否 | 否 | 进入下一个硬关卡的批量摘要 |
| 长时间无活动 | 是 | 否 | 进度条下的提醒条 |
| 重启后有恢复关卡 | 是，合并成一条 | 圆点 | — |
| 出现未解决漂移 | 是；与同时产生的关卡一起按 30 秒合并 | 「待我决定」+1 | 依赖它的进度项显示阻止接受的提示 |
| 必要副作用重试用尽、实例暂停 | 是 | 圆点 | 项目室顶部的错误条 |
| 检查点开始、轮次推进、评审返回 | 否 | 否 | 进度条更新 |

- 30 秒内产生的多个关卡合并成一条通知：「项目室 A 有 3 个待决关卡」。
- 用户正在看这个关卡时不发通知。
- 系统通知的文字只包含项目室名、检查点名和关卡原因，不包含产物或评审的内容（锁屏上可见）。

## 8. 状态用语

M2 的内部状态对用户统一呈现成下面这些词。全部进入 `zh.js` / `en.js`，状态图标不只靠颜色区分：

| 内部状态 | 中文 | English | 图标 |
| --- | --- | --- | --- |
| `pending` | 等待上游 | Waiting on upstream | 空心圆 |
| `checking` | 核对文件 | Checking files | 旋转 |
| 任意运行中状态，正在等待写入租约 | 等待写入权 | Waiting for write access | 沙漏；悬停说明是哪个群聊或检查点在写 |

| `submitted` | 准备送审 | Preparing review | 旋转 |
| `reviewing` | 评审中 | In review | 旋转 |
| `gate` | 等你决定 | Needs your decision | 实心圆 + 感叹号 |
| `accepting` | 正在保存 | Saving | 旋转 |
| `accepted` | 已接受 | Accepted | 对勾 |
| `stale` | 需要更新 | Needs update | 循环箭头 |

关卡原因的用语：硬关卡通过 → 「评审已通过，等你确认」；需要人 → 「评审请你裁决」；驳回未获接受 → 「主笔与评审意见不一致」；轮数上限 → 「已到评审轮数上限」；产物未变 → 「要求修改但没有改动」；问题 → 「主笔有问题」；续跑上限 → 「主笔多次未完成」；标记缺失 → 「无法判断主笔是否完成」；失败 → 「主笔调用失败」；评审失败 → 「评审调用失败」；漂移 → 「文件与已接受版本不一致」；文档新版本 → 「已接受文档有新版本」；恢复 → 「上次中断」；清单无效 → 「检查点清单格式不对」。英文文案在 locale 文件中给出。

## 9. 看得见评审之后发生了什么：本地指标

所有指标只在本机计算和保存（M1 项目状态），不上报，不引入遥测。

| 指标 | 怎么得出 |
| --- | --- |
| 每个关卡的决定用时 | 关卡产生到决定的时间 |
| 评审通过后人工要求修改 | 关卡原因是「硬关卡通过」，而走向是继续改或打回。只记录这个事实，不推断原因：可能是评审漏检，也可能是人有了新想法或偏好变化。不要求用户额外标注 |
| 接受现状的次数 | 没有全体通过时的接受 |
| 打回与重新打开 | 来源、目标与理由 |
| 最终评审发现、前面没抓到的问题 | 复盘评审者列出 |

这些指标出现在复盘首屏，以及项目室概览（点击进度条标题）。它们是给人判断「评审值不值得信任」的事实材料，平台不据此给评审打分；复盘评审者和人据此调整 playbook 与侧写（R29）。

## 10. 通用规范

- 中英双语：所有新文案进入 `frontend/src/locales/zh.js` 与 `en.js`。
- 弹层（席位配置、打回、接受现状确认）：沿用 `useOverlayLifecycle.js`，支持 Escape / 返回，阻止背景滚动。

- 视觉：沿用现有的颜色变量和组件风格，不做重新设计。
- 用户在 Electron 桌面模式下验收所有流程（AGENTS.md）。
