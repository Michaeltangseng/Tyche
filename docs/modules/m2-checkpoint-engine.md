# 模块文档：M2 检查点引擎

第十版，2026-11-13。

- 第二版吸收评审 r1：关卡与接受绑定候选提交；调用结果按调用 id 隔离；副作用结果与状态转移同一次原子写入；上游待确认成为接受的前置条件；一个关卡只有一个原因；新增「重新打开」。
- 第十版随 M1/M5 评审 r21 同步：租约的调度器通知（`release-scope`、`withdraw-lease`）与取消调用不随纪元作废；新增调度器对账。
- 第九版随 M3 评审 r12 同步：一轮评审中先并行运行只读评审，再逐个运行 `read-exec` 评审，每个 `read-exec` 评审结束后核对候选内容；取消 `read-exec` 评审要等容器清空。
- 第八版吸收评审 r7（`docs/reviews/architecture-v5/r7-review.md`）：确认不了已结束的持有者只恢复一次，由残留占用代表；残留占用按真实路径识别冲突。
- 第七版吸收评审 r6（`docs/reviews/architecture-v5/r6-review.md`）：残留进程的处理上移为架构决定 A14「受管理的可写进程」，本文只引用它的契约：结束以进程容器已空为准；恢复屏障先处理应用级的进程登记表，确认不了的作用域在调度器里保持「残留占用」；覆盖项目内群聊。
- 第六版吸收评审 r5（`docs/reviews/architecture-v5/r5-review.md`）：撤回与释放都先在转移里落盘、再通知调度器；调度器在释放通知之前不把冲突的作用域授予下一位；等待中的申请立即撤回，只有实际写入需要等待结束；「结束」以确认进程退出或写入不再发生为准，超时不算结束；崩溃后的残留 Agent 进程在恢复屏障里先确认结束。
- 第五版吸收评审 r4（`docs/reviews/architecture-v5/r4-review.md`）：新增 5.4「租约的生命周期」（申请、获批、撤回、释放分别持久化，获批结果按申请隔离，撤回同时覆盖等待中与已获批）；漂移处理必须等原接受事务完成并绑定基准版本；越过暂停的只限放弃时的清理，正常流程中的释放按顺序执行；受租约保护的副作用启动前确认租约仍在；恢复屏障只恢复已获批的租约，等待中的申请在屏障后重新排队。
- 第四版吸收评审 r3（`docs/reviews/architecture-v5/r3-review.md`）：未解决漂移改为状态而不是副作用，与接受同一次落盘；漂移条目带修订号和观察快照；恢复文件经租约执行；协调类副作用越过暂停，纪元变化时清理作废的失败；重启先建屏障、重建租约，再执行任何副作用；用户仓库提交只在自己改过索引时才恢复索引。
- 第三版吸收评审 r2（`docs/reviews/architecture-v5/r2-review.md`）：
  - 检查点在主笔与评审的整个循环里持有写入租约，保证评审读到的是候选内容。
  - 关卡带修订号，决定必须带关卡修订号和候选提交；打回与重新打开的预览带影响范围哈希。
  - 副作用带执行纪元，上游重开时作废过期的待执行副作用。
  - 新增项目级「未解决漂移」。
  - 写入作用域取代「每个实例一个可写调用」。
  - `ArtifactVersion` 记录接受提交。
  - 定义副作用失败的处理。

依据：`docs/product-target.md`（R1–R5、R7、R11、R12、R15、R17、R19、R20、R27）与 `docs/functional-architecture.md` 第七版（决定 A10–A13）。本文给出单个检查点的完整「状态 × 事件」转移表、关卡走向、副作用目录和恢复规则。实现与单元测试以本文的表为准；表外的组合一律视为「事件被忽略」并记录诊断日志。

## 1. 范围

| 本模块负责 | 不负责 |
| --- | --- |
| 单个检查点的状态转移（纯函数） | 提示词拼装、会话键、权限映射（M3） |
| 项目级进度：依赖、清单展开、打回与重新打开的影响范围、未解决漂移（纯函数） | 影子仓库的 git 调用细节（M4） |
| 副作用的定义、发件箱、幂等执行、失败处理与重启重放 | 关卡首屏的渲染（M12、M13） |
| 关卡的产生与决定的校验 | 租约在调度器里的实现（M6） |

文件：`desktop/src/project-room/checkpoint-transitions.cjs`、`project-progress.cjs`、`effect-runner.cjs`、`checkpoint-engine.cjs`。

## 2. 实例里与转移有关的字段

| 字段 | 含义 |
| --- | --- |
| `state` | 见第 3 节 |
| `seq` | 转移序号，每次转移加 1；副作用 id = `<实例 id>:<seq>:<序号>` |
| `epoch` | 执行纪元。进入 `stale`、被打回或重新打开时加 1；每个副作用记录产生它时的纪元（5.3） |
| `round` | 已发起的评审轮数 |
| `roundsSinceHuman` | 自上一次人的输入（关卡决定或插话）以来的评审轮数；轮数上限按它判断 |
| `continuations` | 当前主笔会话的续跑次数；人的输入后归零 |
| `sessionGeneration` | 主笔会话代数。重入（打回、重新打开、过期后重开、换人接替）时加 1，会话键为 `project:<projectId>:cp:<checkpointId>:seat:<seatId>:<kind>:g<n>` |
| `candidate` | 当前候选提交：最近一次送审快照的提交号。本轮评审、关卡和接受都绑定它 |
| `rounds[]` | 每轮：候选提交、`rebuttal`（是否驳回轮）、各评审席位的结论与评审文件路径 |
| `leaseRequests` | 这个实例名下的租约申请（5.4）：申请 id、作用域、所属副作用链、申请时的纪元、申请时间、状态（等待中 / 已获批 / 待释放 / 已撤回 / 已释放） |
| `activeInvocations` | 进行中的调用：副作用 id → 角色（主笔 / 草稿 / 评审）、席位、写入作用域（只读调用为空）、轮次、会话代数、是否已请求取消；可能写入的调用（`workspace-write` 与 `read-exec`）另记它在进程登记表中的记录 id（A14） |
| `pendingStart` | 等某个写入作用域空出来后要发起的调用（5.2） |
| `drafts` | 并行草稿：每个草稿席位的结果（ready / question / 失败 / 未返回） |
| `interjections[]` | 插话：内容、状态（排队 / 已交付） |
| `gate` | 待决关卡或 `null`：id、修订号、唯一的原因、绑定的候选提交、首屏内容 |
| `blockedOn` | 必要副作用失败时记下的副作用 id 与错误；非空时这个实例的副作用暂停执行，清理类除外（9.2） |
| `effects[]` | 发件箱：每个副作用有 id、类型、纪元、类别（9.1）、状态 |

项目级字段（M1 项目状态文件）：未解决漂移列表（第 8 节）、越界条目列表（M6）。

## 3. 状态

| 状态 | 含义 | 是否有进行中的调用 |
| --- | --- | --- |
| `pending` | 依赖还没有全部接受 | 否 |
| `checking` | 漂移检查中（R11） | 否（只有 git 副作用） |
| `drafting` | 并行草稿进行中 | 是，多个 |
| `leading` | 主笔这一轮进行中 | 是 |
| `submitted` | 主笔交回 `ready`，正在做送审快照与比较 | 否（只有 git 副作用） |
| `reviewing` | 评审进行中 | 是，每位评审一个 |
| `gate` | 等人；`gate` 字段非空 | 否（可能有正在结束的已取消调用，见 5.2） |
| `accepting` | 接受的副作用正在执行 | 否 |
| `accepted` | 已接受 | 否 |
| `stale` | 上游被打回或重新打开，等待上游重新接受 | 可能有正在结束的已取消调用 |

`accepted` 状态下也可以挂一个待决关卡（需求或架构文档的新版本，第 6 节），这时 `state` 保持 `accepted`，`gate` 非空。

## 4. 事件与结果的消费

### 4.1 事件

| 事件 | 来源 | 载荷 |
| --- | --- | --- |
| `DEPS_READY` | 项目级进度 | — |
| `INVOCATION_ENDED` | 调用副作用 | 副作用 id、角色、席位、轮次、会话代数；结果：`marker`（主笔与草稿为 `ready` / `question` / `continue` / 缺失；评审为 `pass` / `revise` / `needs-human` / 缺失）、`failed`（附失败分类）或 `cancelled` |
| `EFFECT_RESULT` | 其他副作用 | 副作用 id、类型、结果（第 9 节） |
| `EFFECT_FAILED` | 副作用执行器 | 副作用 id、错误；只在自动重试用尽后发出（9.2） |
| `RETRY_EFFECT` | 人 | 副作用 id |
| `GATE_DECIDED` | 人（经 M5 校验） | 关卡 id、关卡修订号、候选提交（如有）、走向、意见、打回目标与影响范围哈希、漂移时选定的版本、是否提交到用户 git |
| `REOPEN` | 人（经 M5 校验） | 理由、影响范围哈希。只对 `accepted` 实例有效 |
| `INTERJECT` | 人 | 内容 |
| `STOP_AND_DELIVER` | 人 | — |
| `UPSTREAM_REOPENED` | 项目级进度（打回或重新打开） | 被重开的上游 |
| `UPSTREAM_BLOCKERS_CHANGED` | 项目级进度 | 读取过的上游出现或解除了「文档新版本」关卡或未解决漂移 |
| `ACCEPTED_DOC_CHANGED` | 已接受文档检测副作用 | 文件、新快照提交号、`changes.md` 头部是否齐全 |
| `RESTORED` | 启动恢复 | 发件箱里「已开始」但没有被消费的副作用 |

### 4.2 结果的隔离

- `INVOCATION_ENDED` 只有在它的副作用 id 仍在 `activeInvocations` 里时才被处理，处理后从中移除。轮次与会话代数也必须与记录一致，否则按「被忽略」处理并记录诊断日志。这样被取消的旧评审即使在新一轮里才返回，也不会被当成新一轮的结果。
- 被取消的调用仍会产生一次 `INVOCATION_ENDED`（结果通常是 `cancelled`，也可能在取消生效前已正常结束）。它的作用只有一个：把这次调用从 `activeInvocations` 中移除，并空出它的写入作用域。它带回的标记或结论一律丢弃。
- M3 保证 `INVOCATION_ENDED` 在调用的进程已经退出之后才发出。

### 4.3 结果与转移同一次落盘

副作用执行器不单独把副作用标记为「完成」。副作用的结果作为事件送进转移函数；转移函数在同一个新实例里把这个副作用标记为已消费，并追加新的副作用；这个新实例一次原子写入项目状态文件。

崩溃发生在执行之后、落盘之前时，这个副作用在文件里仍是「待执行」或「已开始」。重启后按第 10 节处理：可以重放的副作用重新执行一遍，得到同样的结果后再消费；不能重放的调用按 R20 的规则处理。不存在「已完成但结果丢失」的状态。

唯一单独落盘的标记是「已开始」：调用和用户仓库提交在执行前先写这个标记，重启时据此判断（第 10 节）。

## 5. 转移表

记号：`→ X` 表示进入状态 X；`fx:` 是写进发件箱的副作用；`gate(原因)` 表示进入 `gate` 状态并产生关卡。下表中的调用结束事件都已经通过了 4.2 的隔离检查。

### 5.1 主表

| 当前状态 | 事件 / 条件 | 结果 |
| --- | --- | --- |
| `pending` | `DEPS_READY` | `→ checking`；fx: 漂移检查 |
| `checking` | 漂移检查 clean，上游没有未解决漂移，有并行草稿定义 | `→ drafting`；获取各草稿作用域；fx: 每个草稿席位做调用前快照并调用 |
| `checking` | 同上，无草稿 | `→ leading`；获取主笔作用域；fx: 调用前快照、调用主笔 |
| `checking` | 漂移检查发现差异，或上游有未解决漂移 | 在同一次转移里把发现的差异写进未解决漂移列表（第 8 节，观察快照取自漂移检查时做的快照）；`gate(漂移)`，首屏列出相关的漂移条目 |
| `drafting` | 草稿 `continue`，未到续跑上限 | 留在 `drafting`；fx: 在同一会话续跑这个席位 |
| `drafting` | 草稿其他结果，仍有草稿在运行 | 留在 `drafting`，记下这个席位的结果 |
| `drafting` | 最后一个草稿结束，全部 `ready` | 释放草稿作用域，获取主笔作用域；`→ leading`；fx: 调用前快照、调用主笔（输入包含全部草稿路径） |
| `drafting` | 最后一个草稿结束，有 `question`、缺失标记、续跑上限或失败 | 释放全部作用域；`gate(草稿问题)`，列出相关席位 |
| `leading` | 主笔 `ready` | `→ submitted`；作用域继续持有；fx: 调用后快照与越界判断、送审快照、送审比较 |
| `leading` | 主笔 `continue`，未到续跑上限 | 留在 `leading`；`continuations + 1`；fx: 同一会话续跑 |
| `leading` | 主笔 `continue`，到达上限 | 释放作用域；`gate(续跑上限)`；fx: 调用后快照与越界判断 |
| `leading` | 主笔 `question` | 释放作用域；`gate(问题)`；fx: 调用后快照与越界判断 |
| `leading` | 主笔标记缺失 | 释放作用域；`gate(标记缺失)`；fx: 调用后快照与越界判断 |
| `leading` | 主笔 `failed` | 释放作用域；`gate(失败)`；fx: 调用后快照与越界判断 |
| `submitted` | 送审快照完成 | `candidate` 记为这次快照的提交号 |
| `submitted` | 有排队的插话 | `→ leading`，交付插话（第 7 节），不发起评审 |
| `submitted` | `manifestValid = false` | 释放作用域；`gate(清单无效)` |
| `submitted` | 首轮，或 `bodyChanged` | `→ reviewing`；作用域继续持有；`round + 1`，`roundsSinceHuman + 1`；fx: 并行调用各只读评审席位；没有只读评审时直接调用第一位 `read-exec` 评审（M3 6.2） |
| `submitted` | 正文未变，`newResponse` | `→ reviewing`，本轮标为驳回轮；`round + 1`，`roundsSinceHuman + 1`；fx: 调用评审（提示词说明正文未改、主笔驳回） |
| `submitted` | 正文未变，无新回应 | 释放作用域；`gate(产物未变)` |
| `reviewing` | 某位评审 `needs-human`、缺失或 `failed` | 释放作用域；`gate(需要人 / 评审失败)`；fx: 取消本轮其余评审（只读，不必等待结束）；fx: 写入已返回的评审文件 |
| `reviewing` | 某位评审返回，仍有评审未返回 | 留在 `reviewing`；fx: 写入这份评审文件 |
| `reviewing` | 只读评审全部返回、无 `needs-human`，还有未运行的 `read-exec` 评审 | 留在 `reviewing`；fx: 写入评审文件；调用前快照，调用下一位 `read-exec` 评审（一次一个，M3 6.2） |
| `reviewing` | 一位 `read-exec` 评审返回（容器已空之后） | 留在 `reviewing`；fx: 调用后快照与越界判断、候选核对 |
| `reviewing` | 上一行的候选核对不通过 | 这位评审的结论作废；释放作用域；`gate(评审失败)`，首屏写明「评审运行的命令改动了送审文件」，列出文件；不再运行其后的评审 |
| `reviewing` | 上一行的候选核对通过，还有未运行的 `read-exec` 评审 | 留在 `reviewing`；fx: 写入评审文件，调用下一位 |
| `reviewing` | 最后一位返回（含 `read-exec` 评审的候选核对已通过），存在 `revise`，驳回轮 | 释放作用域；`gate(驳回未获接受)`；`revise` 在驳回轮里按 `needs-human` 处理 |
| `reviewing` | 最后一位返回，存在 `revise`，普通轮，有排队插话 | `→ leading`，交付插话与评审文件 |
| `reviewing` | 最后一位返回，存在 `revise`，普通轮，`roundsSinceHuman` 到达上限 | 释放作用域；`gate(轮数上限)` |
| `reviewing` | 最后一位返回，存在 `revise`，普通轮，未到上限 | `→ leading`；fx: 调用前快照、在同一会话调用主笔，输入加上本轮评审文件 |
| `reviewing` | 最后一位返回，全部 `pass` | 留在 `reviewing`；fx: 候选核对（工作目录的目标文件是否仍等于 `candidate`） |
| `reviewing` | 候选核对完成，有排队插话 | 作废这次 `pass`，`→ leading`，交付插话 |
| `reviewing` | 候选核对完成，硬关卡 | 释放作用域；`gate(硬关卡通过)` |
| `reviewing` | 候选核对完成，软关卡，存在第 8.3 节的任一条件 | 释放作用域；`gate(硬关卡通过)`，首屏列出原因 |
| `reviewing` | 候选核对完成，软关卡，无第 8.3 节的条件 | 释放作用域；`→ accepting`；fx: 第 9 节的接受副作用 |
| `gate` | `GATE_DECIDED` | 见第 6 节 |
| `accepting` | 接受提交完成 | `→ accepted`；记下 `ArtifactVersion`：`commit` 为接受提交的提交号，`candidateCommit` 为 `candidate`；通知项目级进度 |
| `accepted` | `ACCEPTED_DOC_CHANGED`，需求或功能架构文档 | 保持 `accepted`，产生 `gate(文档新版本)`；已有同原因的待决关卡时，用新快照刷新它，关卡修订号加 1，不另开 |
| `accepted` | `ACCEPTED_DOC_CHANGED`，其他文档 | 保持 `accepted`；fx: 把新快照记为 `ArtifactVersion`（来源：实施中调整）；变更进入下一个关卡的摘要 |
| `accepted` | `REOPEN` | 待决关卡（如有）作废并记入决策；`epoch + 1`；`sessionGeneration + 1`；`→ checking`，理由作为主笔输入；项目级进度向依赖它的实例发 `UPSTREAM_REOPENED` |
| `pending`、`checking`、`submitted`、`gate`、`accepted` | `UPSTREAM_REOPENED` | `epoch + 1`；释放作用域；`→ stale`；待决关卡作废并记入决策（原因：上游重开） |
| `drafting`、`leading`、`reviewing` | `UPSTREAM_REOPENED` | `epoch + 1`；`→ stale`；fx: 取消进行中的调用。作用域在被取消的调用结束后释放 |
| `accepting` | `UPSTREAM_REOPENED` | 记下标记；接受事务照常完成，然后 `epoch + 1`、`→ stale` |
| `stale` | `DEPS_READY`，没有进行中的可写调用 | `sessionGeneration + 1`，`→ checking`；主笔输入包含上游的变化与决策记录 |
| `stale` | `DEPS_READY`，仍有可写调用在结束中 | 记下 `pendingStart`；最后一个可写调用结束时再执行上一行 |
| 任意 | `EFFECT_FAILED`、`RETRY_EFFECT` | 见 9.2 |
| 任意 | `RESTORED` | 见第 10 节 |
| 任意 | `UPSTREAM_BLOCKERS_CHANGED` | 只刷新关卡首屏的阻止信号与接受按钮的可用性；`checking` 中因上游漂移而停在 `gate(漂移)` 的实例，在相关漂移全部解决后回到 `checking` 重新检查 |

### 5.2 写入作用域与租约

写入作用域是一组互斥的租约键（M6）：主笔作用域是目标文件和这一轮的回应文件；每个草稿席位的作用域是它自己的草稿目录；里程碑的作用域是整个工作目录。

规则：

1. **租约由检查点实例持有，而不是由单次调用持有。** 主笔作用域从进入 `leading` 时获取，经过 `submitted`、`reviewing` 一直持有，直到进入 `gate`、`accepting` 或 `stale` 时释放；`revise` 回到 `leading` 时不释放。草稿作用域在 `drafting` 期间持有，主笔开始前释放。获取作用域可能要等待项目里其他写入者释放，这期间实例停在原状态，界面显示「等待写入权」。申请、获批、撤回与释放的完整规则见 5.4。
2. 同一个作用域同一时刻最多一个进行中的可写调用。并行草稿分属不同作用域，可以同时运行。
3. 主笔调用开始前，这个实例的草稿调用必须全部结束。
4. 要发起新的可写调用、而同一作用域里还有已请求取消但尚未结束的调用时，引擎不立即发起，而是把它记进 `pendingStart`；那次调用的 `INVOCATION_ENDED` 到达后再发起。
5. 只读的评审调用不占作用域。取消后可以立即进入下一个状态，晚到的结果由 4.2 的隔离规则丢弃。例外是 `read-exec` 评审：它运行的命令可能写文件，取消后要等它的容器清空（M3 3.4），才能进入下一个状态或开始下一位评审；同一轮里它们排在只读评审之后、一次只跑一个（M3 6.2）。这样只读评审读到的一定是候选内容，每位 `read-exec` 评审开始时工作目录也已核对等于候选内容。

这样，从主笔交回 `ready` 到评审结束，项目室里没有其他写入者能改动目标文件，评审者在工作目录里读到的就是候选提交的内容。评审者照常在真实的工作目录里工作，需要运行测试的评审（`read-exec`）可以使用已安装的依赖和构建产物。评审提示词里的 diff 由影子仓库的两个固定提交计算，不读工作目录。候选核对仍在评审结束时执行一次，用来发现应用外的改动。

已知限制：应用外的程序在评审期间把文件改成 B、又在评审结束前改回 A，平台无法发现。这条写入 `architecture.md` 的 Known Risks。

### 5.3 执行纪元：作废过期的副作用

每个副作用记录产生它时实例的 `epoch`。执行器在启动一个副作用之前比较它的纪元与实例当前的纪元：

- 一致 → 执行。
- 不一致 → 不执行，标记为「已作废」并作为已消费落盘。被打回、重新打开或进入 `stale` 的那次转移本身产生的副作用（取消调用、记录作废的关卡）用的是新纪元，不受影响。
- 例外一：`accepting` 中的接受事务不会因 `UPSTREAM_REOPENED` 而作废。转移表规定接受先完成，再进入 `stale` 并增加纪元。
- 例外二：**租约的调度器通知（`release-scope`、`withdraw-lease`）与取消调用（`cancel-invocation`）永不因纪元作废。** 它们不推进业务，只是让调度器与进程跟上已经落盘的状态：记录已经是「已释放」或「已撤回」，通知却被作废，调度器就会一直占着这个作用域，冲突的写入永远等待。它们按申请 id 或调用 id 幂等，任何时候执行都安全。

**调度器对账**（`reconcile-scheduler`，清理类副作用）：取 `scheduler.snapshot()` 中持有者属于这个实例（或项目）的授予与等待申请，与项目状态文件中的申请记录逐条比对：调度器中有、而记录已是「已释放」「已撤回」或不存在的，调用 `withdraw`（等待中的移出队列，已授予的释放）。记录是「已获批」「待释放」而调度器中没有的，不在这里补授予（那只会发生在重启后，由恢复屏障的 `restoreGranted` 处理）。对账在以下时机执行：每次纪元增加之后；恢复屏障通过之后；删除进入 `drained` 之前（M1/M5 9.1）。

纪元增加时同时清空 `pendingStart`，并按 5.4 撤回实例名下所有等待中和已获批的租约申请（纪元增加后需要的新租约由新纪元的副作用重新申请）。重启重放时同样先比较纪元（第 10 节）。

### 5.4 租约的生命周期

租约的持有者有两种：检查点实例的某个作用域（5.2），以及一次漂移恢复操作（8.2，「项目维护」）。两者遵守同一套生命周期。M4/M6 模块文档在此基础上给出调度器侧的实现。

**状态。** 每一次申请在项目状态文件里有一条记录：申请 id（由发起申请的副作用 id 得出）、持有者、所属副作用链、作用域的键、申请时的纪元、申请时间、状态。状态有五种：

```
等待中 ──获批──→ 已获批 ──决定释放──→ 待释放 ──实际写入已结束──→ 已释放
   │                                  （有实际写入在进行时）
   └──放弃──→ 已撤回                已获批 ──决定释放，且没有写入在进行──→ 已释放
```

**唯一的顺序原则：状态先落盘，再通知调度器。** 记录状态的每一次变化都由转移函数完成，与那次转移一起原子写入；副作用只负责把已经落盘的变化告诉调度器。调度器只在内存里持有等待队列与当前授予，项目状态文件是权威。

**调度器契约**（M6 必须实现）：

1. 一个作用域只有在调度器收到当前持有者的释放通知之后，才能授予与它冲突的下一位。
2. 释放通知只在记录已经以「已释放」或「已撤回」落盘之后发出（由上面的顺序原则保证）。
3. 授予只是让申请者有资格继续；申请者的「已获批」要等转移函数消费 `LEASE_GRANTED` 并落盘之后才生效，在此之前它的链不执行任何需要租约的步骤。

由这三条可以推出：任何时刻，项目状态文件中所有「已获批」与「待释放」的记录在作用域上互不重叠。B 的获批要落盘，调度器必须已经授予 B；调度器授予 B 之前必须收到 A 的释放通知；A 的释放通知发出之前，A 的「已释放」已经落盘。所以文件里不会同时出现 A 和 B 都持有同一作用域。恢复屏障依赖这条性质（第 10 节）。

**申请。** `acquire-scope` 在转移里写入一条「等待中」记录，副作用把申请排进调度器的队列。获批之前，链上后面的副作用不执行。`acquire-scope` 本身没有「正在执行的写入」：它只是在队列里等待。

**获批。** 调度器授予后发出 `LEASE_GRANTED(申请 id)`。转移函数只在记录仍是「等待中」、且申请时的纪元等于持有者当前纪元时，才把它改为「已获批」，让链继续；否则立即把它记为「已释放」并产生释放通知。迟到的获批因此不会推进被放弃的链，也不会留下没人释放的租约。

**放弃（撤回）。** 持有者被放弃时（纪元增加、用户取消漂移恢复、实例进入 `stale`），**同一次转移**按记录当前的状态处理它名下的每一条申请：

| 记录当前状态 | 这次转移把它改为 | 之后的副作用 |
| --- | --- | --- |
| 等待中 | 已撤回，立即生效，不等任何东西 | 通知调度器把它移出队列。在这条通知执行之前到达的 `LEASE_GRANTED` 看到的是「已撤回」，按上面的规则直接释放 |
| 已获批，链上没有实际写入在进行 | 已释放 | 释放通知 |
| 已获批，链上有实际写入在进行（可写调用、`restore-files`） | 待释放 | 先停止写入（见下），确认写入已结束后，再由一次转移改为「已释放」并发出释放通知 |

所以，用户在恢复还在排队时点「取消处理」，撤回立即生效，不会被自己的申请挡住；持有者因错误暂停时也一样，因为等待中的申请不涉及任何写入。

**正常释放。** 链按设计走到「不再需要这个租约」的那一步（进入关卡、恢复文件写完），由那次转移把记录改为「已释放」，再发出释放通知。它是链上的普通一步，严格排在前面的步骤之后；前面的步骤失败暂停时，它也一起等待，租约继续持有（9.2），人重试失败的步骤时仍受保护。

**「写入已结束」的确认。** 只有确认写入不会再发生，「待释放」才能变为「已释放」。超时本身不算结束：超时只说明不再等待，底层写入可能仍在继续。确认的方式：

- 可写调用：经 A14 的受管理进程结束整个进程容器，并**确认容器已空**（POSIX 上进程组中没有任何进程，Windows 上作业对象中没有任何进程）。根进程退出不算结束：Agent 启动的测试、构建或脚本可能仍在写。
- `restore-files`：它在 main 进程里逐个文件以「写临时文件 → 改名替换」完成，每次改名前检查取消标记。取消后，当前这次改名（如果已经开始）完成即停止，之后不再改名；操作在确认「不会再执行任何改名」时上报结束。
- 无法确认时（例如进程始终没有退出，或文件系统调用一直不返回），记录保持「待释放」，租约继续持有，**不放行**。项目室顶部显示诊断：哪个操作、在哪个文件或进程上停住、已经等了多久，并建议的处理（例如检查网络文件系统，或退出该 Agent 进程）。重启后的处理见第 10 节：`restore-files` 在 main 进程里执行，随应用一起结束；Agent 进程则不一定（见下）。

**崩溃后的残留进程。** 由架构决定 A14 统一处理：启动握手保证任何能写文件的 Agent 都已登记容器标识；监护进程在主进程死亡时结束整个容器；应用启动时，恢复屏障之前先处理进程登记表（第 10 节第 2 步）。

**受租约保护的副作用。** 可写调用和 `restore-files` 启动前确认所属链的申请仍是「已获批」。不是的话，不执行，作为失败上报（`LEASE_NOT_HELD`）；人重试时，这条链从 `acquire-scope` 重新开始，并重新做内容核对，而不是从失败的那一步继续。

## 6. 关卡：原因与走向

**一个关卡只有一个原因，不合并。** 按第 5 节的表，每个原因都产生在没有其他待决关卡的时刻：

- 进入 `gate` 状态的转移，都从没有关卡的状态出发。
- `accepted` 上的「文档新版本」关卡只有一种原因；再出现新版本时刷新这个关卡并增加修订号，而不是新增。
- 「恢复」只来自已开始的可写调用，而实例处于 `gate` 时没有正在运行的可写调用。
- 越界条目、上游待确认、未解决漂移、候选被改动是关卡上的信号或接受的前置条件，不是关卡原因。副作用失败也不是关卡原因（9.2）。

如果实现中出现了第二个原因（违反上述不变量），引擎拒绝这次转移，记录诊断日志，保留原有关卡。测试覆盖这条不变量。

| 原因 | `continue`（继续改，意见必填） | `accept`（接受） | `reject-upstream`（打回） |
| --- | --- | --- | --- |
| 文档新版本（在 `accepted` 实例上） | 等同 `REOPEN`，意见作为理由 | 新版本生效：fx 记 `ArtifactVersion`（来源：实施中调整），通知读取过它的下游，不标过期 | 打回到所选上游 |
| 漂移 | 不可用 | 对列出的每个漂移条目选定版本（第 8 节），全部解决后回到 `checking` | 可用 |
| 失败 | 重试：`→ leading`；席位若已换 Agent，`sessionGeneration + 1` | 把当前文件当作送审：`→ submitted` | 可用 |
| 恢复（第 10 节） | 在同一会话续跑：`→ leading` | 把当前文件当作送审：`→ submitted` | 可用 |
| 问题、草稿问题 | 意见作为回答：`→ leading` 或 `→ drafting`（只重跑相关席位），同一会话 | 不可用 | 可用 |
| 续跑上限、标记缺失 | `continuations` 归零，`→ leading`，同一会话 | 把当前文件当作送审：`→ submitted` | 可用 |
| 清单无效 | `→ leading`，意见交给主笔 | 不可用（清单必须通过校验才能展开后续检查点） | 可用 |
| 需要人、评审失败、驳回未获接受、轮数上限、产物未变、硬关卡通过 | `→ leading`，同一会话；输入加上意见和本轮全部评审文件 | `→ accepting`，接受的是 `candidate`；没有全体 `pass` 时记为「接受现状」 | 可用 |

凡是从关卡回到 `leading` 或 `submitted`，都要重新获取写入作用域（5.2）。

### 6.1 决定的校验

M5 收到决定时先在 main 里校验，转移函数再校验一次；任一条件不满足，决定被拒绝，关卡保持待决，界面重新载入首屏并保留用户写的意见。

1. **关卡仍是待决状态，关卡 id 与关卡修订号都与提交的一致。** 关卡在用户查看期间被刷新（例如「文档新版本」出现了更新的快照）时，修订号已经变化，决定被拒绝，用户重新查看后再决定。
2. **对绑定了候选提交的关卡，提交的候选提交与关卡记录的一致。**
3. 打回：提交的影响范围哈希与 main 重新计算的一致；不一致说明影响范围在预览之后变了，要求重新预览。
4. 接受，额外检查：
   - 本检查点读取过的上游没有待决的「文档新版本」关卡，也没有未解决漂移。不提供强制接受：先处理上游，这个关卡的接受按钮随后自动可用（`UPSTREAM_BLOCKERS_CHANGED`）。
   - 工作目录里的目标文件是否仍等于 `candidate`。不等时（关卡期间作用域已释放，项目内另一个群聊可能改了文件），M5 先把差异告诉人，人可以：
     - 「接受送审版本」：接受 `candidate`。M5 在核对时为工作目录做一次快照（观察快照），把差异文件和这个快照的提交号随决定一起提交，转移函数核对后，**在进入 `accepting` 的同一次转移里**把这些文件写进未解决漂移列表，归属于这个检查点。所以在接受结果对下游可见之前，漂移条目已经落盘，下游不会看到「上游已接受、没有漂移」的中间状态。
     - 「以当前文件重新送审」：这是 `continue` 的一个变体，意见可以为空，不调用主笔；重新获取作用域后直接 `→ submitted`，以当前文件做新的送审快照并重新评审，算人的输入。

### 6.2 所有走向的共同规则

- 关卡上的任何决定都算人的输入：`roundsSinceHuman`、`continuations` 归零，排队的插话随意见一并交付。
- 决定记入 `decisions.md`（fx：追加决策）：走向、意见、关卡原因、关卡修订号、候选提交号、引用的评审文件。
- 打回：renderer 在提交前调用 `project:previewReject(projectId, checkpointId, upstreamId)`，项目级进度返回会被标为过期的实例、会被取消的进行中调用，以及这组结果的影响范围哈希；提交时带上这个哈希。目标上游按 `REOPEN` 处理（意见作为理由），依赖它的实例（包括本实例）收到 `UPSTREAM_REOPENED`。

### 6.3 重新打开

已接受的检查点（包括最终评审）可以由人直接重新打开，不需要等后续关卡：renderer 调用 `project:previewReopen(projectId, checkpointId)` 展示影响预览并取得影响范围哈希，再提交 `project:reopen(projectId, checkpointId, reason, impactHash)`，理由必填。之后的处理与打回相同，这是对需求里「任何关卡都可以打回」的补充：没有后续关卡时，也有入口可以回到上游。

## 7. 插话

| 当前状态 | `INTERJECT` | `STOP_AND_DELIVER` |
| --- | --- | --- |
| `leading`、`drafting` | 排队；下一次调用主笔时交付 | fx: 取消当前调用；把「交付插话」记进 `pendingStart`，按 5.2 等旧调用结束后在同一会话发起 |
| `submitted` | 排队；按第 5 节，不发起评审，直接 `→ leading` 交付 | 同左 |
| `reviewing` | 排队；本轮评审照常结束，除 `needs-human` 外一律 `→ leading` 交付，本轮 `pass` 作废 | fx: 取消本轮评审；没有 `read-exec` 评审在运行时立即 `→ leading` 交付；有的话把「交付插话」记进 `pendingStart`，等它的容器清空后再发起（5.2 规则 5） |
| `gate` | 不接受；renderer 把文字作为关卡意见 | 不接受 |
| `pending`、`checking` | 排队；第一次调用主笔时交付 | 不接受 |
| `accepting`、`accepted`、`stale` | 不接受；界面提供「重新打开」入口 | 不接受 |

插话和关卡意见都按目标实例 id 提交（M13 第 6 节）。目标实例的状态已经变化、这类输入不再被接受时，main 拒绝提交并返回原因，renderer 保留用户写下的文字，不自动改投其他目标。

交付插话也算人的输入：`roundsSinceHuman`、`continuations` 归零。

## 8. 未解决漂移与阻止接受的条件

### 8.1 三种「已接受文件被改动」

| 情况 | 怎么发现 | 怎么处理 |
| --- | --- | --- |
| 项目室里的可写调用改了**已经接受**的文档 | 调用结束后的 `detect-accepted-changes` | 实施中调整（R12）：需求或架构文档开「文档新版本」关卡，其他文档自动形成新版本 |
| 人在接受时选了「接受送审版本」，而工作目录与候选提交不同 | 接受前的核对（6.1） | 立即记为未解决漂移 |
| 应用外的改动，或上面两种之外的任何差异 | 检查点开始前的漂移检查 | 记为未解决漂移 |

### 8.2 未解决漂移

项目级列表，存在 M1 的项目状态文件里。**条目是状态，不是副作用**：它在产生它的那次转移里与实例状态一起原子写入（接受送审版本时随进入 `accepting` 写入；漂移检查发现差异时随消费检查结果写入）。

每个条目：id、修订号、文件、归属的已接受检查点、对应的已接受内容（候选提交或已接受提交）、观察快照（发现差异时为工作目录做的影子仓库快照）、发现时间、来源（接受送审版本 / 漂移检查）、状态（未解决 / 处理中 / 已解决 / 作废）。

- **立即可见**：条目一落盘就进入侧边栏「待我决定」，归在所属项目室下。项目全部完成后仍然保留，直到被处理。
- **用户看到的是固定内容**：界面上的 diff 是「已接受内容 ↔ 观察快照」，两端都是影子仓库里的固定提交，不读工作目录的实时内容。同一文件再次发现差异时，用新的观察快照刷新条目，修订号加 1，不另建条目。
- **基准版本**：每个条目记录它所偏离的那个已接受版本（`baseVersion`，即归属检查点的某个 `ArtifactVersion`）。接受送审版本时产生的条目，在原接受事务完成、进入 `accepted` 的那次转移里才填入 `baseVersion`。
- **处理的前提**：归属检查点必须处于 `accepted`，而且它最新的 `ArtifactVersion` 等于条目的 `baseVersion`。
  - 原接受事务还没完成（`accepting`，包括失败暂停中）时，条目照常显示、照常阻止下游接受，但「处理」不可用，界面显示「等待接受完成」。这样就不会出现「先确认了漂移 B，之后原接受事务又登记了 A」的交错。
  - 归属检查点在条目产生之后又形成了新版本（例如需求文档的新版本被接受），条目的基准已经过时：处理被拒绝，引擎以新版本为基准重新比较这些文件。仍有差异就刷新条目（修订号加 1），没有差异就把条目标为已解决。
  - 任何为归属检查点形成新 `ArtifactVersion` 的操作（接受、文档新版本、漂移确认）都核对「最新版本 = 预期基准」，不符即拒绝。同一检查点的版本因此按顺序形成，不会互相覆盖。
- **处理**：renderer 调用 `project:resolveDrift(projectId, [{ itemId, revision }], choice)`。main 与转移函数都核对每个条目的修订号和上面的前提；任一不符，整次处理被拒绝，界面重新载入并要求用户重新查看。
  - 「以工作目录为准」：接受的是**观察快照**里的内容，不是工作目录此刻的内容。fx 先核对工作目录里这些文件是否仍等于观察快照：相等 → 以观察快照为基础形成归属检查点的新 `ArtifactVersion`（来源：漂移确认），通知读取过它的下游；不相等 → 不形成版本，用工作目录的新内容刷新条目（修订号加 1），告诉用户内容又变了、请重新查看。这一处理不写工作目录，不需要租约。
  - 「恢复为已接受版本」：一条以「项目维护」为持有者的副作用链，按 5.4 执行：`acquire-scope`（这些文件的作用域，与检查点和项目内群聊的作用域互斥）→ `verify-observed`（工作目录仍等于观察快照，且基准版本未变）→ `restore-files` → 正常释放。正在运行的里程碑持有整个工作目录时，链停在第一步，界面显示「等待写入权」，用户可以「取消处理」（放弃这条链，按 5.4 撤回）。核对发现内容已变化不算失败：链走到正常释放，刷新条目并要求重新查看。核对或写入出错才是失败：链暂停，租约继续持有，人重试时从失败步骤继续。
  - 两种处理都记入 `decisions.md`；处理期间条目状态为「处理中」，仍然阻止接受。
- **影响**：
  - 读取过归属检查点的下游，在条目解决前不能被接受（6.1、8.3）。
  - 正在运行的下游不被打断；它的下一次调用的提示词里写明「文件 F 与已接受版本不一致，等待人确认」。
  - 开始前的漂移检查遇到相关条目时，停在 `gate(漂移)`；条目在别处被解决后，经 `UPSTREAM_BLOCKERS_CHANGED` 自动回到 `checking`。
- **作废**：归属检查点被打回或重新打开时，它的未解决条目标为作废并记入决策。重新开始的主笔面对的是工作目录的真实状态，漂移失去意义；正在进行的恢复链被放弃，按 5.4 的「放弃」处理它的租约申请。

### 8.3 阻止自动接受的条件

软关卡的全体 `pass` 在下面任一条件成立时转为硬关卡，首屏列出原因：

- 有未处理的越界条目（M6）。越界条目不打断流程，只阻止自动接受。条目存在项目级列表里；人在任何一个关卡上处理（接受即保留这些改动），所有引用它的实例同时视为已处理。
- 本检查点读取过的上游有待决的「文档新版本」关卡或未解决漂移。这一条同时是人工接受的前置条件（6.1）。
- 候选核对发现工作目录的目标文件已经不等于 `candidate`。
- 这一轮期间检测到其他已接受文档的变化，但 `changes.md` 头部缺失。

## 9. 副作用

### 9.1 目录

| 副作用 | 类别 | 做什么 | 幂等方式 | 结果 |
| --- | --- | --- | --- | --- |
| `drift-check` | 必要 | 对每个上游的已接受提交做 `git diff --quiet -- <文件>` | 只读，可重放 | `clean` 或漂移文件列表 |
| `snapshot` | 必要 | 调用前、调用后、送审快照（M4） | 引用 `refs/meldwork/effects/<id>` | 提交号 |
| `evaluate-submission` | 必要 | 与上一轮送审快照比较目标文件；检查 `r<n>-response.md` 是否存在且在本次快照里有变化；校验清单 | 只读，可重放 | `bodyChanged`、`newResponse`、`manifestValid` |
| `verify-candidate` | 必要 | 工作目录的目标文件是否仍等于 `candidate` | 只读，可重放 | `intact` 与差异文件 |
| `invoke-lead`、`invoke-draft`、`invoke-reviewer` | 调用 | 经 M3 调用 | 开始前标记「已开始」；运行 id 由副作用 id 得出 | `INVOCATION_ENDED` |
| `cancel-invocation` | 清理 | 用现有停止机制结束调用 | 调用已结束时无操作 | 无（结束由原调用的 `INVOCATION_ENDED` 体现） |
| `write-review-file` | 必要 | 平台把评审者的最终回答写入 `meldwork/reviews/<检查点>/r<n>-<席位>.md` | 覆盖写同样的内容；这个路径只有平台写，不申请租约 | — |
| `detect-accepted-changes` | 必要 | 每次可写调用结束后，比较各已接受文档与工作目录 | 只读，可重放 | `ACCEPTED_DOC_CHANGED`（发给文档所属的实例） |
| `append-decision`、`stamp-changes` | 必要 | 追加 `decisions.md`；给 `changes.md` 头部补 `to=` | 隐藏标记 `<!-- meldwork:<副作用 id> -->` | — |
| `acquire-scope` | 必要 | 写入「等待中」的申请记录并向 M6 排队（5.4）。它是所属链的第一步，获批之前后面的副作用不执行 | 按申请 id 幂等 | `LEASE_GRANTED` |
| `release-scope` | 必要 | 正常释放的通知（5.4）：记录已在转移里改为「已释放」并落盘，这一步通知调度器 | 按申请 id 幂等 | — |
| `withdraw-lease` | 清理 | 放弃时的调度器通知（5.4）：记录已在转移里改为「已撤回」「已释放」或「待释放」。前两种立即通知调度器移出队列或释放；「待释放」先停止写入，确认结束后经一次转移改为「已释放」再通知 | 按申请 id 幂等 | 写入已结束 |
| `verify-observed` | 必要 | 漂移处理前，核对工作目录中的文件是否仍等于条目的观察快照 | 只读，可重放 | `intact` |
| `accept-commit` | 必要 | 影子仓库的接受提交。树以 `candidate` 为基础，再叠加平台管理的记录文件（本检查点的评审与回应文件、`decisions.md`、`changes.md`）的当前内容；不读工作目录里的目标文件 | 引用 `refs/meldwork/effects/<id>` | 接受提交的提交号 |
| `restore-files` | 必要 | 从影子仓库的已接受提交恢复指定文件到工作目录，每个文件以临时文件加改名原子替换。受租约保护：启动前确认所属申请仍是「已获批」（5.4），且排在 `verify-observed` 之后 | 恢复成同样的内容 | — |
| `user-git-commit` | 外部 | 提交到用户仓库，规则见架构 M4 | 至多一次（见架构 M2） | 成功，或跳过 / 失败并附原因 |
| `reconcile-scheduler` | 清理 | 调度器对账（5.3） | 只读比对后按申请 id 撤回，幂等 | — |
| `drop-snapshot-refs` | 清理 | 关卡决定后删除前后快照引用 | 引用不存在时无操作 | — |
| `notify` | 尽力 | 系统通知 | 不重放 | — |

接受时副作用的顺序：`append-decision` → `stamp-changes` → `accept-commit` → `user-git-commit`（如勾选）→ `drop-snapshot-refs` → `notify`。`decisions.md` 先写，才能进入同一次接受提交。漂移条目不在这里：它已经在进入 `accepting` 时写进状态。

### 9.2 失败

| 类别 | 失败时 |
| --- | --- |
| 必要 | 执行器自动重试 3 次（间隔约 1 秒、5 秒、30 秒）。仍失败则发 `EFFECT_FAILED`：实例记下 `blockedOn`，这个实例后续的必要、调用和外部副作用暂停执行，状态不变；清理类副作用不受暂停影响（见下）。正常流程中的释放是必要副作用，同样暂停，所以失败步骤所在链的租约继续持有，人重试时仍受保护。代价是：暂停期间这个检查点的租约不会因进入关卡而释放，项目内群聊的写入会一直等到人处理这个错误；错误条上写明这一点。项目室顶部出现错误条，写明哪一步失败和错误原因（例如「磁盘空间不足，接受提交未完成」），提供「重试」和「查看诊断」。人点「重试」发 `RETRY_EFFECT`，从失败的那个副作用继续。暂停期间人的决定照常被接受和记录，产生的副作用排在后面 |
| 调用 | 失败本身就是调用结果（`INVOCATION_ENDED` 的 `failed`），按转移表进入失败关卡 |
| 外部 | `user-git-commit` 的前置条件不再满足时，直接跳过，不碰用户的索引。只有这个副作用自己执行过 `git add`、之后提交失败时，才按架构 M4 恢复：只把索引条目仍等于本次暂存内容的路径恢复为 `HEAD`，其余路径保持原样并在通知里列出。两种情况都记为未提交并通知人，项目内部的接受不撤销 |
| 清理 | 取消调用、放弃时的租约通知（`withdraw-lease`）、删除快照引用。只在持有者被放弃时产生（纪元增加、用户取消操作、进入 `stale`），它们**越过暂停**照常执行；被放弃的链不会再有后续步骤需要这些租约，所以越过暂停是安全的。失败时自动重试；仍失败的撤回由恢复屏障按记录状态处理（第 10 节） |
| 尽力 | 记录诊断日志后视为已消费，不重试，不提示 |

`blockedOn` 是实例上的标记，不是关卡原因，也不改变 `state`，所以不会与待决关卡冲突。

纪元变化时：如果 `blockedOn` 指向的副作用因纪元过期而作废（5.3），`blockedOn` 一并清除，实例恢复执行新纪元的副作用。接受事务的副作用不随纪元作废（5.3 的例外），它的 `blockedOn` 保留到人重试成功为止。

## 10. 重启恢复

启动时，每个项目先经过一道**恢复屏障**。屏障通过之前，这个项目不执行任何副作用、不发起任何调用；调度器对这个项目的租约键（`project:<id>:*`）不批给任何其他请求，项目内群聊的可写调用排队等待；改变项目状态的 IPC 返回「正在恢复」，界面在项目室上显示同样的提示。

屏障内按顺序：

1. 读取状态文件；模式版本低于当前版本时先迁移。迁移失败的项目只读打开，在界面上说明，不进入后续步骤。
2. **等待进程登记表处理完成**（A14）。应用启动时，进程登记表先于所有项目的恢复屏障处理，覆盖 Meldwork 启动的所有可写调用，包括项目内群聊：每条未结束的记录确认容器已空，不空就结束容器并再次确认；只有「启动中」而没有容器标识的记录，表示 Agent 从未开始，直接记为已结束。确认不了的记录，在调度器里登记为「残留占用」，按真实路径识别冲突（A14）：项目室调用为它租约作用域对应的文件或目录，项目内群聊与普通群聊为它的工作目录。残留占用与路径相同或互相包含的任何可写申请互斥，直到人在界面上确认已结束或重试成功；对应的实例记为 `blockedOn`。**同一持有者只恢复一次**：这条调用在项目状态文件里如有「已获批」的租约申请，在同一步改为「待释放」并与残留占用关联，此后由残留占用代表它继续阻挡写入。不冲突的作用域照常恢复。
3. 处理中断的调用（只改状态，不执行）。「已开始」的调用副作用，其进程容器已在上一步确认已空（确认不了的已登记为残留占用，实例已阻塞），从 `activeInvocations` 中移除：
   - 只读调用（评审、只读草稿）：记下要以新的副作用 id 重新发起，归入原轮次。
   - 可写调用（主笔、可写草稿）：不重放，产生 `gate(恢复)`，首屏说明中断时间和当时的调用。
   - 已请求取消的调用：直接移除；`pendingStart` 留到屏障之后按 5.2 发起。
4. 纪元与实例当前纪元不一致的待执行副作用标记为已作废（5.3）；随之作废的 `blockedOn` 一并清除（9.2）。
5. 「处理中」的漂移条目：对应恢复链已被放弃的，回到「未解决」。
6. **重建租约**：只重建状态为「已获批」、且没有被第 2 步的残留占用代表的申请，向调度器一次性授予。由 5.4 的调度器契约，项目状态文件中「已获批」与「待释放」的记录互不重叠，所以重建不会冲突；残留占用代表的持有者已在第 2 步转为「待释放」，不会与自己冲突。如果仍然冲突，说明记录损坏，冲突的持有者记为 `blockedOn`，交人处理。「待释放」的记录：容器已在第 2 步确认已空的，以及 `restore-files`（随应用一起结束）的，改为「已释放」；第 2 步确认不了的保持「待释放」，由与它关联的残留占用在调度器里阻挡写入，其他实例拿不到冲突的作用域。「等待中」的申请不在这里处理（例如里程碑持有工作目录、漂移恢复在等待文件租约时崩溃，这是合法状态，不是冲突）；「已撤回」「已释放」的记录忽略。项目内群聊的调用租约不在项目状态文件里；它们的残留进程由第 2 步的进程登记表处理，确认不了的同样登记为残留占用。
7. 以上全部落盘。屏障通过。

屏障之后：

8. 按顺序重放未消费的副作用（`notify` 除外），结果按 4.3 消费；`blockedOn` 非空的实例只执行清理类副作用，其余等人重试。
9. 「等待中」的租约申请按原申请时间重新向调度器排队（5.4）。
10. 发起第 3 步记下的只读调用，以及 `pendingStart`。
11. 「已开始」的 `user-git-commit`：按架构 M4 核对。`HEAD` 带本次尾注 → 记为完成。否则不重试、也不自动恢复索引，因为无法确定中断前是否执行过 `git add`。通知人「提交状态未知」，并列出这些路径在索引中的状态。
12. 待决关卡、未解决漂移原样保留。

## 11. 测试要求

- 转移表穷举：对每个状态 × 每个事件生成用例，表里的组合断言结果状态与副作用列表，表外的组合断言「忽略」。
- 不变量（性质测试）：
  - 项目状态文件中「已获批」与「待释放」的租约记录在作用域上互不重叠。
  - 任何时刻每个实例最多一个待决关卡、一个原因；每个写入作用域最多一个进行中的可写调用；主笔调用与本实例的草稿调用不同时进行。
  - 从主笔交回 `ready` 到评审结束，实例一直持有主笔作用域。
  - 只有全体 `pass` 或人的 `accept` 能进入 `accepting`；接受提交的树中，目标文件等于 `candidate`；`ArtifactVersion.commit` 是接受提交，`candidateCommit` 是候选提交。
  - 上游有待决的「文档新版本」关卡或未解决漂移时，下游不能进入 `accepting`。
  - 进入 `accepted` 的那次落盘，必然已经包含它产生的漂移条目。
  - 正文未变时，不可能连续两轮都送审（驳回轮之后只能 `pass` 或进关卡）。
  - 不经过人的输入，`roundsSinceHuman` 不超过轮数上限、`continuations` 不超过续跑上限。
  - 副作用 id 不在 `activeInvocations` 中的 `INVOCATION_ENDED` 不改变状态。
  - 纪元过期的副作用不会被执行，但 `release-scope`、`withdraw-lease`、`cancel-invocation` 例外：记录已落盘为「已释放」而通知尚未执行时增加纪元，断言通知仍被执行，调度器中不留占用。
  - 每次对账之后，调度器中属于这个实例的授予与等待申请，与项目状态文件中的未结束申请一一对应。
- 时序：
  - 取消评审后立即开始新一轮，再让旧评审返回，断言新一轮不受影响。
  - 取消主笔后旧进程延迟结束，断言新的主笔调用在它结束之后才发起。
  - 关卡在用户查看期间被刷新，断言旧修订号的接受被拒绝。
  - 预览之后影响范围变化，断言打回被拒绝。
  - 下游的主笔调用已排入发件箱但尚未启动时上游被重开，断言这次调用不会启动，重启后也不会。
- 发件箱：在每个副作用执行前后、以及结果落盘前注入崩溃，重启后断言影子仓库、项目状态、`decisions.md` 三者一致，没有实例停在 `submitted` 或 `accepting`，用户仓库至多一次提交。
- 失败：让 `accept-commit` 持续失败，断言实例保持 `accepting` 并带 `blockedOn`，重试成功后进入 `accepted`；让 `user-git-commit` 失败，断言实例仍为 `accepted`，用户索引恢复原样。
- 暂停：一份评审文件写入失败使实例暂停，此时上游重开，断言取消与释放照常执行、`blockedOn` 被清除。
- 漂移：接受送审版本后在 `accept-commit` 之前崩溃，断言重启后漂移条目已存在、下游不能被接受；条目在用户查看后内容又变，断言旧修订号的处理被拒绝；里程碑持有工作目录时请求恢复，断言恢复在租约释放前不写文件。
- 用户仓库：执行前用户自行暂存了本次路径，断言跳过提交且索引不变。
- 租约生命周期：
  - 撤回与获批以两种顺序到达，断言最终都不持有租约。
  - 恢复在排队等待租约时用户取消，而当前持有者因错误暂停，断言撤回立即生效。
  - A 正常释放、调度器授予 B，在每两步之间注入崩溃，断言项目状态文件里从未同时出现 A、B 持有同一作用域，重启重建不报冲突。
  - 让被停止的 Agent 进程不退出，断言记录保持「待释放」、租约不放行、出现诊断。
  - 主进程崩溃而主笔进程存活：重启后断言进程登记表先确认容器已空（或结束容器后再确认），之后才产生恢复关卡、重建租约；让容器无法结束，断言它的作用域登记为残留占用、冲突的申请拿不到、同项目其他不冲突的实例照常恢复。
  - Agent 根进程已退出而它启动的测试进程仍在运行：断言租约不释放，平台结束容器、确认已空后才释放。
  - 主进程在容器启动、身份落盘之前死亡：断言 Agent 从未开始（门未放行）。
  - 主笔持有已获批租约时崩溃、容器无法结束：断言重启后原申请转为「待释放」并由残留占用代表，重建租约不报冲突，冲突的申请拿不到。
  - 普通群聊的残留进程无法结束：断言使用同一目录、其父目录或其子目录的另一个普通群聊和项目室都拿不到写入，使用无关目录的照常运行。
  - 进程组 id 已被无关进程复用：断言不会误结束（组长启动时间不符）。
  - 项目内群聊的 Agent 在崩溃后存活：断言主流程在它的容器确认已空之前拿不到工作目录内的任何作用域。
  - 恢复链在等待租约时上游重开，断言申请被撤回、之后的迟到获批被立即释放。
  - 恢复链在核对步骤出错暂停，断言租约仍持有，重试从核对继续。
  - 让受保护的副作用在租约丢失时启动，断言它不执行，重试从申请重新开始。
  - 里程碑持有工作目录、漂移恢复等待文件租约时崩溃，断言重启不判为冲突，恢复申请在屏障后重新排队。
- 漂移与接受交错：接受提交失败暂停期间尝试处理漂移，断言被拒绝；归属检查点形成新版本后处理旧条目，断言被拒绝并重新比较。
- 重启：断言屏障通过前没有任何副作用执行、项目键没有批给其他请求；断言评审中崩溃重启后，重新发起评审之前主笔作用域已经重建。
