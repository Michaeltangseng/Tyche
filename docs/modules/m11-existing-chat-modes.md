# 模块文档：M11 现有群聊模式

初稿第一版，2026-11-13。依据：`docs/product-target.md`（「与 Meldwork 现有能力的关系」、R24）、`docs/functional-architecture.md` 第三十版（M11 中的用户裁决）、`docs/modules/m3-seat-invocation.md` 定稿（4.6 项目内群聊的调用、第 3 节受管理进程）、`docs/modules/m13-interaction-experience.md` 定稿。

本文回答：现有的几种群聊模式在项目室上线之后怎样存在；本期要改什么、不改什么；将来是否退役由什么决定、退役时怎样做。

## 1. 已定的事（用户裁决，2026-11-13）

- 项目室不是一种新的群聊模式。
- 单次回答、并发回复保留，不改；顺序讨论保留，冻结新功能。
- 自动讨论保留，冻结新功能，旧会话照常可用。
- 项目内群聊不提供自动讨论。
- 是否退役，等项目室在真实项目上跑通之后再定。

## 2. 现状：界面上的模式与后端的对应

读代码之后的一个关键事实：**界面上的几种多 Agent 模式都走 V4 协议**，区别只在参数。

| 界面上的名称 | 文案键 | 前端发出的参数 | 后端 | 位置 |
| --- | --- | --- | --- | --- |
| 单次回答（一位 Agent） | `composer.manual` | `mode: 'manual'`，一个目标 | 非 V4：单 Agent 调用 | `useConversationExecution.js:89-108`、`local-workspace-message-submission.cjs:349-353` |
| 并发回复（多位 Agent，`composer.concurrentResponsesHint`） | `composer.manual` | `mode: 'manual'`，多个目标，`protocol: 'v4'` | V4 的 manual 流程：独立回复 | 同上 |
| 顺序讨论 | `composer.auto` | `mode: 'auto'`，`protocol: 'v4'`，`discussionStyle` 默认 `sequential` | V4 auto runner，顺序风格 | `local-workspace-message-submission.cjs:368-370` |
| 自动讨论（「Beta」） | `composer.autoBeta` | `mode: 'auto'`，`protocol: 'v4'`，`discussionStyle: 'agent-led'` | V4 auto runner，Agent 主导风格：责任图协商、work package、多人合成 | `useConversationExecution.js:107` |
| 单聊 | — | `conversationType: 'direct'` | 非 V4 | — |

由此，架构 M11 中的「项目内群聊不提供自动讨论 V4」应当准确地理解为：**项目内群聊不提供 `discussionStyle: 'agent-led'` 的自动讨论**。并发回复与顺序讨论虽然也走 V4 协议，但它们是需求文档认为「项目室的原语已经覆盖其核心用法」的那两种（并发回复 ≈ 几个席位各写草稿，顺序讨论 ≈ 写作者与评审往复），本身不做责任图协商，项目内照常提供。

规模（架构 M11）：自动讨论执行器家族（`local-workspace-auto-runner*.cjs`，16 个文件）约 7,900 行；`orchestration-v4-records.cjs` 约 2,800 行；消息提交约 1,900 行。

## 3. 本期的改动

### 3.1 项目内群聊不提供自动讨论

为什么：自动讨论由 Agent 协商分工与写入（责任图、work package、多人合成），它在项目内会形成第二个编排器，与项目室的检查点、文档真源与写入协调争夺同一个工作目录（需求「项目室不使用 V4 的责任图协商、work package 和多人合成」）。

改动：

1. **前端**：`ConversationComposer.vue` 的模式选择中，当前群聊的 `projectId` 非空时，不显示「自动讨论」（`composer.autoBeta`）这一项；其余模式照常。
2. **后端**（防止前端之外的调用绕过）：`local-workspace-message-submission.cjs` 的 `validateInput` 中，群聊属于项目室（`projectId` 非空）且 `discussionStyle === 'agent-led'` 时，拒绝并返回 `LOCAL_DISCUSSION_STYLE_UNAVAILABLE_IN_PROJECT`（加入 `docs/error-codes.md`）。主流程群聊不经过这里（它的调用全部是 `project-room` 策略，M3 第 4 节）。
3. **移入项目室的群聊**：普通群聊被移入项目室（项目室创建时选择「把这个群聊加入项目室」，或以后提供的移入入口）时，如果它记住的模式是自动讨论，改为顺序讨论，并在时间线中显示一条系统提示：「项目内不提供自动讨论，已改为顺序讨论。」（中英文案）。已有的自动讨论历史消息与运行记录保持原样，可以查看。
4. **正在进行的自动讨论**：群聊有正在运行的自动讨论时，不允许移入项目室，提示先停止。

### 3.2 受管理进程对所有模式的影响

A14（M3 第 3 节）作用于所有可能写入的调用，包括单次回答、并发回复、顺序讨论、自动讨论中的写入轮次。这不是 M11 的改动，在里程碑 1 实现；这里只登记它对现有模式的影响，供发布说明使用：

- 每一轮可能写入的调用结束后，Agent 留下的进程被结束（M13 第 6 节「普通群聊的写入开关」）。
- 可能写入的 ACP 调用每轮启动一个进程并恢复会话（M3 3.9）；会话策略为 `new` 的 Agent 在这类调用中每轮都是新会话。
- 与项目室工作目录重叠的普通群聊，写入与项目室互斥（M4/M6 A2.3）。

### 3.3 不改动的部分

- V2/V3/V4 的执行器、记录格式、恢复逻辑：**不修改任何代码**。
- 现有群聊的模式选择、轮数设置、自动组队开关：不变（项目内群聊只隐藏自动讨论一项）。
- 现有的运行详情：按 M7/M8 改为完整轨迹组件，这是 M7 的改动，不改变模式的行为。

## 4. 项目内群聊可用的模式

| 模式 | 项目内群聊 | 说明 |
| --- | --- | --- |
| 单次回答 | 提供 | 按 M3 4.6 注入项目室上下文 |
| 并发回复 | 提供 | 每位 Agent 的调用都注入项目室上下文；可能写入的调用以整个工作目录为声明，彼此与检查点循环互斥（M4/M6 A2.3），所以多位 Agent 同时写入时会排队 |
| 顺序讨论 | 提供 | 同上 |
| 自动讨论 | **不提供** | 3.1 |

## 5. 退役的决策（将来）

### 5.1 决策时点与依据

在项目室默认开启（里程碑 9 任务 9.5 的决定）之后，满足以下全部条件时，提出退役自动讨论的决策：

1. 项目室至少完成过 3 个真实项目（从访谈到最终评审），试用记录（里程碑 8 任务 8.7 的格式）没有未解决的严重问题。
2. 在这些项目中，用户没有因为缺少自动讨论而在项目室之外另开自动讨论来完成同一项工作；或者有，但原因能被项目室的现有原语覆盖。
3. README 的产品定位已经从「Auto Discussion」转向项目室（README 把 Auto Discussion V4 写成了核心卖点，退役会改变产品定位，这是用户的决定，不是技术决定）。

是否同时退役顺序讨论、并发回复（用项目室的原语重建），在同一次决策中单独回答。

### 5.2 退役时的做法（供决策后使用）

- **只读兼容**：已有的自动讨论会话、消息、运行记录可以打开查看，不能继续发送。V2/V3/V4 的记录加载代码保留，执行代码删除。
- **模式选择**：自动讨论从模式选择中移除；已记住自动讨论模式的群聊改为顺序讨论并提示。
- **代码**：退役前先列出 `local-workspace-auto-runner*.cjs` 与 `orchestration-v4-records.cjs` 中，哪些被顺序讨论、并发回复使用（它们也走 V4 协议，第 2 节）。只删除自动讨论独有的部分；顺序讨论与并发回复依赖的部分保留，或在决定重建它们之后再删除。
- **文档**：`README.md`、`README.zh-CN.md`、`architecture.md` 中关于 Auto Discussion V4 的段落同步修改。
- 退役在一个单独的里程碑中进行，有自己的任务单与验收。

## 6. 测试（本期）

- 前端：项目内群聊的模式选择中没有自动讨论；普通群聊照常；切换群聊时选择项随之变化。
- 后端：项目内群聊以 `discussionStyle: 'agent-led'` 提交时返回 `LOCAL_DISCUSSION_STYLE_UNAVAILABLE_IN_PROJECT`；以顺序讨论、并发回复提交时正常；普通群聊以自动讨论提交时正常。
- 移入：记住自动讨论模式的群聊移入后改为顺序讨论并出现系统提示；有正在运行的自动讨论时不允许移入。
- 回归：现有群聊的全部模式测试不变、全部通过。
