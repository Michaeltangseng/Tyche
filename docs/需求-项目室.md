# 需求：项目室

讨论稿，2026-11-12。还没开发。用来对齐「群聊之后要做成什么样」，不是实现说明。

## 真实需求

现有群聊是按轮次说话：一起答，或按名单轮流答。角色不会从任务里长出来，也没有一份会留下来的项目文件。

要做的是另一种会话：项目室。人给出目标之后，工作按阶段推进，每个阶段留下一份被接受的文件。评审发生在这份文件写完之后，不发生在每一句发言上。文中的「大任务」指这一份完整产物（原文里的「大人物」按这个意思理解）。

人的习惯是：

1. 一位写作者先写需求文档。
2. 一位评审者挑缺漏。
3. 写作者改。人可以在修改期间插话，把自己的判断加进去。
4. 这样往复，直到这份需求大家基本满意、看不出缺漏。
5. 再写功能架构文档，用同样的方式收口。
6. 再讨论关键模块并写成文档。
7. 再写实施计划。
8. 然后才开发。开发也是做完一个大任务再请人评审，满意后再做下一个。
9. 全部做完之后有一次最终评审：看结果、分析问题、打回修改。

并发各自思考、顺序改同一份文件、对抗性评审，都是某个阶段内部的做法，不是全程固定的群聊模式。需求文档这种单份文件，默认是一个人写、另一个人评。需要几套独立方案时，才让多人同时各自写一版，再收到一份文件里。

## 已经说清的部分

### 组队

用户输入需求。中央主控（或一个等价的决策模块）给出团队席位。每个席位是一个角色，而不只是一个 Agent 种类。

界面放在群聊主区域右上角：全体成员的头像。点击头像弹出配置。人可以改角色、换背后的 Agent、增删席位。

团队草案出来之后，主控 `@用户`，询问这套架构要不要改。用户确定之前，不进入写文档。

### 主流程

用户确定团队之后，按上一节的阶段顺序推进。应用右侧是工作目录的目录树，接近 Codex 的侧栏：可以折叠，可以打开文件预览，可以看到这一版相对上一版改了什么。

阶段产物至少包括：

| 顺序 | 产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1 | 需求文档 | 写作者与评审者基本满意，缺漏已补 |
| 2 | 功能架构文档 | 同上 |
| 3 | 关键模块文档 | 同上，可以按模块拆成多份大任务 |
| 4 | 实施计划 | 同上 |
| 5 | 开发实施 | 每个大任务完成后再评审，不逐次提交都评审 |
| 6 | 最终评审 | 预览和分析之后，要么接受，要么打回 |

## 还没说清的缺口

下面这些不补上，阶段机无法判断「现在该谁写、写完没有、能不能进入下一步」。

### 主控是谁

主控可以是本机某一个 Agent CLI，也可以是应用自己的调度模块。这两种差很多：CLI 会占用一个席位，也有自己的偏好；调度模块只负责组队和推进阶段，不参加写和评。

还要定：主控能不能兼任写作者或评审者。组队时它只能看到用户刚写的那段需求，还是可以先读工作目录。

### 一个席位要记下什么

现在只说了「角色」。一个能执行的席位至少还要有：角色名、这份工作负责什么、由哪个本机 Agent 担任、这一阶段能不能改文件、评审谁、被谁评审。

同一个 Agent 种类能否占两个席位（两个 Claude，两套会话，两个角色）。角色是整个项目固定，还是换阶段时可以换人。

### 用户确认团队时能做什么

草案出现后，用户这边需要明确的动作：接受、改完再接受、退回让主控重判、或者自己指定整套班子。

用户不回复时，流程停在这一步。确认之后如果再改席位，已经写完的文档是否还算数，需要单独定。

### 谁宣布大任务写完了

写作者可以说「我写完了」，主控也可以代为宣布，也可以必须等人点一下才进入评审。三种选择里，只有人点头才能保证不会自己宣布通过。

「各方基本满意」里的各方，默认理解成：这一阶段的写作者改完，指定的评审者不再提出缺漏，并且人接受。若整队每个人都要表态，周期会长一截，和「做完一个大任务再评审」不是同一件事。

不满意时打回给写作者。若最终评审发现需求本身错了，只改代码不够，需求文档要重新打开，后面的架构、模块和计划要标成过期。这个级联规则还没写。

### 评审循环怎么停

默认循环是一位写作者加一位评审者，不是全员轮流发言。对抗性评审是评审者的读法：专门找缺漏和互相矛盾的地方，不是第三种群聊开关。

同一份文件在评审期间只由写作者改。多人同时写，只用于「这一阶段需要几份独立草案」的时候，收口时仍然并成一份文件再评审。

每一份大任务要有评审次数上限。到了上限还不满意，停下来问人，避免无限改。

### 人插话的时候，循环算不算断了

修改期间人可以加入自己的判断。这句话是暂停自动循环、并成为当前文件的新要求，还是只留在聊天里供写作者参考，需要定死。

人改了要求之后，这一阶段已经得到的「满意」作废，评审者要再看一遍。否则插话和已通过的版本会分叉。

### 右侧目录树看什么

目录的根是会话的工作目录。预览和折叠针对其中的文件。

「修改」默认对比这份文件上一次被接受的版本，而不是整个 git 历史。讨论阶段只写文档；实施阶段才改代码。每个被接受的版本要留下内容指纹，下一阶段只引用这个指纹，避免实现对着一份还在改的需求做。

这里的「预览分析」指打开文件、看 diff、由评审者指出问题。不是在应用里把产品界面跑起来。若最终评审还要一个可运行的预览，那是额外的一步。

### 和现有群聊的关系

项目室是一种新的会话，不是顺序讨论或并发回复的另一种按钮。现有的单次回答、并发回复、顺序讨论、自动讨论先保留。

写到一半进程超时或应用退出时，从已经落盘的文件续写。主控若是某个 Agent，它失败时要有人指定接替，否则阶段机停住。
