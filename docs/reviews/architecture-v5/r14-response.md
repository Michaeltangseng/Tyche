# 回应 r14

对应评审：`r14-review.md`。修改后的版本：M3 模块文档第四版、功能架构第二十版。

三条意见全部成立。第 1、2 条有同一个根源，用一个结构性的改动同时修复，并经第三轮原型实测。

**根源与修法**：第三版把监护程序移到 Agent 的进程组之外，是为了让它能对整组发信号而不杀死自己；代价是组号在 Agent 启动之后才能得知（第 2 条的窗口），且没有任何进程在等待期间钉住组号（第 1 条的窗口）。第四版改回：**监护程序领头容器进程组，作为组号的「钉子」。**

- 监护程序以 `detached` 启动、成为新会话与新进程组的组长，组号就是它的 pid，在启动 Agent 之前就已确定并落盘（第 2 条：恢复了「身份落盘后才放行」，没有组号的记录必定从未放行）。
- 监护程序忽略 `SIGTERM`，存活期间组不可能清空、组号不可能被复用。清理顺序：报告 `agentExit` → 对整组 `SIGTERM` → 等待 → 报告 `finalKill` 成员清单 → 对整组 `SIGKILL`（最后一步，连同自己）。等待期间钉子一直在，最后的 `SIGKILL` 发出时钉子仍在，之后不再发任何信号（第 1 条）。
- 评审 r12 的问题（先自杀后报告）只是顺序问题，第四版的顺序是先报告、最后自杀；r13 为绕开它而引入的逐个发信号已经删除。
- 结束的确认改由 main 完成：监护程序退出后，核对 `finalKill` 清单中的进程都已不存在且组已空；之后若组号又能找到成员，只有成员都晚于 `finalKill` 时刻启动才认作复用。
- 监护程序意外退出（未发出 `finalKill`）：钉子已没，main 不再对 `-pgid` 发信号，改为逐个核实成员。
- 恢复时组长存活且启动时间相同：说明它正在执行自己的清理（旧 main 死亡时 fd 3 已关闭），main **不发信号**，只等它完成，最多 10 秒，否则登记残留占用。这避免了 main 与监护程序的清理之间的竞态。

第三轮实测（M3 3.6）：场景 B 整组被结束、写入停止；场景 C 事件依次为 stdout `FINAL-ANSWER` → `agentExit` → `finalKill` → stdout 结束 → 监护程序以 `SIGKILL` 退出，容器已空。实验进程均已清理。

代价：每个可能写入的调用多一个监护进程（最小的 Node 进程）。
