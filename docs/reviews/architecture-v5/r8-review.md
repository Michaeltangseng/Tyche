M4/M6 初稿里发现 **5 处需要修改的问题**，主要集中在具体 Git 命令和恢复顺序。

1. **[P1] 副作用 ID 不能直接用作 Git 引用名**

   B3 使用 `refs/meldwork/effects/<副作用 id>`，但 M2 定义的 ID 是 `<实例 id>:<seq>:<序号>`，含冒号。

   实测 `git update-ref refs/meldwork/effects/cp:1:0 …` 返回 128，引用名非法，快照流程无法完成。

   **建议：**统一定义 ID 到引用名的确定性编码，例如使用完整 ID 的哈希；临时索引文件名也采用跨平台安全的编码。

2. **[P1] `.gitattributes` 仍会改写快照内容，候选核对却可能通过**

   B1 的 `core.autocrlf=false` 不能覆盖工作目录里的属性规则。例如 `*.txt text eol=lf` 会让 `git add` 将 CRLF 文件存成 LF。

   临时仓库实测：工作目录是 CRLF，候选 blob 是 LF，而 B3.3 的候选核对返回“无差异”。随后恢复会改变原始字节，B7 的 SHA-256 前置条件也可能一直不满足。

   **建议：**明确影子仓库保存原始字节，隔离工作目录属性的内容转换，或使用原始 blob 加索引条目的方式构造快照；核对也应比较原始内容及文件模式。

3. **[P1] 内部符号链接别名可以绕过路径互斥**

   A2.2 只解析 `root`，内部路径按字面比较。若 `root/alias` 指向 `root/docs`，两个检查点分别声明 `alias/spec.md` 和 `docs/spec.md`，调度器会判断不冲突，实际却写同一个文件。

   这里没有写到工作目录之外，因此现有 Known Risks 的例外没有覆盖它。

   **建议：**解析声明路径中已存在的符号链接及父目录；不存在的文件解析到最近的已存在祖先。或者明确拒绝包含符号链接的受保护路径，不能仅按字面给予互斥保证。

4. **[P1] 开放写入申请时，尚未恢复的项目可能还没有目录保护**

   C 节在进程登记表处理完成后开放申请，但 `holdRoot(root)` 到下一步各项目恢复时才执行。

   这之间，普通群聊可以先获得项目目录的写入权；随后项目恢复旧租约时发生冲突，合法状态被当成记录损坏。

   **建议：**退出全局恢复模式之前，先为所有待恢复项目建立 `holdRoot`。各项目再独立恢复并逐个开放；无法读取项目状态的目录继续保持保护。

5. **[P2] 强制加入尚不存在的目标或回应文件，会让首次快照失败**

   B3.1 直接对目标和回应文件执行 `git add -f`。主笔首次开工前，目标文件可能还未创建，回应文件通常也不存在。

   实测对尚未存在、也未被跟踪的路径执行该命令会返回 128，按 B9 将触发重试和暂停。

   **建议：**只对存在的文件强制加入；已跟踪文件的删除照常记录；从未存在的文件保留为快照中的“不存在”，不要作为 Git 失败。

工作目录重叠的普通群聊与项目室互斥，这个调整合理，也与评审期间保护送审内容的目标一致。可以继续推进 M3，但以上规则应先修入 M4/M6。
