这轮五项修复基本成立，但还有四处需要在 M4/M6 定稿前补上。

- **[P1] 被 `.gitignore` 忽略的目标文件无法提交到用户仓库**
  B7 使用 `git add -A -- <路径>`，没有 `-f`。目标文件在影子仓库中会被强制纳入，但在用户仓库中仍可能被忽略，导致 `commit --only` 没有该文件。
  建议对本次接受路径使用 `git add -f -A`，并补充“忽略目标文件提交成功”的测试。

- **[P1] 文件大小上限对已跟踪文件无效**
  B2、B3.1、B3.4 依赖 exclude 排除大文件，但 Git 的忽略规则不会排除已经存在于影子索引中的路径。目标文件曾被强制加入，或文件此前低于上限后变大时，`git add -A` 仍会把完整内容写入快照，绕过 50 MB 限制。
  建议在 `git add` 前显式扫描并处理已跟踪的超限路径，或将其作为快照失败处理；LFS 路径也需要同样覆盖。

- **[P1] “解除目录写入保护”仍可绕过恢复安全边界**
  C 第 6 步只写了“经确认”，没有定义确认强度、记录方式和解除后的限制。状态文件读不出时，进程残留、旧租约和接受版本都可能未知；解除保护后普通群聊即可写入，后续恢复可能覆盖未核实内容。
  建议至少要求输入明确的目录路径或风险短语，显示“状态未知、可能仍有 Agent 写入”的原因，记录操作者和时间，并在解除后保持项目室只读、禁止自动恢复和接受。最好先提供一次重新扫描/确认残留进程的操作。

- **[P2] 用户仓库提交的前置条件没有比较文件模式**
  B7 只比较内容 SHA-256。用户把已接受文件改成或改回可执行位、符号链接类型或普通文件类型时，内容哈希仍可能相同，但 `git add` 会把模式变化提交出去，提交内容就不再严格等于接受版本。
  建议同时比较 Git mode、文件类型、存在性和内容；测试中加入“仅改变可执行位”的用户提交前置条件用例。

关于反馈里提出的 LFS 疑问：关闭影子仓库的 LFS filter 后，目标文件按原始内容保存，提交到用户仓库时再由用户仓库的 LFS filter 转成指针，这个方向可以成立；但文档应明确区分“影子仓库比较原始内容”和“用户仓库提交允许生成 LFS 指针”，并覆盖“曾被强制加入后又超过上限”的已跟踪路径问题。
