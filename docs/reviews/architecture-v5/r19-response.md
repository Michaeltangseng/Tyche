| # | 意见 | 处理 | 位置 |
| --- | --- | --- | --- |
| 1 | 写入报错不能一律视为没有发生 | 采纳。**提交点是改名**，三种结果分开处理：改名之前失败 → 没有发生；改名之后目录 `fsync` 失败 → 内存采用新状态，但这次转移的副作用暂停，先对同一内容重写并持久化成功再执行（像租约释放这样的副作用会对外生效，断电后文件若退回旧内容就违反了「状态先落盘」）；通知失败 → 已提交。`atomicWritePrivateFile` 的错误带 `phase`，现有调用方不受影响。另外推广到其他「落盘后才对外生效」的地方：M3 的进程登记表在放行 Agent 之前，同样要求持久化确认 | M1/M5 6.1、第 12 节；M3 3.3；架构 A11 |
| 2 | 删除前没有停止并排空副作用 | 采纳。新增**项目删除屏障**：停止接受新事件、不再发起副作用；取消调用并按 M2 5.4 放弃所有持有者；等待正在执行的副作用（影子仓库队列、`restore-files`、接受提交、用户仓库提交、通知）全部结束，不打断进行中的 git 命令或文件改名；等待所有容器清空，确认不了的登记残留占用、删除停下等人处理。之后才删除数据。拒绝条件只剩「有未处理的残留占用」 | M1/M5 第 9 节 |
| 3 | 删除恢复丢失 `keepChats` | 采纳。删除请求以 `deleting: { requestedAt, keepChats }` 一次落盘，恢复时严格沿用；屏障幂等，重启后从屏障重新执行 | M1/M5 3.1、第 9 节 |
| 4 | 超限后暂停无法落盘 | 采纳。两级上限：常规 8 MiB；控制类写入（暂停与存储故障、取消、租约撤回与释放、删除屏障）可以使用到 9 MiB。常规转移超限时先自动压缩一次再重试，仍超限则以控制类写入记下故障并暂停，提供「压缩项目状态」。压缩从不删除活动记录（未消费的副作用、待决关卡、未结束的租约申请、未解决的漂移与越界、活动调用、当前配置）。控制类写入也超过硬上限时，进入只读并写入独立的小文件 `fault.json`，重启后仍保持只读 | M1/M5 4.6；`project:compact` |
| 5 | 缺少取消漂移恢复的接口 | 采纳。新增 `cancelDriftResolution({ projectId, itemId, revision })`：条目须处于「处理中」且修订号一致；作为放弃恢复链的事件进入项目队列，按 M2 5.4 在同一次转移中持久化撤回 | M1/M5 8.2 |
