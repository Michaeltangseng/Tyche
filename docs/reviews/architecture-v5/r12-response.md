# 回应 r12

对应评审：`r12-review.md`。修改后的版本：M3 模块文档第二版、M2 第九版、M4/M6 定稿第六版（定稿后的补充）、功能架构第十八版。

四条意见全部成立，全部修复。

| # | 意见 | 处理 | 位置 |
| --- | --- | --- | --- |
| 1 | 组号复用导致误杀 | 采纳。原推理只对「旧组一直没有变空」成立。新增**容器标记**：main 为每个容器生成随机值，以 `MELDWORK_CONTAINER` 环境变量交给监护程序与 Agent，子进程默认继承，随机值与组号、组长启动时间一起登记。恢复时：组长存活且启动时间相同 → 整组属于本容器；否则逐个核实成员的环境（macOS 用 `KERN_PROCARGS2`，Linux 用 `/proc/<pid>/environ`），带有本容器标记的才逐个结束，发信号前再比对启动时间；读不到环境或没有标记的一律不发信号；确认不了已空的登记为残留占用 | M3 3.3「容器标记」、3.7 第 2 步；架构 A14 |
| 2 | `read-exec` 破坏候选内容隔离 | 采纳。同一轮先并行运行只读评审，之后 `read-exec` 评审**一次一个**；每个前后快照、纳入越界检测，结束（容器清空）后做候选核对；核对不通过则这位评审的结论作废，进入评审失败关卡，其后的评审不再运行；取消 `read-exec` 评审要等容器清空。由此只读评审读到的一定是候选内容，每位 `read-exec` 评审开始时工作目录也已核对等于候选内容。剩余限制（它运行期间改了又改回，只影响它自己读到的内容）写入 Known Risks | M3 6.2；M2 5.1、5.2 规则 5、第 7 节；M4/M6 A6；架构第 6 节 |
| 3 | 常驻只读 ACP 永不报告完成 | 采纳。结束事件按调用类型分三种时机：可能写入的调用在 `container-empty` 之后；非常驻的只读调用在进程退出之后；常驻 ACP 的只读调用在协议的一轮完成（`prompt` 得到响应，`runPersistentAcpAgent` 返回）之后，进程继续存活是预期行为 | M3 第 5 节 |
| 4 | 监护程序先杀死自己 | 采纳。监护程序不再对整个组发 `SIGKILL`：先经 fd 3 报告 Agent 根进程的退出码与信号，再列出组内其他进程逐个 `SIGTERM`、宽限后逐个 `SIGKILL`，反复列出直到只剩自己（最多 10 轮），然后报告 `containerEmpty` 并退出；仍清不空则报告 `containerStuck`、不退出。启动器把 `exit` / `close`（Agent 的真实结果，供适配器使用）与 `container-empty`（供租约使用）分成两个事件；`kill()` 实现为发送 `stop` 消息，而不是直接发信号，以免监护程序被杀而丢失结果 | M3 3.2「启动器」、3.4 |

说明：第 4 条的问题在文档中，3.6 的原型实际是先打印 Agent 退出再清组，但文档描述的顺序是错的，按评审意见改正，并在测试中加入「留下进程时适配器收到的是 Agent 的真实退出码」。

请下一轮评审重点看：3.7 依赖读取其他进程的环境变量来核实身份。macOS 对同一用户的进程允许读取，但如果 Agent 启动的子进程主动清空了环境，它就无法被核实，会被登记为残留占用，需要人处理。这种「宁可不杀、交人处理」的倾向是否合适。
