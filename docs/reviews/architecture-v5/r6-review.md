# 评审 r6：功能架构第十版、M2 第六版、M13 第六版

结论：`revise`（残留进程恢复方案的 4 个缺口）。原文由用户转交，2026-11-13，按原样保存（去掉了指向本地文件的链接，保留文字）。

这轮的租约交接规则修复了上一轮两条问题，但新增的残留进程恢复方案还有 **4 个缺口**。

1. **[P1] 未能停止的进程，其“待释放”租约没有重建到调度器**

   M2 恢复屏障只重建「已获批」申请，无法确认进程结束的记录保持「待释放」，随后允许其他实例恢复。

   这样，文件里虽然仍记录着占用，内存调度器却没有对应的阻挡；其他检查点或项目群聊可能获得同一作用域，与残留 Agent 同时写入。`blockedOn` 只暂停原实例，不能保护文件。

   **建议：**恢复时把尚未确认结束的「待释放」作用域也注册为占用；其他实例只能在不冲突的作用域继续运行。

2. **[P1] “启动后立即落盘”仍留下无法追踪进程的崩溃窗口**

   架构要求启动 Agent 后上报进程标识，但进程启动与标识落盘并非原子操作。如果在两者之间崩溃，Agent 已能写文件，恢复屏障却找不到它。M2 又只检查“记有进程标识”的调用。

   **建议：**定义启动握手：进程身份持久化前不得开始实际 Agent 工作，并保证握手未完成时主进程死亡不会留下可写进程。至少也要规定：已开始但缺少身份信息的调用按“无法确认结束”阻塞，不能直接进入恢复关卡。

3. **[P1] Agent 主进程退出，不代表它启动的写入子进程全部退出**

   M2 把收到 Agent 进程退出事件作为结束依据；恢复步骤也先检查这个 PID。Agent 启动的测试、构建或脚本可能在父进程退出后继续运行。此时父 PID 已不存在，进程组内仍可能有写入者。

   Windows 同样存在这个问题：现有 `terminateWindowsProcessTree` 在直接子进程已退出时直接返回，不能据此证明后代已退出。

   **建议：**把确认对象改为整次调用的进程树或受管理的进程容器。M3 分别定义 POSIX 与 Windows 的身份、终止和确认规则；不能只用根进程退出事件证明“不会再写”。

4. **[P1] 项目内其他群聊的残留写进程被排除在恢复协议之外**

   M2 明确让项目群聊调用租约随 Run Ledger 的中断记录结束。但核对现有 `recoverInterrupted()`，它只是把运行状态改为 `interrupted`，没有确认操作系统进程结束。群聊调用使用同样的 detached 启动路径，也会在应用崩溃后存活。

   因此，即使所有检查点 Agent 都已停止，旧群聊 Agent 仍可能在新主流程运行时写同一个工作目录。

   **建议：**残留进程登记和恢复应覆盖所有访问项目工作目录的可写调用，包括项目群聊；确认结束前保留对应作用域的占用。

我赞成下一份转向 M4/M6。上述问题需要先明确跨模块契约，具体实现可以分别落到 M4/M6 和 M3，不必继续把实现细节都塞进 M2。
