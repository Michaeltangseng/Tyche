本轮结论仍是 **`revise`**。上一轮多数问题已经落实，但下面几条仍会影响版本可信度和恢复正确性。

1. **[P1] 候选提交绑定了结论，却还没保证评审者读的是候选内容。**
   功能架构「候选提交」目前只要求提示词写明提交号，未定义评审者如何读取应用私有影子仓库里的版本。评审仍读工作目录时，可能读到 B，最后核对时文件又恢复为 A，于是给 A 绑定了针对 B 的结论。
   **建议：**明确提供候选版本的只读文件或读取入口；评审正文与 diff 都来自固定提交。仅在结束时比较工作目录不够。

2. **[P1] 文档新版本刷新原关卡后，旧决定仍可能接受新内容。**
   M2 转移表允许新快照刷新同一个待决关卡，而接受校验只检查关卡 ID。用户看到版本 B 后点击接受，期间后台已把该关卡刷新成 C，main 就可能接受用户没看过的 C。
   **建议：**决定必须携带 `gateRevision` 和候选提交；任一不匹配就拒绝并要求重新查看。打回影响预览也应绑定项目修订号，防止确认时影响范围已经变化。

3. **[P1] 上游重开只取消进行中的调用，没有废止待执行副作用。**
   M2 上游重开规则没有处理发件箱中尚未启动的调用、恢复文件等副作用。比如下游已排入主笔调用，但调用还未执行，上游被重开后下游进入 `stale`；旧副作用仍可能启动，重启重放时也一样。
   **建议：**为副作用绑定执行代数和前置状态。上游重开时废止失效代数的待执行副作用、清理 `pendingStart`；执行器启动前再次校验。已经开始的接受事务则按现有规则完成后标为过期。

4. **[P1] “接受送审版本，稍后检查漂移”遗漏已经启动的下游和最终检查点。**
   M2 接受前置条件只把后续改动交给“下游开始前”处理。但文档新版本关卡出现时，下游里程碑允许继续运行；它不会再次经过开始前的漂移检查。最终检查点接受后更没有下游。
   **建议：**接受候选后，将工作目录差异保存为项目级“未解决漂移”，立即显示；所有相关调用开始及检查点接受前都检查它，项目完成态也保留处理入口。差异本身是真实漂移，不是误报；问题在于不能只等待未来的开始事件来发现它。

5. **[P2] 新增“每个实例只有一个可写调用”与并行草稿直接冲突。**
   M2 第 5.2 节禁止同实例内多个可写调用，但 `drafting` 明确允许多个席位同时写自己的草稿目录；测试又把单写调用设为不变量。
   **建议：**约束改为“同一写入作用域不重叠；主笔启动前，属于该实例的草稿写调用必须全部结束”。正常并行草稿与取消后的旧写调用需要分别处理。

6. **[P2] `ArtifactVersion` 仍记录了错误的提交号。**
   M2 接受完成转移写的是“提交号来自 `candidate`”，但 `accept-commit` 会叠加评审、决策等记录，生成另一个提交。记录候选提交会使已接受版本缺少这些记录。
   **建议：**`ArtifactVersion.commit` 使用 `accept-commit` 的结果；另存 `candidateCommit`，保留送审与接受之间的关联。

7. **[P2] 非调用副作用失败仍没有可恢复的状态转移。**
   M2 副作用目录没有定义影子提交、写评审文件、追加决策等失败后怎么办。例如磁盘写满导致 `accept-commit` 失败，实例只能留在 `accepting`，也没有人的处理入口。
   **建议：**定义副作用失败事件、暂停状态和重试入口；区分必要副作用与通知等可忽略副作用。接受已落盘后的用户 git 提交失败，不应撤销项目内部的接受。

针对你提出的两个重点：

- **单原因关卡：认可这个修法，不要求恢复合并。** 我上一轮“漂移检查期间产生可写恢复关卡”的例子不成立，应撤回。不过单原因只解决操作语义，第 2 条的关卡版本校验仍需补齐。
- **接受送审版本：方向正确。** 需要把剩余工作目录差异变成持久、可处理的状态，覆盖已经运行的下游及项目完成态。

M13 的操作目标、首屏预算、重新打开入口和指标命名，本轮未发现新的阻塞问题。
