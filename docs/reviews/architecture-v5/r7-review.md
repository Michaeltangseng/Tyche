这轮 A14 的方向成立，启动握手和“容器已空”的定义补上了上一轮的主要缺口。仍有 **2 处跨模块规则需要明确**。

1. **[P2] 同一个持有者可能被恢复成两份互相冲突的占用**

   M2 恢复屏障为无法结束的调用登记「残留占用」，但没有把它原来的「已获批」租约改为「待释放」。随后又要求重建所有「已获批」租约，遇到冲突就判为记录损坏。

   触发路径是：主笔持有已获批租约 → 应用崩溃 → 容器无法结束 → 登记残留占用 → 重建原租约。正常的残留进程场景会产生与自身的冲突。

   **建议：**明确两种占用的衔接：同一持有者只恢复一次；无法确认结束时，将原申请转为「待释放」，由残留占用代表它继续阻挡写入。不能把这种重复识别为记录损坏。

2. **[P2] 普通群聊虽然纳入登记表，但残留占用仍不能保护同目录的其他调用**

   架构将普通群聊纳入 A14；但只定义了项目室和项目内群聊的残留作用域。

   核对现有调用代码，普通群聊的租约键按群聊 ID 生成，即使两个群聊使用同一个目录，键也不同。因此，普通群聊 A 的残留进程无法结束时，登记它原来的租约键，并不能阻止群聊 B 或新项目室写入同一目录。

   **建议：**为残留占用补充按实际工作目录识别冲突的规则，并让所有新可写调用检查它。路径规范化、目录包含关系及其与 `project:<id>:…` 键的映射，可以交给 M4/M6 定义。

关于一轮结束后清理开发服务器：我倾向保留这个默认规则，它与“调用结束后不再有后台写入者”的约定一致；需要在启用写入权限时提前说明。POSIX 逃逸进程和 Windows 尚未实现的限制已经明示，本轮不再作为遗漏提出。
