| # | 意见 | 处理 | 位置 |

| 1 | 标记缺失不能证明不属于旧容器 | 采纳，完整写进恢复规则。原则改为：只对能证明属于旧容器的进程发信号；证明不了的不发信号、也不当作「不属于」，而是作为身份未知登记残留占用。逐个成员的判断：启动时间早于记录创建时间 → 不属于（这是唯一可以排除归属的证据）；带有本容器标记 → 属于；环境可读但没有标记 → 身份未知；环境不可读 → 身份未知。所有成员都判为「不属于」，原容器才算已空 | M3 3.7 |
| 2 | 正常清理逐个发信号时的 PID 复用 | **修法更根本：容器改为 Agent 自己的进程组，监护程序在组外。** 监护程序以 `detached` 启动 Agent（Node 调用 `setsid()`），容器就是 Agent 的组，监护程序可以对 `-pgid` 整组原子发信号，不再逐个进程发信号。组内还有成员时组号不会被重新分配，所以正常清理中不存在 PID 复用的竞态。恢复时的判断随之更精确：组长存活、组号与启动时间都相符即为原来的组（组属于 Agent 的会话，其他会话的进程无法加入）；组长存活但启动时间不同即组号已被复用，不发信号。新增的握手窗口（Agent 已启动、组号尚未落盘）由存活的监护程序覆盖，监护程序与 main 同时死亡时按容器标记在同用户进程中查找 | M3 3.2、3.3、3.4、3.7 |
| 3 | `agentExit` 时触发 `close` 截断解析 | 采纳。三个事件分开：`exit` 为 Agent 根进程退出（附真实退出状态）；`close` 在 `exit` 之后、stdout 与 stderr 都读到结束时才发出；`container-empty` 为容器清空（监护程序报告，main 以 `kill(-pgid, 0)` 复核）。为此规定监护程序从不写 fd 1、2，并在启动 Agent 后关闭自己持有的 fd 0、1、2，使输出的结束只取决于 Agent 及其子进程；容器卡住、留下的进程一直持有管道时，`exit` 后最多等 5 秒，再以 `outputTruncated` 发出 `close`，租约仍保持「待释放」 | M3 3.3、3.4、第 11 节 |

第二轮实测（M3 3.6）：按新结构重做场景 B、C，均通过；main 先收到 `{"agentExit":0}`，之后容器被清空、监护程序正常退出。实测还发现一个实现约束：用 `fs.createReadStream` 读取 fd 3 时，监护程序清理完毕后 `process.exit` 挂起不退出（线程池中的阻塞读），改为 `net.Socket({ fd: 3 })` 后正常。已写入 3.5：控制通道必须用非阻塞的流。实验进程均已清理。

请下一轮评审重点看：3.7 中「启动时间早于记录创建时间即不属于」是唯一的排除证据。在 macOS 上，`ps` 的启动时间精度为秒；记录创建与 Agent 启动在同一秒内时，比较应取「早于记录创建时间减 1 秒」，以免把同一秒内启动的成员误判为不属于。已按此写入 3.7 的成员判断表。
