# 评审 r1：功能架构第五版、M2、M13

结论：`revise`。原文由用户转交，2026-11-13，按原样保存。

---

已检查 git diff，以及新增的 M2、M13 两份模块文档。**结论是 `revise`：整体方向可以保留，但还有几处会导致接受错误版本、恢复后卡住或交互无法执行的问题，建议修完再定稿。**

这次把项目关卡收进检查点实例、明确唯一权威状态，并引入副作用发件箱，职责比上一版清楚。M12 负责实现、M13 负责体验规格的分工也成立。

以下按优先级排列。

1. **[P1] 接受时仍可能提交未经评审的内容。**
   功能架构 M4 规定接受时提交工作目录中的目标文件，但没有要求它们仍等于本轮送审快照。比如评审通过 A，人尚未接受，项目内另一个群聊把文件改成 B；此时点接受，B 就可能以 A 的评审结论进入已接受版本。租约只协调写调用，不能覆盖整个等待期。
   建议把关卡、评审结论和接受操作绑定到确定的候选提交；接受前检查目标文件是否变化，变化则刷新关卡、使旧结论失效。评审读取工作目录时也需要检查它读到的是否仍是候选版本。

2. **[P1] 取消后立即重开，缺少旧调用结果的隔离规则。**
   M2 插话处理在取消评审后立即回到 `leading`；但结束事件只携带席位和结论，没有规定校验调用 ID、轮次或会话代数。“在 gate 状态丢弃晚到事件”不够：旧评审返回时，实例可能已经进入新一轮 `reviewing`，被当成本轮结果。取消尚未完成时，也不能直接保证没有旧写入者。
   建议所有调用结果携带并核对 `effectId/invocationId`、轮次和代数；重开写调用前等待取消完成及租约释放。草稿调用的取消完成事件也需明确，不能都依赖 `LEAD_CANCELLED`。

3. **[P1] 发件箱的“完成落盘”和“结果事件生效”之间还有崩溃窗口。**
   功能架构的执行顺序先把副作用标记完成并落盘，再将结果作为事件转移。若在两者之间崩溃，恢复只重放未完成副作用，实例就可能永久停在 `submitted` 或 `accepting`。
   需要明确：副作用结果与对应状态转移在同一次项目原子写入中确认，或者持久化“结果待消费”记录，恢复后继续消费。幂等执行本身不能解决结果丢失。

4. **[P1] 上游新版本待确认，目前只阻止自动接受，仍能被人工绕过。**
   M2 阻止条件会把软关卡升级为硬关卡，但普通关卡的 `accept` 仍直接进入 `accepting`。因此需求新版本未确认时，用户仍能接受依赖它的里程碑；这与 M13 的“确认后才能接受”冲突。
   建议把“上游待确认”定义为接受前置条件，前后端都校验；如允许强制接受，则需要单独定义其版本归属与决策含义。

5. **[P2] 一个输入框尚不能确定多个并行检查点中的操作对象。**
   M13 输入框规则假定存在唯一“当前检查点”，但 M2 允许多个模块检查点并行，甚至一个在运行、两个在等人。此时输入框该插话还是写关卡意见，没有确定规则。已接受实例挂着“文档新版本”关卡时，按 `state` 切换也会判断错误。
   建议显式显示“正在操作：检查点 X / 关卡 Y”，点击进度项或待决卡切换目标；草稿按目标保存，发送时绑定目标 ID，后台状态变化不能把已输入的文字自动改投其他目标。

6. **[P2] 没有撤销可以，但目前连完成后的重开入口也不成立。**
   M13 要求从后续关卡打回；然而最终评审接受后已经没有后续关卡，输入框又禁用。完成态提示说“在检查点上打回”，M2 却只允许待决关卡提交决定。
   建议为已接受检查点增加“重新打开”入口，经影响预览和理由确认后重开，复用级联逻辑即可，不需要延迟接受或增加撤销窗口。

7. **[P2] 关卡原因合并后，只取走向交集不能确定操作语义。**
   M2 关卡合并规定按最高优先级解释接受。例如漂移关卡期间进程崩溃，恢复后又合入“恢复”原因：同一个 `accept` 分别意味着“选择文件版本”和“把当前文件送审”。按优先级执行其中一个，另一个原因并未解决。
   建议定义原因逐项解决及后续恢复路径；如果暂不支持某些组合，就明确禁止合并，按顺序处理，不能仅靠按钮交集。

8. **[P1] 提交用户仓库仍可能夹带用户原本暂存的内容。**
   M4 用户 git 提交只限制 `git add` 的路径，但后续普通 `git commit` 会提交整个索引。用户已有的其他暂存文件也会被提交，同路径原先的部分暂存状态还可能被覆盖。
   模块规格需要明确如何只提交本次接受版本，同时保留用户原有暂存状态。若暂不支持这种情况，应在执行前检测并明确阻止，不能将“只 add 本次路径”等同于“只提交本次内容”。

对反馈中三个重点，我的判断是：

- **不设几秒撤销窗口：可以。** 必须补第 6 条的完成后重开路径。
- **主流程输入框只用于推进流程：可以。** 但先解决并行目标选择，并提供明显的“去项目群聊讨论”入口。
- **自动记录人工要求修改：可以；称为“评审漏检”不准确。** M13 指标应保留事实名称“评审通过后人工要求修改”，不要自动推断发现问题。新想法、偏好变化与漏检不能据此区分，也不必增加用户标注负担。

另外，“首屏不滚动”还需给出内容预算：多位评审各 8 行摘要，加任意长度文件列表和软关卡摘要，无法保证决定区始终可见。建议固定决定区，其他区域限定条数、显示总数并支持展开，在窄窗口和放大字体下验收。
