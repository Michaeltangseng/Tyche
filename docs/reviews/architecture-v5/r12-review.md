本轮发现 **4 个需要修正的问题**，建议处理后再定稿 M3。

1. **[P1] 重启恢复仍可能误杀无关进程组。**
   M3 3.7 的推理只适用于“旧组始终没有变空”。应用退出后，旧组可能已被监护程序清空，随后相同的 PID/PGID 被无关进程组复用；重启时 `pgrep` 非空，按当前规则就会结束这个新组。启动时间不符分支也没有阻止这种误杀。需要先验证容器身份；无法验证时保留残留占用，不能仅凭组号发送信号。

2. **[P1] `read-exec` 能破坏“评审读到的就是送审内容”的保证。**
   M3 第 6 节允许命令写文件，但 M2 5.2 仍把评审当作不占作用域的只读调用，M4/M6 A6 也只为可写调用定义前后快照和归属。评审运行的测试或脚本可以改动目标文件，让另一位评审读到非候选内容；若随后还原，结束时的候选核对也发现不了。进程容器只能确保结束后停止写入，无法隔离评审期间的改动。需要明确 `read-exec` 的写入范围、协调与检测流程，并解决它与候选内容隔离之间的冲突。

3. **[P1] 只读 ACP 调用可能永远不报告完成。**
   M3 第 5 节要求只读调用等进程退出才发结束事件，但 3.9 明确让它继续使用常驻 ACP。现有 `runPersistentAcpAgent` 在一轮 prompt 完成后返回结果，并保留进程；因此正常完成的只读评审可能一直停在 `reviewing`。这里需要按协议的一轮完成报告结束，进程退出仅适用于非持久调用。

4. **[P2] 监护程序会在转报 Agent 结果前杀死自己。**
   M3 3.4 规定对整个组发 `SIGKILL`，然后经 fd 3 报告退出码；监护程序自己就在组内，无法执行后面的报告。按当前“只替换 spawnFn”的接法，适配器还可能收到监护程序的 `SIGKILL`，而非 Agent 的真实退出状态。应先可靠保存或传递 Agent 结果，再清组；启动器需明确区分 Agent 结果与容器清理完成事件。
