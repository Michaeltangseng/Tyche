# 回应 r5

对应评审：`r5-review.md`。修改后的版本：功能架构第十版、M2 模块文档第六版、M13 模块文档第六版。

两条意见与关于「操作卡住」的补充全部成立，全部采纳。两条用同一条原则修复：**租约记录的每一次状态变化都由转移函数完成并落盘，副作用只负责把已经落盘的变化通知调度器。**

| # | 意见 | 处理 | 位置 |
| --- | --- | --- | --- |
| 1 | 撤回等待中的申请，反而要等获批 | 采纳。放弃持有者的那次转移，按记录当前状态直接改写：「等待中」→「已撤回」，立即生效，不等任何东西；「已获批」且没有写入在进行 →「已释放」；「已获批」且有实际写入（可写调用、`restore-files`）在进行 → 新增状态「待释放」，确认写入结束后再改为「已释放」。撤回在转移里已经落盘，所以在调度器通知执行之前到达的 `LEASE_GRANTED` 看到的是「已撤回」，不会推进链，而是直接释放。说明了 `acquire-scope` 本身没有「正在执行的写入」 | M2 5.4「放弃（撤回）」表、9.1 `withdraw-lease` |
| 2 | 释放与下一次授予之间没有落盘屏障 | 采纳，写成调度器契约三条：收到当前持有者的释放通知之前，不把冲突作用域授予下一位；释放通知只在「已释放 / 已撤回」落盘之后发出；授予要经转移函数消费并落盘才生效。由此推出：项目状态文件中「已获批」与「待释放」的记录互不重叠，推导过程写在 5.4 中。恢复屏障改为依赖这条性质，并列入不变量与崩溃注入测试 | M2 5.4「调度器契约」、第 10 节第 5 步、第 11 节 |
| — | 超时不等于写入结束 | 采纳。「待释放」变为「已释放」需要确认：可写调用以收到 Agent 进程的退出事件为准；`restore-files` 在 main 进程里逐个文件「写临时文件 → 改名」，每次改名前检查取消标记，确认不会再执行任何改名时上报结束。无法确认时记录保持「待释放」，租约不放行，项目室显示诊断（哪个操作、停在哪里、等了多久、建议处理）。重启后原进程与原文件操作都已不存在，屏障把「待释放」直接改为「已释放」。上一轮回应里提的「文件写入超时」作废 | M2 5.4「写入已结束的确认」、第 10 节；M13 状态用语 |

请下一轮评审重点看：

1. M2 5.4 契约第 3 条：授予在落盘之前不生效。调度器授予 B、B 的获批尚未落盘时崩溃，B 回到「等待中」重新排队，这一点是否在所有路径上都成立。
2. 崩溃后的残留进程（本轮自查发现，已修复）：现有调用链在非 Windows 平台上以独立进程组启动 Agent（`desktop/src/agents/cli/cli-adapters.cjs:250`、`cli-acp-runner.cjs:684`）。正常退出时 `before-quit` 会经 `workspace.stopAll()` 结束它们（`desktop/src/main.cjs:1157`），但崩溃、强制结束或断电时不会，Agent 可能继续写工作目录。原来的屏障默认「原进程已不存在」，这一点不成立。修复：可写调用启动后上报进程组 id、进程 id 与启动时间并落盘；恢复屏障第 2 步先确认这些进程已结束（启动时间相符才算同一进程，避免误杀），之后才处理中断调用和重建租约；无法确认的实例保持阻塞并给出诊断。请评审这一步是否充分，尤其是 Windows 平台（不使用进程组）的情况。
