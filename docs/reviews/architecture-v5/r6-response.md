# 回应 r6

对应评审：`r6-review.md`。修改后的版本：功能架构第十一版（新增决定 A14）、M2 模块文档第七版、M13 模块文档第七版。

四条意见全部成立，已在代码中逐一核实：`terminateWindowsProcessTree` 在直接子进程已退出时立即返回（`desktop/src/agents/cli/cli-process-support.cjs:47`）；`recoverInterrupted` 只改运行状态（`desktop/src/runs/run-ledger.cjs:568`）。

按评审建议，残留进程的处理不再放在 M2，而是上移为架构决定 **A14「受管理的可写进程」**，作为跨模块契约；M2 只引用它，POSIX 与 Windows 的具体实现及实测放进 M3 模块文档。

| # | 意见 | 处理 | 位置 |
| --- | --- | --- | --- |
| 1 | 确认不了的「待释放」没有在调度器里占用 | 采纳。调度器新增第三种占用「残留占用」：恢复时，进程登记表中确认不了容器已空的记录，它的作用域登记为残留占用，与冲突的申请互斥，直到人确认已结束或重试成功。其他不冲突的作用域照常恢复 | 架构 A14、M6 租约生命周期；M2 第 10 节第 2、6 步；M13 5.7 |
| 2 | 启动与身份落盘之间的窗口 | 采纳完整方案（启动握手），而不只是兜底规则。先写「启动中」记录，再启动容器；容器里最先运行的是一道门，收到主进程的「放行」之前不启动 Agent；主进程拿到容器标识并落盘为「运行中」后才放行。主进程在放行前死亡，门的信号通道关闭，门直接退出。所以能写文件的 Agent 必定已登记容器标识；只有「启动中」而无标识的记录表示 Agent 从未开始。Windows 上门的形式在 M3 中确定 | 架构 A14「启动握手」 |
| 3 | 根进程退出不代表后代已退出 | 采纳。「结束」改为**容器已空**：POSIX 为进程组中没有任何进程，Windows 为作业对象中没有任何进程。正常结束时，根进程退出后仍留在容器里的进程由平台结束，确认已空后才释放租约。另加一层监护：主进程死亡时容器随之结束，从源头减少残留；屏障复核是第二道防线。已知限制：POSIX 上主动脱离进程组的进程（`setsid` 守护进程）无法跟踪；Windows 方案实测前标为未实现。两者都写进 Known Risks，界面上也说明，不静默降级 | 架构 A14「容器与结束的确认」「监护」、第 6 节；M2 5.4 |
| 4 | 项目内群聊的残留进程被排除 | 采纳，而且范围更大：进程登记表在应用级，覆盖 Meldwork 启动的**所有**可写调用（项目室、项目内群聊、普通群聊）。应用启动时先处理登记表，再允许任何可写调用；项目内群聊确认不了的，以 `project:<id>:workdir` 登记为残留占用，主流程在此之前拿不到工作目录内的任何作用域 | 架构 A14「登记表」「恢复屏障复核」；M2 第 10 节第 2 步、第 11 节 |

同意下一份转向 M4/M6。M3 模块文档的优先级相应提前：A14 的平台实现是所有可写调用的前提，需要尽早实测（尤其是 POSIX 上门与监护进程的形式，以及 Windows 作业对象辅助程序的分发方式）。

请下一轮评审重点看：

1. A14 的启动握手和监护在 POSIX 上能否用不经过 shell 的方式实现。我倾向用随应用分发的小型监护程序，同时承担门和监护两个角色，而不是 `sh -c`。
2. 「正常结束时，平台结束容器中的剩余进程」是否会误伤合理的场景，例如 Agent 有意启动、需要跨轮存活的开发服务器。我的判断是：可写调用的一轮结束后，不应该再有写入者，所以误伤在可以接受的范围内；需要常驻的服务应由用户在 Meldwork 之外启动。
