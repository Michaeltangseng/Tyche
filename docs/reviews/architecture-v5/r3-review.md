# 评审 r3：功能架构第七版、M2 第三版、M13 第三版

结论：`revise`（6 处时序问题）。原文由用户转交，2026-11-13，按原样保存（去掉了指向本地文件的链接，保留文字）。

---

本轮仍有 **6 处需要补齐的时序问题**，建议修完再进入实现。

1. **[P1] 未解决漂移落盘之前，接受结果已经对下游生效。**
   M2 在 `accept-commit` 完成时就进入 `accepted`、通知项目进度，但把 `record-drift` 排在它后面。如果后者失败、重试或中途崩溃，下游会暂时看到“上游已接受、没有漂移阻止”。建议把漂移条目与接受状态的发布放在同一次项目状态落盘中，再通知下游。

2. **[P1] 漂移确认仍可能接受用户没看过的内容。**
   M2 的 `resolveDrift` 只提交条目 id 和选择，执行时读取工作目录当前内容；同时，同一条目可以被刷新。用户查看 B 后，文件变成 C，再点击确认，就会直接接受 C。建议漂移预览也绑定修订号和固定快照，内容变化时要求重新查看。

3. **[P1] 恢复漂移文件没有遵守写入租约。**
   同样在 `resolveDrift`，恢复文件直接交给副作用执行；而正在运行的下游明确不会停止。此时里程碑可能还持有整个工作目录的租约，恢复操作会覆盖它正在修改的文件。建议平台的 `restore-files` 也通过 M6 获取对应作用域，拿到租约后重新校验恢复目标。

4. **[P1] 实例暂停会连取消调用一起暂停。**
   M2 暂停实例后续的全部副作用。例如，一份评审文件写入失败导致暂停，其他评审仍在运行；这时上游重开，新产生的取消副作用也无法执行，租约就可能一直占着。纪元增加也没有清除过期 `blockedOn` 的规则。建议取消、释放等清理操作允许越过暂停，并在纪元变化时处理已经作废的失败项。

5. **[P1] 重启时先重放调用，后恢复租约，存在无保护窗口。**
   M2 重启恢复开始重放副作用、重新发起评审，直到第 4 步才恢复写入作用域。这会破坏本轮新增的“评审全过程持有租约”。建议明确启动屏障：先迁移、核对中断调用并重建租约，再允许任何项目调用或副作用执行。

6. **[P1] 用户提交的前置条件失效时，不应重置索引。**
   M2 将“提交失败”和“前置条件不再满足”统一处理为恢复索引到 `HEAD`。如果用户在勾选后自行暂存了本次路径，执行前检查会失败，随后的 reset 却会清掉用户刚做的暂存。建议前置检查失败直接跳过；只有本次副作用实际修改过索引时，才进入受约束的恢复流程。

对于反馈里的取舍，我的判断是：

- **延长租约可以作为当前方案**，但等待范围比“同一批文件”更大：M6 规定项目内群聊申请整个工作目录，因此主流程持有任意文件租约时，其他群聊的所有写入都会等待。产品说明需要如实表达这个代价。
- **影响范围哈希的替代方案合理**，无需因为无关检查点推进而让预览失效。
- **漂移允许运行、阻止接受的方向可以成立**，前提是补上上述发布顺序、版本绑定和恢复写入协调。
