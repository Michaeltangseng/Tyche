本轮发现 5 个需要修改的问题，前三个影响持久化或删除安全。

1. **[P1] 写入报错不能一律视为“操作没有发生”**
   M1/M5 6.1
   现有 `atomicWritePrivateFile` 在改名成功后，还可能因目录 `fsync` 失败而抛错。我注入 `EIO` 实测：调用报错，但磁盘已经是新修订号。按本文规则保留旧内存副本，会造成内存与磁盘分叉，后续写入可能覆盖已落盘的转移。应明确提交点，区分提交前失败、提交后持久性不确定，以及通知失败；后两者不能当作未发生。

2. **[P1] 删除前没有停止并排空项目的副作用执行器**
   M1/M5 第 9 节
   拒绝条件只检查可能写入的 Agent 调用、等待租约和残留占用，未覆盖 main 中正在执行的 `restore-files`、接受提交等副作用，也没有停止内部调度。删除可能在恢复文件尚未结束时撤回租约，或删除影子仓库后仍继续执行接受链。应先建立项目删除屏障，禁止新任务，取消并等待现有操作结束，再释放租约和删除数据。

3. **[P1] 删除恢复丢失 `keepChats`，无法保证保留用户选择的群聊**
   M1/M5 第 9 节
   持久化标记只有 `deleting: true`，但恢复后的第 4 步需要原请求的 `keepChats`。标记写入后立即崩溃，重启就无法知道该保留还是删除其他群聊。应把删除选项与删除标记一起落盘，恢复时严格沿用。

4. **[P2] 状态超限后的暂停与清理缺少可执行的存储路径**
   M1/M5 4.6
   文件接近 8 MiB 时，记录 `blockedOn`、取消调用或租约释放也可能继续超过上限，因此“按 M2 9.2 暂停”本身不保证能落盘。当前也没有明确的减容恢复入口，重试可能永久失败。需要为错误与清理状态预留空间，或定义独立的存储故障阻塞机制，并说明如何恢复。

5. **[P2] IPC 清单缺少漂移恢复的“取消处理”接口**
   M1/M5 8.2
   `resolveDrift` 只有 `workdir / accepted`，其余方法也没有取消恢复链的入口。但 M2 8.2、M13 5.7 明确要求等待写入权时可立即取消。应补充取消接口，绑定条目或恢复链身份，并按 M2 5.4 持久化撤回状态。
