# 回应 r4

对应评审：`r4-review.md`。修改后的版本：功能架构第九版、M2 模块文档第五版、M13 模块文档第五版。

四条意见全部成立，全部修复。第 2、3、4 条的根源相同：租约缺少完整的生命周期定义。所以没有逐条打补丁，而是在 M2 新增 5.4「租约的生命周期」统一处理；按评审建议，调度器侧的实现作为 M4/M6 模块文档的第一部分。

| # | 意见 | 处理 | 位置 |
| --- | --- | --- | --- |
| 1 | 漂移处理与原接受事务交错 | 采纳，并推广为一条通用规则。条目绑定 `baseVersion`（它所偏离的已接受版本），在原接受事务进入 `accepted` 时填入。处理的前提：归属检查点处于 `accepted`，且最新版本等于 `baseVersion`。接受未完成（包括失败暂停）时，条目照常显示、照常阻止下游接受，但不能处理。通用规则：任何为某个检查点形成新版本的操作（接受、文档新版本、漂移确认）都核对「最新版本 = 预期基准」，所以同一检查点的版本按顺序形成。基准过时的条目重新比较，差异消失就自动解决 | M2 8.2「基准版本」「处理的前提」；架构 M5；M13 5.8.1 |
| 2 | 释放越过暂停，提前放掉恢复所需的租约 | 采纳。区分两种释放：**正常释放**是链上的普通一步，前面步骤暂停时它也等待，租约继续持有，重试时仍受保护；**清理释放**只在持有者被放弃时产生，才越过暂停。原「协调」类改名为「清理」类，`acquire-scope`、`release-scope` 改为必要类。受租约保护的副作用（可写调用、`restore-files`）启动前确认租约仍是「已获批」，否则以 `LEASE_NOT_HELD` 失败，重试从申请重新开始并重新核对。代价写明：暂停期间检查点的租约不随进入关卡释放，项目内群聊的写入会一直等到人处理错误 | M2 5.4「释放」「受租约保护的副作用」、9.1、9.2；架构 M2 |
| 3 | 纪元校验撤销不了等待中的租约申请 | 采纳。申请在项目状态文件里有记录，状态为等待中、已获批、已撤回、已释放。获批结果按申请 id 与纪元隔离：记录已撤回或纪元过期时，迟到的获批立即释放。持有者被放弃时产生 `withdraw-lease`，按申请 id 幂等，既把等待中的申请移出队列，也释放恰好已获批的申请，所以撤回与获批无论谁先到，最终都不持有。纪元增加时撤回实例名下所有申请。正在写入的恢复：每个文件原子替换，清理释放等这次写入结束，结果按纪元丢弃，决策记录写明「恢复可能已部分执行」 | M2 5.3、5.4「获批结果的隔离」「撤回」「释放」 |
| 4 | 恢复屏障把等待中当成已持有 | 采纳，按建议修改。屏障只重建「已获批」的申请，它们在崩溃前就同时被授予过，不会重叠；「等待中」的申请在屏障通过后按原申请时间重新排队；评审举的「里程碑持有工作目录、恢复在等待文件租约时崩溃」不再判为冲突 | M2 第 10 节第 5、8 步 |

测试补了：撤回与获批的两种到达顺序；恢复链在等待时上游重开；核对出错暂停后重试仍持有租约；租约丢失时受保护副作用不执行；等待中崩溃重启不判冲突；接受暂停期间处理漂移被拒绝；基准版本过时的条目被拒绝并重新比较（M2 第 11 节）。

请下一轮评审重点看：

1. M2 5.4 的四态模型是否覆盖调度器的全部情况，尤其是「清理释放要等正在执行的副作用结束」：如果那个副作用卡住不结束，清理会不会无限等待。我的倾向是复用调用的取消机制，对文件写入设超时。
2. 8.2「同一检查点的版本按顺序形成」这条通用规则，与「文档新版本」关卡的刷新（修订号加 1）是否还有交错。
